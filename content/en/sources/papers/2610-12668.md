# Recurrent Harness for Agentic Continual Learning

**Source**: Xiao et al., arXiv, 2026-10-08

**Lead**: Language-model agents operating over long interaction streams must adapt online to distribution shifts without updating model weights. Existing harnesses evolve memory only forward—write once, retrieve forever—so overgeneralized or outdated reflections keep misguiding future instances. ReHarness closes the loop with backward revision: after each instance, a revision agent revisits the retrieved reflections using the resulting trajectory as feedback, grounding new content in their source trajectories. It wins on 8 of 9 benchmark–backbone combinations with statistically significant gains.

## Background

Agent harnesses wrap a fixed LLM with persistent runtime scaffolding: memory stores (Mem0), reflection banks (RBank), reflection playbooks with curation (ACE), diverse reflection generators (DoT), and online prompt optimizers (GEPA-Online). Almost all evolve state through forward flow only: extract from the last trajectory, write to state, retrieve later. Once written, a reflection is rarely revised based on how well it actually worked downstream. Under distribution shifts, stale guidance persists and error propagates.

ReHarness targets a strictly online streaming protocol: each instance seen once, no replay, no validation set, no gradients (API models)—only textual feedback in the harness state.

## ReHarness: Closing the Recurrent Loop

Per instance $t$ with harness state $h_t$, three steps:

1. **Forward read**: retrieve top-$k$ ($k=5$) relevant reflections, decision agent acts, environment returns reward → trajectory $\tau_t$
2. **Backward revision**: revision agent independently revises each retrieved reflection $R_i$ into $R'_i$ using its source trajectory $\tau_i$ plus $\tau_t$ as effectiveness feedback—adding missed evidence, correcting unsupported hypotheses, or narrowing applicability conditions. All new content must stay grounded in $\tau_i$ (no leakage from $\tau_t$)
3. **Forward write**: memory agent distills $\tau_t$ into a new reflection $R_t$, using the revised reflections as demonstrations; $h_{t+1} = h'_t \oplus R_t$

Sorting example: "put larger numbers first" (learned on descending sort) misleads an ascending query; revision narrows it to "larger first only if descending," and the fix propagates to future instances.

## Experiments

**Setup**: Strictly online streaming, no train/validation split, harness reset between streams, 3 sampled rollouts per task. Backbones: Claude Opus 4.8, GPT-5.5, Gemini 3.7 Flash (same backbone for all agents in a method). Retrieval: top-5 via Qwen3-Embedding-8B. Baselines: Mem0, RBank, DoT, ACE, GEPA-Online, Top-K Raw, Full Raw.

**Benchmarks**: CL-Bench (6 tasks: cohort studies, codebase adaptation, database exploration, sales prediction, spectrum monitoring, poker), MemoryBench (5 English writing tasks), MemoryArena (5 domains: travel, shopping, web search, math, physics). Metric: normalized gain over the stateless backbone, averaged per stream.

**Results**:

| Result | Number |
|--------|--------|
| Mean normalized gain (ReHarness) | 0.240 — 1st or tied in 8/9 combos; vs Top-K Raw 0.168, Full Raw 0.164 |
| Statistical significance | Paired Wilcoxon + Bonferroni: beats every baseline ($p_{adj}$ < 0.05), incl. Top-K Raw (0.039), Full Raw (0.043) |
| Source grounding of revisions | >95% claims grounded in source trajectory; leakage only 0.8–2.1% |
| Counterfactual replay (CL-Bench, Claude) | 0.335 vs online ReHarness 0.217 vs no-revision 0.144 — revision is meaningful, online use still helps |
| Stability / plasticity (avg) | 0.015 / 0.241 — best average in both; forward-only baselines go negative on stability |
| Token efficiency (CL-Bench, Claude) | ~41.6M total vs Top-K Raw ~52.7M vs Full Raw ~142.1M (compact reflections beat raw history) |
| Ablations | $k=5$ optimal (larger $k$ drifts); dropping revised demos as write guidance: 0.217 → 0.191 |

Weak spot: exploitable poker, where stochastic rewards give noisy revision signals. Limitation: raw trajectories are still stored for future revision (storage overhead).

## Relevance to Software Engineers

- **Self-correcting agent memory**: if you run long-lived agents (support bots, coding assistants, research agents) with a memory/reflection store, add a revision pass—score retrieved memories against the outcome they produced and narrow or correct them
- **Grounding constraint matters**: revisions must cite their source trajectory, not the current one; without it, feedback becomes leakage and reflections drift
- **Small retrieval is enough**: $k=5$ beat larger revision sets; cap revision breadth to control cost and drift
- **Compact beats raw**: storing distilled reflections used ~1/3 the tokens of full history while scoring higher—relevant for context-window budgeting in production agents
- **Measure stability and plasticity separately**: forward-only memories often score negative right after a distribution shift; test both post-shift transfer and within-distribution adaptation
