# Loopback Transformer: Towards a Unified View of Residual Looped Transformers

**Source**: [arXiv:2611.07226](https://arxiv.org/abs/2611.07226) · **Published**: 2026-11-04
**Authors**: Xuan Ouyang, Zefan Cai, Chenlong Zhang, Cheng Luo, Ke Wan, Junjie Hu

## Overview

Looped Transformers cut parameter counts by applying one shared stack of blocks over and over, but sharing parameters says nothing about how the results of the repeated computation are reused — that is decided by the residual design. The paper develops a depth-memory view of residual connections, treating write, transport, and read operations on per-token memory as the common interface of every residual variant. Unrolling this recurrence traces each written value through subsequent transports and reads, so designs as different as plain loops, hyper-connections, and attention-based residual readers can be compared by the weights they place on stored values.

The first analytical finding concerns what should be stored. A full block output contains both its input and its new update, so any weighting of that output also reweights the history already carried by the input — input strength and history are entangled. Storing individual block updates instead, with the shared stack's input kept on a separate path, separates three controls that residual designs otherwise blur: the strength of the input, the total weight given to accumulated updates, and the allocation of that total across individual updates.

The Loopback Transformer implements exactly these three controls. Geometric decay — a fixed retention factor applied at iteration boundaries — bounds the total update weight as loop iterations accumulate and supplies a recency prior, since updates that cross more boundaries shrink geometrically. Attention then learns how to allocate that bounded total across updates according to their content, while the original loop input keeps coefficient one, preserving the usual residual identity path: if all updates vanish, the shared stack simply returns the input. Only the residual aggregation changes; the shared blocks are untouched.

## Key points

- Depth-memory formulation: residual designs are expressed as write/transport/read operations on per-token memory, and unrolling the recurrence yields each stored value's weight in any later readout — a common yardstick for otherwise incompatible designs.
- Storage choice matters: reading full block outputs entangles history with input reweighting; reading individual block updates decouples input strength, total update weight, and per-update allocation.
- Loopback design: iteration-end geometric decay (retention λ) bounds the total update weight and gives a recency prior; a learned attention reader redistributes that total over past block updates by content; the input coefficient stays at one; the shared blocks and their computation are unchanged.
- Decay motivation: Pre-Norm Transformers show high representation similarity across depth and looped models across iterations, so ordinary residual addition reinforces the common component at every application; decay limits this accumulation by shrinking earlier updates.
- Parameter efficiency: on ClimbMix at 20 tokens-per-parameter with matched training tokens and executed depth, Loopback reaches lower validation loss than the standard Transformer at all five reference scales (191M, 374M, 778M, 1.4B, 3B) while storing 40–75% of its Transformer parameters (e.g., 191M uses a 2L→4L(×4)→2L loop at 40.0% of Standard's parameters; 3B uses 6L→6L(×2)→6L at 75%).
- Nine-design comparison: at 191M, 374M, and 778M, Loopback has the lowest validation loss and the highest thirteen-task zero-shot mean among the standard Transformer and seven looped residual designs spanning hyper-connection (mHC, HC, iHC, Hyperloop) and attention-reader (MHAR, AttnRes) families, at matched tokens and depth.
- Larger-scale quality: at 1.4B and 3B Loopback has the higher thirteen-task mean (ahead on 9 and 11 of the 13 tasks respectively) and lower WikiText perplexity (20.29 vs 21.09 at 1.4B; 16.74 vs 17.28 at 3B).
- Code and math: with matched tokens and depth, Loopback attains lower reference-solution loss on GSM8K, MATH-500, HumanEval, and MBPP at both large scales, and five-shot word-problem accuracy at 3B rises from 2.6% to 6.4%.
- Overthinking robustness: shared weights allow extra loop visits at inference, but recurrence beyond the trained count usually degrades predictions; Loopback's validation loss rises far less than Plain Loop's (at eight visits, +0.060 vs +0.454 at 191M; +0.074 vs +0.270 at 374M with four; +0.028 vs +0.248 at 1.4B), and at 3B one extra iteration raises the thirteen-task mean from 49.45% to 50.17%.
- Initialization robustness: under three initialization schemes (fixed-scale Gaussian, GPT-2 residual scaling, PyTorch defaults) with learning rates held fixed, Loopback stays below Standard — at 191M it scores 2.6187/2.6178/2.6138 across the three schemes against Standard's 2.6234/2.6419/2.7145 — addressing the report that a prior looped design's advantage vanished after initialization retuning.

## Details

### The memory interface and the coefficient expansion

The formulation gives each token a memory matrix M_s before block application s, whose read produces the block input and whose write adds the block's value. Expanding the recurrence expresses every later hidden state as a weighted sum of the original input and all past block updates, with coefficients determined by the transport and read operations. Different residual designs — fixed-width recurrent states, explicit history banks, hyper-connection streams, attention readers — become different coefficient schedules over the same stored values. This is what makes the three controls visible: whatever else a design does, its behavior reduces to how it sets the input weight, the total update weight, and the allocation across updates.

### Why decay and attention split the job

The decay-only reference keeps each new update at coefficient one inside an iteration and multiplies all coefficients by λ at iteration boundaries, which is a scalar instance of recurrent memory; it defines Loopback's prior and initialization trajectory. The learned reader then reweights updates after every block application, replacing fixed geometric coefficients with content-dependent ones while preserving the decayed total. The ablation confirms the split: with decay off (λ = 1) the loss degrades to the plain-loop range even with learned allocation, while fixed allocation with decay on already recovers most of the gap; both together are best, and the ordering holds under all three initializations.

### Robustness to additional visits

Overthinking — degradation when a looped model runs more visits than trained — has been reported for other looped language models. Extra destinations in Loopback reuse the last trained visit's queries, so no retraining is needed to test it. Because the geometric prior keeps accumulated update weight bounded and the input path stays intact, added visits move the output less: the loss increase at doubled visit counts is a fraction of Plain Loop's at every tested scale, and at 3B the extra iteration actually improves the thirteen-task mean. This positions Loopback as a compute-recycling knob as well as a parameter saver.

### Scope and provenance

Evaluations use ClimbMix at a 20-TPP budget, with scale names based on Standard's total parameters and Transformer counts excluding embeddings and the vocabulary head; downstream evaluation covers thirteen zero-shot tasks plus WikiText perplexity, code/math solution loss and word-problem accuracy, and robustness sweeps up to twice the trained visit count.
