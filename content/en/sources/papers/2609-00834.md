# Replacing Training with Memory: Listwise Selection for Text-to-SQL

Source: Yeonseok Jeong and 3 other authors, arXiv:2609.00834, Sep 1, 2026. Findings of EMNLP 2026.

**Lead**: Modern Text-to-SQL follows generate-execute-select pipelines — generate multiple candidate queries, then pick the best — and listwise selection (comparing candidates jointly) is widely adopted but expensive to fine-tune. This paper proposes a **fine-tuning-free listwise selector** that replaces the two main fine-tuning objectives with inference-time strategies. First, instead of baking selection behavior into weights, **MaP-SQL** retrieves reusable **structured memories** distilled from training data that encode how natural language maps to schema elements, SQL operations, and expected outputs — explicit decision criteria for listwise evaluation. Second, it mitigates listwise **ordering bias** by aggregating rankings across multiple input permutations, with inference cost controlled via execution results and pointwise scoring. On BIRD-dev it beats the previous state-of-the-art selector method **R^3-SQL by 2.02 execution-accuracy points on average using the same candidate sets, with 2.92x fewer tokens**.

## Why selection is the place to save

Candidate generation keeps getting cheaper as base models improve, but the selector is where fine-tuning cost concentrates: every schema family or workload shift wants a retrained judge. Replacing learned selection criteria with retrieved memories turns a training problem into a retrieval problem — memories are inspectable, reusable across models, and updated without gradient steps. The approach stays compatible with existing LLMs precisely because nothing is fine-tuned.

## Taming positional bias without training

Listwise judges are notoriously order-sensitive: shuffle the candidates and the verdict changes. The paper's answer is permutation aggregation — rank across multiple input orders and combine — while keeping cost down by pruning with execution results and pointwise scores so fewer full listwise comparisons are needed. The reported result is more stable selection with fewer unnecessary comparisons than existing methods.

## What the results show

| Metric (BIRD-dev, same candidate sets) | Result |
|---|---|
| Execution accuracy vs R^3-SQL | +2.02 points on average |
| Token cost | 2.92x fewer tokens |
| Stability | More stable selection without fine-tuning |

Beating the prior selector on identical candidates isolates the contribution: the gain comes from selection quality, not from generating easier candidates.

## Caveats

This summary is abstract-based; per-dataset breakdowns, permutation counts, and latency (tokens are down, but round-trips may differ) live in the full text. Results are on Text-to-SQL benchmarks led by BIRD-dev — transfer to other structured-generation tasks is unshown. Memory quality bounds everything: stale or mismatched memories will mislead the selector exactly as stale few-shot examples do.

## Relevance to SW engineers

- If you run generate-then-select pipelines (SQL, code, queries), a memory-based selector can remove a fine-tuning step from your deployment loop while cutting token spend nearly 3x.
- Distilling "how questions map to schema/operations/outputs" into retrievable criteria is a pattern worth stealing for any domain with stable mapping knowledge and shifting workloads.
- Always control for candidate sets when evaluating selectors — this paper's same-candidate comparison is the honest design; copy it.
