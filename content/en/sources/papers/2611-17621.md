# AscendGYM: A Cost-Aware Kernel Optimization Benchmark for Real-World Workloads on Ascend NPUs

**Source**: [arXiv](https://arxiv.org/abs/2611.17621)
**Published**: 2026-11-13

## Overview

AscendGYM (SLAI Training Platform / Huawei-adjacent Ascend ecosystem) is a benchmark for a concrete and under-measured task: given a correct Ascend NPU kernel implementation, can an agent further improve its performance for a target workload within an acceptable budget while preserving correctness? Unlike kernel-generation benchmarks (KernelBench, NPUKernelBench, CANN Bench), AscendGYM focuses on optimizing existing implementations under input configurations drawn from real training and inference workloads — so improvements map directly onto the corresponding deployments.

The initial suite comprises 48 kernels across three difficulty levels, each paired with test cases whose dtypes and tensor shapes are collected from real workloads, and each shipped with complete runnable initial source code. AscendForge, the built-in execution sandbox, integrates candidate compilation, correctness checking, and performance measurement into a programmatically accessible evaluation service and records optimization trajectories. Two evaluation modes are supported — model evaluation (fixed Default harness) and model–harness evaluation (custom agents). A new metric, the Speedup–Token Score (STS), quantifies performance gains relative to token cost, enabling assessment under tight, moderate, and generous budgets (10M / 20M / 50M tokens per task). Available at https://github.com/SLAI-AITP/AscendGYM.

## Key points

- Metric suite: joint performance–budget metrics (STS, Cost-to-Gain), performance metrics (fast_p, GM Speedup), budget metrics (token consumption, interaction rounds, wall-clock time), and reliability metrics (Candidate Pass Rate, Task Pass Rate).
- Current systems struggle: roughly 70% of evaluated model–harness combinations have GM speedups below 1.2x, with gains concentrated in modest improvements and limited coverage at high speedup thresholds.
- Claude Code/Opus 5 and Codex/GPT-5.6 accelerate all tasks, but seven and three tasks respectively exceed 2x speedup — identical coverage does not imply identical magnitudes; fast_p distinguishes them.
- Tight budget (10M tokens): Warm configuration (GPT-5.6 Luna) achieves the highest STS at all three budgets; cold recovers part of the gap with more search, but warm retains higher score and performance component at 50M tokens.
- Code only outperforms no lessons at all three budgets, but both remain below the full cold configuration — Default harness configuration itself influences outcomes.
- At 50M-token budget and a 10% gain target, Opus 5 with OpenCode vs Claude Code show median attainment costs of 3.8M vs 6.6M tokens, but OpenCode reaches the target on only a subset of tasks while Claude Code covers all 17 Batch-1 tasks.
- GPT-5.6 passes all tasks with each of the three harnesses, yet GM speedup differs substantially: ~1.69x with Codex vs ~1.05x with Claude Code — correctness does not guarantee performance.
- OpenCode/Qwen-35B has modest token/round counts but takes ~11.1 hours per task — token cost and wall-clock time favor different choices.

## Details

- Task design: kernels and input shapes/dtypes/parameters are selected from real training and inference workloads; each task has a concrete optimization target and validation conditions; gains are measured relative to initial-implementation latency under identical conditions.
- Reliability: compilation, correctness, and speed are checked separately through actual execution on NPUs; AscendForge builds host and device code, runs measurement, and returns feedback under predefined validation conditions.
- STS: combines final performance gains with cumulative token consumption at each improvement; CTG reports attainment cost with attainment counts to avoid selecting on conditional medians alone; fast_p measures the fraction of tasks exceeding a speedup threshold.
- Evaluation modes: model–harness evaluation compares agent stacks; model evaluation holds the model fixed (GPT-5.6 Luna) across Default configurations (cold, warm, no lessons, code only) with experience management and search orchestration.
- Reporting practice: GM speedup should be read alongside fast_p coverage; budget metrics (tokens, rounds, wall-clock) must be reported separately since they diverge; non-passing runs are included in cumulative/mean costs.
- Conclusion: AscendGYM poses a meaningful challenge — substantial improvements across a broad range of tasks remain out of reach for current systems under the given initial implementations and evaluation conditions.
