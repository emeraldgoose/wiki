# PreSTO: Predictive Subtree Prefetching for Fast LLM Power Sampling

**Source**: Jiang, Theodoropoulos & Deng, arXiv, 2026-10-09

**Lead**: Power sampling improves LLM reasoning at test time by sampling from a sharpened version of the base model's distribution, but its Metropolis–Hastings sampler (PowerMH) is slow because each accept/reject decision must complete before the next proposal is generated. Predictive Subtree Prefetching (PreSTO) views future MH outcomes as a tree of accept/reject decisions, generates the proposals of a prefetched subtree in one batched model call, and follows the realized path with the original acceptance rule—provably leaving the MH transition kernel unchanged. Across seven datasets and five base LLMs, PreSTO achieves median speedups of $1.71\times$ (PowerMH), $1.91\times$ (EntropyCut), and $2.33\times$ (MultiTryMH).

## Background

Recent work suggests RL post-training largely sharpens the base model's distribution, and sampling directly from a power-sharpened target $\pi_{\alpha}(\mathbf{x}_{1:n} \mid \mathbf{x}_0) \propto p_0(\mathbf{x}_{1:n} \mid \mathbf{x}_0)^{\alpha}$ with $\alpha > 1$ can match RL post-training without training. Exact sampling is intractable, so PowerMH runs block-by-block MH with suffix resampling: at each step it draws a cut index $c$, resamples the suffix from a proposal LLM $q_{\tau}$, and accepts with the standard MH probability.

The bottleneck is sequential dependence: proposal $k+1$ can only be generated after the accept/reject outcome at step $k$. On MATH500, PowerMH generates up to $8.8\times$ as many tokens as standard sampling; on LCB V6 with Qwen3.5-9B it takes $6.5\times$–$18.4\times$ as long per prompt as single-sample low-temperature sampling. Prior work responds by changing the sampler (SMC, replica exchange), approximating the target, refining proposals (entropy-based cuts), or modifying the objective—PreSTO instead accelerates PowerMH itself.

## Subtree Prefetching for MH-Based Power Sharpening

Each round, PreSTO builds a prefetched subtree, scores its feasible proposals in one batched call, and walks the realized accept/reject path:

1. **Collecting feasible requests**: Breadth-first traversal gathers up to $N_{\mathrm{pf}}$ suffix-resampling requests. A request at an acceptance child with cut $c'$ is feasible in the current batch only if $c' \leq c$ (the parent cut), because then its conditioning prefix is already available at the root—its conditional distribution is unchanged by generating it early.
2. **Batched proposal sampling**: All feasible requests go to the serving engine (vLLM/SGLang) in one call. Shared prefixes reuse KV cache via prefix caching, so one batched call replaces many serial calls.
3. **MH transitions over the subtree**: Starting from the root, accept/reject decisions are simulated sequentially with the original acceptance probabilities, advancing $k_{\Delta} \geq 1$ transitions per round.

Proposition 1 proves PreSTO-PowerMH preserves the exact MH transition kernel—only the proposal-generation schedule changes.

## Predictive Traversal Rule

Under the sharpened target, most acceptance probabilities collapse toward 0 or 1: with $\epsilon = 0.01$, 67%–95% of edges across the seven datasets are $\epsilon$-certain, so the reachable ($\epsilon$-rounded) subtree is sparse and nearly unary. Default BFS wastes budget on nodes MH rarely visits. The predictive traversal rule instead predicts each decision's $\epsilon$-certainty class with a three-class logistic regression on the cut fraction $c_j/T$, converts it to branch probabilities, and selects up to $N_{\mathrm{pf}}$ requests maximizing the predicted number of completed transitions (solved by dynamic programming). On LCB V6 with Qwen3.5-9B it is $1.25\times$–$1.37\times$ faster than BFS at all five budgets tested.

## Experiments

**Setup**: Samplers PowerMH, EntropyCut, MultiTryMH and their PreSTO variants; five base LLMs including Qwen3-4B/8B and Qwen3.5-4B/9B; seven datasets (MATH500, AIME 24&25, MBPP, GPQA, HumanEval, MMLU, LCB V6); $K = 100$ MH steps, prefetch budget $N_{\mathrm{pf}} = 20$, first 20 prompts. Metric: mean cumulative model-call time of baseline divided by PreSTO variant.

**Benchmarks**: The seven datasets above, spanning competition math, code generation, and science QA.

**Results**:

| Baseline | Median speedup (105 settings) | Detail |
|----------|-------------------------------|--------|
| PowerMH | $1.71\times$ | $3.9\times$ fewer model calls, each $2.1\times$ longer; max $2.29\times$ |
| EntropyCut | $1.91\times$ | max $2.85\times$ |
| MultiTryMH | $2.33\times$ | — |

PreSTO is never slower than its baseline in any setting. Output-distribution checks support exactness: log-likelihood and confidence of PreSTO outputs pass paired equivalence tests against baselines in 29 of 38 comparisons.

## Relevance to Software Engineers

PreSTO is a serving-side optimization with no model or sampler changes: if you run test-time scaling (repeated sampling, self-consistency, agentic rollouts) behind vLLM or SGLang, the same idea—batch speculative futures that share prefixes, then commit the realized path—converts serial latency into one prefix-cached batch. The $\epsilon$-certainty observation generalizes: whenever a stochastic search collapses to near-deterministic branches, budget should follow predicted reach probability, not BFS order. One caveat: gains depend on prefix-cache reuse, so per-batch cost ($1.9\times$–$3.4\times$) must be weighed against saved round trips in your serving setup.
