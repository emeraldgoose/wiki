# FinForesight: A Diagnostic Backtesting Benchmark for Deep Research Systems in Financial Forecasting

**Source**: [arXiv:2611.01621](https://arxiv.org/abs/2611.01621) · **Published**: 2026-11-01
**Authors**: Fengyuan Liu, Mukai Li, Jieshun You, Yilin Zheng, Chenjia Min, Yizhou Zhang, Harper Chen, Qi Liu

## Overview

Deep research systems can gather time-sensitive evidence and reason through it in multiple steps, which makes them attractive for financial forecasting. The real difficulty is evaluation: a historical backtest may look like good forecasting even when the model is partly recalling outcomes or using evidence that was not available at prediction time; live forecasting avoids that leakage but only provides feedback after events resolve. FinForesight is a diagnostic benchmark built around this tension. It is designed for deep research systems in financial markets and uses historical backtests in a tightly controlled way so that their scores can be treated as evidence about future forecasting rather than memory.

The benchmark covers the Chinese, U.S., and Hong Kong markets and evaluates four forecasting targets: stock valuation, relative return ranking, event direction, and future financial fundamentals. It also includes two capability diagnostics, counterfactual reasoning and financial calculation, which are scored separately from the forecasting score so that a headline number is not inflated by general reasoning skills. Instances are generated relative to each model's knowledge cutoff, and a harness-compatible framework restricts retrieved evidence to what had been public at the forecast date. This makes it possible to compare controlled historical backtests with live forecasting and to diagnose where measured performance comes from.

The paper's larger argument is that forecasting scores must be read alongside the conditions that produced them. Pretraining-era evaluations tend to show historical score advantages, while stronger retrieval controls bring post-cutoff backtests closer to live results. The authors therefore treat controlled historical evaluation as a useful source of timely feedback during development, provided it is accompanied by leakage checks, prompt and numerical sensitivity checks, and explicit distinction between forecasting and capability diagnostics.

## Key points

- The four forecasting tasks are valuation, return ranking, event direction, and future financial fundamentals; the two separate diagnostics are counterfactual reasoning and financial calculation.
- The benchmark spans multiple markets, so cross-market differences are visible rather than hiding behind a single U.S.-only score.
- Explicit temporal splits separate pretraining-era history from resolved post-cutoff events and unresolved live events.
- A time-controlled retrieval framework is meant to prevent outcomes or post-hoc analysis from being leaked into evidence.
- Stronger retrieval controls narrow the gap between post-cutoff backtests and live results, suggesting leakage is a real source of apparent forecast performance.
- Forecasting attribution includes prompt rewrites and numerical perturbations, exposing brittle or explanation-sensitive predictions.
- The finance-specific workflow does not consistently beat general-purpose deep research harnesses in the reported experiments.
- Across model-harness configurations, aggregate forecasting scores need interpretation by information-access policy.

## Details

- **Three evaluation regimes.** Knowledge cutoffs and benchmark run dates divide history into pretraining-era, resolved post-cutoff, and live intervals. Only resolved post-cutoff events provide timely scored feedback.
- **Retrieval policy is central.** Applying search date filters alone is not enough; the framework audits retrieved evidence against the forecast date.
- **Why diagnostics are separate.** Better counterfactual or arithmetic skill is valuable, but it should not be conflated with finance forecasting; reporting them separately keeps the main evaluation honest.
- **Practical use.** The benchmark is intended as a development-time signal, with delayed live scoring used for validation when events resolve.
- Code and benchmark data are publicly available.
