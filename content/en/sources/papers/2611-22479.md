# Exploited Before It Was Fixed? Vulnerability Timelines from Open, Machine-Readable Evidence

**Source**: [arXiv:2611.22479](https://arxiv.org/abs/2611.22479) · **Published**: 2026-11-17 (v1)
**Authors**: Cédric Bonhomme, Alexandre Dulaunoy

## Overview

When a vulnerability is exploited, the question that matters to a defender is whether a fix existed and, if not, how long exploitation ran before one did. Prior answers (Frei et al., Bilge and Dumitraş's 312-day average zero-days, Householder et al.'s median 2 days vs mean 91 days to exploit publication) rest on whatever data each author could assemble and are reported mainly as fragile aggregates. This paper instead computes per-vulnerability intervals — exploitation to patch, plus lifecycle intervals adapted from the 2015 VTEM framework — from open, machine-readable evidence: CVE and CSAF records, publisher timelines via GCVE BCP-05-X-03, several Known Exploited Vulnerabilities catalogs, and typed sightings.

The evidence model selects the earliest evidence of each lifecycle event, uses only records that state they describe the vulnerability itself, carries the precision of every date into explicit bounds, and traces every figure to the record that produced it. It is implemented in Vulnerability-Lookup, where each vulnerability page and the timeline API expose the intervals with their evidence. Measured on one instance as of 2026-11-03 over 3,758 identifiers with exploitation evidence (3,690 of them CVEs), the headline finding is that the intervals can be computed but what limits them is the evidence publishers release: disclosure is dated for 98.1%, patch evidence exists for only 15.7%, and the vendor-side dates VTEM requires (report, acknowledgement) are never published — so VTEM's time-to-patch and vendor-response metrics cannot be computed for any exploited vulnerability.

## Key points

- **Coverage**: of 3,758 identifiers with exploitation evidence, exploitation anchors 99.9%, disclosure 98.1%, public exploit 36.4%, discovery 9.6%, patch 15.7%; report/acknowledgement 0% — vendor-side VTEM dates are never published.
- **What exploitation dates are**: catalog listing dates dominate (2,401 of 3,756 anchors; 875 first-hand honeypot/sinkhole observations, 343 classified channel posts); 1,041 anchors fall on catalog batch listing/import days and date the catalog, not the exploitation.
- **Exploitation to patch**: excluding batch listings and unordered same-day pairs, of 455 comparable identifiers, patch evidence precedes exploitation evidence for 307 (median −188.3 days) and follows it for only 59, by a median of 7.6 days (IQR 3.8–22.4), mostly from a catalog listing to a distributor's (e.g., Red Hat's) fix — narrower than "time from exploitation to patch".
- **Other intervals**: exploitation follows disclosure by a median 298 days (2,389 identifiers); patch follows disclosure by a median 13.3 days; first public proof of concept follows disclosure by a median 610 days.
- **Correctable data**: traceability exposed that one collector had recorded Exploit-DB entries as exploitation (40% of exploitation dates in a first measurement, moving the median patch-after-exploitation from 39.5 to 10.6 days), that one catalog dated 11% of listings with the CVE publication instant, and SUSE/Red Hat advisory copies had displaced 49 patch anchors.
- **Closing the gap**: publisher timelines in records (GCVE BCP-05-X-03), catalogs separating first observation from listing date, and dated upstream fix events would supply the missing dates.

## Details

The model turns every dated statement about a vulnerability into typed anchors — discovery (V), report (R), acknowledgement (A), disclosure (D), public exploit (X), exploitation (E), patch (P) — taking the earliest input across all records as the tightest bound, keeping source, field path, precision and basis so each figure is traceable. Record identity is strict: a linked record counts only when it states it describes the requested vulnerability; advisories that gain a vulnerability in a later revision use the revision date for it. Day-precision dates are treated as standing for any instant of their UTC day, so a same-day sighting and fix yields an interval of −1 to +1 day with unknown order, not a measured zero. Metrics keep single start/end pairs (vendor response A−R, time to patch P−R, total time to patch P−V, disclosure to patch P−D, exploitation to patch (P or N)−E, etc.), report distributions split by sign with medians and IQRs, and treat missing anchors as unavailable rather than zero.

Data comes from a Vulnerability-Lookup instance holding the CVE 5 corpus (418,263 records), 53 CSAF providers, national advisories, OSV/GitHub advisories, six KEV catalogs (6,470 exploited entries), 55,815 exploited sightings and 26,925 proof-of-concept sightings. Patch anchors are concentrated in distributor/vendor CSAF fixes (323 Red Hat, 209 Microsoft, 40 ENISA patchedSince); for most libraries the first recorded fix is a distributor's package, not the upstream release. Threats to validity are explicit: exploitation dates are upper bounds at best; the population inherits catalog selection bias; 25.9% of identifiers without dated patch evidence have an undated "patch"-tagged reference, which is not a verified fix; and the only discovery dates are distributors' CSAF discovery_date values (192 of 362 later than public disclosure). The measurement script and per-identifier output are published with the paper; code is AGPL-3.0 Vulnerability-Lookup at commit a9c6edf2.
