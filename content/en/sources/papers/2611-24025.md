# Intent Contracts: Taking Tools Away from Agents

**Source**: [huggingface](https://arxiv.org/abs/2611.24025) · **Published**: 2026-11-18
**Authors**: Ziyuan Wang, Genliang Zhu, Xiaobo Chen, Chu Wang

## Overview

Intent contracts are an authorization interface for tool-using LLM agents in which the planning model holds no tools. For each step the planner submits a short logged contract containing a goal, a verbatim quotation of the user, and scope fields. Code validates the contract and a small trusted model checks it against the user's words and writes the tool call itself. Provided validation and dispatch code is correct, every executed call is written by the trusted model, the planner's influence is confined to a contract logged before it, and the trusted side decides how much of a request to carry out. The approach is compared with blind and intent-visible reviewers of planner-written commands on AmPermBench task families using gpt-6.1-terra as planner and GLM-5.3-Flash as trusted model.

## Key points

- The planner has no environment tools; it submits a contract with goal, user quotation, egress hosts, write prefixes, and error policy.
- Validation code checks quotation, scope, and goal format before the trusted model writes at most one tool call per step.
- Under contracts, every object changed is named in the goal of the contract that produced the change; under review, objects are rarely named in goals.
- When the planner adds work the user never asked for, contracts complete the user's task in 27/30 runs vs 16/30 for intent-visible reviewer.
- Contracts do not reduce unauthorized actions and are indistinguishable from blind review for ambiguous references; 40-49% of state-changing conditions hit wrong targets when environment terms are clarified.
- The error stems from the planner's choice of objects for ambiguous references, which the trusted model cannot verify without environment visibility.

## Details

The interface separates planning from execution to limit planner influence. The trusted side holds original user messages, plugin configuration, and tool-dispatch code. The strong planner is untrusted for scope, while the small model is trusted to try to follow the user and can make mistakes. Properties such as "trusted model writes every executed call" and "logged contract precedes every call" hold by construction when validation and dispatch code is correct.

Compared with blind review, where the reviewer sees only user words and proposed command, and intent-visible review, where the reviewer also sees goal and checked quotation, contract execution shows better partial execution: the trusted model can refuse part of a step rather than the whole command. The evaluation uses benign over-reach with one planner and one small model, not adversarial planners.

The authors release the plugin and run records. Limitations include inability to resolve ambiguous references without environment visibility, and no reduction in unauthorized actions relative to blind review.
