# Mobile AI Factory: Building Specialized Language Models for Your Mobile Device

**Source**: [arXiv:2611.13509](https://arxiv.org/abs/2611.13509) · **Published**: 2026-11-10
**Authors**: Evan Li, Krishna Deshpande, Wen Cheng, Shyamnath Gollakota

## Overview

Small language models running on phones offer two things servers cannot: user data stays on the device and the app works without connectivity. Modern SoCs and inference engines like llama.cpp and MNN make quantized SLMs practical on hardware. But an SLM performs well only when fine-tuned for the target task and sized for the target device — a coupling that today demands repeated expert tuning across base models, quantizations, training data, and runtime configurations. The paper poses the question directly: given a task specification and a target phone, can we automatically produce a fine-tuned, quantized SLM that meets both the task's accuracy goal and the phone's resource budget?

Mobile AI Factory's answer is an agentic loop that curates training data, fine-tunes and evaluates a model, then decides what to try next. An orchestrator LLM chooses exactly one intervention per iteration — tuning hyperparameters (LoRA rank, scaling, learning rate, weight decay, epochs), mining more real data from the task's sources, or having a teacher model generate synthetic examples aimed at the failure categories that hurt accuracy most. Fixed rules handle what LLM judgment should not: any change that lowers accuracy is rolled back to the best model so far, budgets are enforced, and model scaling follows a bucketed small-to-large schedule. Three support components surround the loop: a teacher that generates synthetic data, a held-out-data agent that prepares the held-out set before training and shares only aggregate results with the orchestrator (a contamination check removes rows appearing in the test set), and a phone profiler that benchmarks every combination of base model, quantization, runtime (llama.cpp or MNN), and backend (CPU or GPU) once per phone.

The design reflects four ways the phone breaks server-side assumptions. Searches maximizing accuracy favor the largest model, so the factory treats base model and quantization as one choice and searches from small to large, moving up only when the current bucket stops improving. A model evaluated at full precision may not run at all on the phone — MNN's default 4-bit export loses up to 0.19 accuracy on the same weights — so every model is scored after quantization. The same model can meet an app's limits on one phone and fail on another, so search and deployment decisions come from measured profiles. And because tasks differ widely in difficulty, the accuracy goal is set from the teacher model's five-shot score (floor 0.8) and raised when reached too easily.

## Key points

- First agentic system (to the authors' knowledge) that builds a fine-tuned, quantized SLM for a given task and a given phone, rather than optimizing accuracy on a single chosen model.
- Search space: nine base models from 135M to 4B parameters (SmolLM2, Gemma 3, Qwen3, Qwen3.5 families) at 4-, 8-, and 16-bit precision — 27 combinations grouped into five buckets by on-disk size (boundaries 300 MB, 750 MB, 1.5 GB, 2.5 GB), searched smallest bucket first.
- Phone profiling: 364 configurations (104 per phone with a GPU, 52 on the Redmi 9A, whose GPU lacks OpenCL and runs CPU-only) across four Android phones spanning five years — OnePlus 15 (Snapdragon 8 Elite Gen 5, 16 GB), Galaxy S23 (8 Gen 2, 8 GB), OnePlus 8 Pro (865, 12 GB), Redmi 9A (Helio G25, 4 GB); the 16-bit Qwen3.5-4B exceeds the RAM of two of the four phones.
- Accuracy on unseen test sets: the factory's on-device models outperform both Claude Sonnet 5 and DeepSeek v4 Flash given five examples on five of ten tasks, by 0.024 to 0.342, and match them on three more.
- Gains concentrate where output format is strict: on biomedical entity extraction a 517 MB model scores 0.828 against Claude's 0.652 with five examples.
- Search efficiency: on an entity extraction task the factory's result comes within 0.03 of exhaustively training all 27 model variants while using 19x less GPU time.
- The phone in the loop changes the answer: the best configuration differs across phones, models, and quantization levels; on a Galaxy S23 whose limits rule out the factory's best model for call summaries, it returns a model within 0.013 of that best.
- Measurements cannot be replaced by reasoning: given every hardware and model specification but no real measurements, Claude Opus 5.5 with high reasoning effort misses the app's requirements in 25% of easy and moderate cases and 60% of hard ones — it misjudges runtime memory and the backend.
- Implementation: Claude Sonnet 5 as orchestrator; each run uses two NVIDIA L40S GPUs, one training/scoring the candidate and one hosting the local teacher (Qwen3.6-35B-A3B) that generates synthetic data; adaptive goal = teacher's five-shot score with a 0.8 floor, raised when met too easily.
- Ten evaluation tasks: biomedical entity extraction, fine-grained entity extraction, calendar event extraction, function calling, command parsing, 151-way intent classification, spam detection, emotion detection, grammatical error correction, and dialogue summarization.

## Details

### The intervention loop and rollback discipline

Each training attempt is modeled as a pipeline of dataset, hyperparameters, and learning strategy. The orchestrator commits to one intervention per iteration, the factory trains and evaluates, and the result is compared on the held-out set the data agent prepared. Because most interventions do not help, the rollback rule is the loop's spine: any change that lowers accuracy returns the system to the best model so far before the orchestrator tries something different. The held-out-data agent's boundary matters for trust — the orchestrator sees only aggregate scores, so it cannot overfit to individual test rows, and the contamination check drops any training row that also appears in the held-out test set.

### Why quantization is part of the search, not a post-step

The paper scores every candidate after quantization because the deployment format changes the answer: a 2B model at 4 bits is smaller on disk than a 16-bit 0.8B model, and MNN's default 4-bit export can cost up to 0.19 accuracy on identical weights. Bucketing by on-disk size makes these trade-offs commensurable and gives the small-to-large schedule its ordering. The profiler's measurements then decide not only which models may run — the Redmi 9A cannot use its GPU at all, and two phones cannot hold the 16-bit 4B model — but how the final model runs, since the best runtime and backend differ across phones, models, and quantization levels.

### What the adversarial measurement study shows

The most pointed result is the study that withholds the profiler. A frontier model (Claude Opus 5.5) given complete hardware and model specifications but no measurements — with high reasoning effort enabled — still violates the app's requirements a quarter of the time on easy and moderate cases and 60% on hard ones, failing specifically on runtime memory and backend choice. The failure mode is structural rather than a prompting artifact: runtime behavior on heterogeneous mobile hardware is determined by measurement, not inference from spec sheets. This is the paper's argument for keeping real phones in the loop rather than estimating latency with predictors or lookup tables.

### Scope and provenance

The evaluation covers ten tasks of varying output strictness, four phones spanning flagship to budget hardware, 27 model variants at three precisions, and two runtimes with two backends each, implemented with Claude Sonnet 5 as orchestrator and a local Qwen3.6-35B-A3B teacher on paired L40S GPUs. The authors position the system as a factory — a repeatable pipeline from task specification to deployed on-device model — rather than a one-off model release.
