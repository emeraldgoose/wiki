# WHALE: A Simple Recipe for Joint Harness–Weight Optimization

Source: Haechan Kim, Yoonho Lee, Gisang Lee, Chelsea Finn, Kangwook Lee (KRAFTON / KAIST / Stanford), arXiv:2609.00196, Aug 31, 2026.

**Lead**: Agent performance depends **jointly** on model parameters and the executable harness code that manages context and control flow. Optimising either alone leaves the system bottlenecked by its frozen counterpart: weight updates change *which* harness is effective, harness updates change *which* model capabilities are exposed. Existing joint-adaptation methods optimise weights and textual prompts but leave the broader harness fixed. WHALE (**W**eight-**H**arness **A**lternating **LE**arning) is a simple recipe alternating two phases — update the model under the current harness, then search for a better harness under the updated model — instantiating them with online rejection-sampling fine-tuning and Meta-Harness. Across Qwen3.5-2B/4B agents on search QA, math and chess, it beats weight-only, harness-only and Fast–Slow Training by **4.15–24.38 points** of mean@8 accuracy, while small interleaved updates also beat stagewise weight-then-harness on **both** accuracy and rollout cost.

## The two halves

The framing the paper insists on: **model weights are only half of an agentic system.** The other half is the harness — the code deciding which observations enter context, how tools are exposed and invoked, how execution errors are handled, and when an interaction terminates.

The coupling is the problem. Consider a QA agent with a retrieval tool:

- Stronger weights cannot use evidence a **brittle harness never retrieves**
- Better retrieval cannot help a model that **cannot synthesise** the returned evidence

So each optimisation is partly wasted on the other. A weight update that unlocks a new capability is worthless if the harness never exercises it; a harness improvement is worthless if the model cannot use what it retrieves. Prior work jointly adapts weights and context, but restricts "context" to **textual prompts** — leaving the executable harness, which is the larger and more consequential target for tool-using agents, fixed.

## Why alternation, not concurrency

Coordinating the two is awkward because the phases run on different timescales: harness search is a long proposal-and-accept cycle conditioned on many rollouts, while online fine-tuning alternates rollout collection with gradient updates.

Running them **concurrently** has a real cost: every update gets evaluated against a **moving counterpart**, which confounds credit assignment — you cannot tell whether a gain came from the weight change or from the harness having drifted. Synchronisation barriers are the alternative, and they are wasteful given mismatched update cadences.

**Alternation sidesteps both** by decomposing the coupled problem into **conditional updates**, each performed against a *fixed* counterpart. Each phase answers: given this harness, what do the weights want to be? Given these weights, what harness do we want?

## The scheduling question

Once you alternate, the obvious design question is: **when do you switch?**

The constraint is two-sided. Each phase must gather enough evidence to distinguish real improvement from noise — but must stop before it over-optimises against a fixed counterpart. WHALE offers both answers:

- **Fixed phase durations** — hyperparameters shared across cycles
- **Adaptive patience** — switch after a minimum duration once the current phase's training signal stops improving

## Results

Qwen3.5-2B and 4B agents across three domains: search question answering, mathematical reasoning, and chess puzzles.

| Comparison | Outcome |
|---|---|
| vs weight-only, harness-only, Fast–Slow | **+4.15 – 24.38 pp** mean@8 |
| Small interleaved vs stagewise weight-then-harness | better on **accuracy and rollout cost** |

The second row is the practically important one. The obvious pipeline — tune weights, then tune the harness — is dominated by simply interleaving small updates.

## The bottleneck is not fixed

A finding worth separating out: **either component can be the bottleneck, and which one depends on the task.** Harness search alone matches peak weight-only accuracy on SearchQA with far fewer rollouts — retrieval is the constraint there. But in math, harness search improves accuracy **only after** a weight update. Same recipe, opposite diagnosis, opposite ordering.

That is a direct argument against fixed pipelines: the right phase to run first is task-dependent, and WHALE's alternation discovers it rather than assuming it.

## Relevance to SW engineers

- If you are tuning an agent, ask which half is actually bottlenecked before choosing what to optimise. WHALE shows the answer is task-dependent — harness-first wins on retrieval, weight-first on maths.
- Joint optimisation of interdependent components is a credit-assignment problem. Alternating against a fixed counterpart is a clean way to avoid evaluating every update against a moving target.
- Alternating beats staging even when each phase is short. Interleaving small updates wins on accuracy *and* cost.
- Your harness — context selection, tool exposure, error handling, termination — is a first-class optimisation target, not plumbing. Existing joint-adaptation work largely leaves it fixed.
