# Invariant-Aware Harness Enforcement to Protect LLM Agents from Silent API Failures

**Source**: [huggingface](https://arxiv.org/abs/2611.20595)
**Date**: 2026-11-19

## Overview

LLM agents increasingly do their work through tools: they search literature databases, look up genes and proteins, query sample catalogs, and book travel by calling APIs, then build their answers from what those APIs return. Most broken tool calls are easy to spot because the API errors out, times out, or returns malformed data. Some failures leave no such trace. An API can ignore part of a request — for example a misnamed filter — yet still return HTTP 200 with a well-formed, plausible, but wrong result. The authors call this a silent API failure and its cause a silent fault.

Existing defenses put the model in charge: checklist prompts, reviewer models, outcome monitors, and LLM judges all ask the agent (or another model) to catch the problem. The authors show this mostly does not work — models often see the inconsistency and answer anyway. Their system, SilentGuard, moves the decision from the model to the harness that runs the tool calls. It tests each result against invariants that any correct API must satisfy, and withholds values that break one.

The reported findings are striking: silent failures appear in 11 of 15 public research APIs, with returned counts inflated by up to 691 times. Across 7 open models, SilentGuard cuts wrong answers on its target faults from 74.0% to 1.7% with no loss on fault-free tasks; on three frontier models, wrong answers fall from 70.2% to 0.5%. Notably, merely warning the agent about a suspicious result leaves 70.1% of answers wrong, so enforcement — not advice — is the key ingredient.

## Key points

- Silent API failures are common and invisible: 11 of 15 public research APIs silently ignored a misnamed filter, dropped a filter value with a typo, or quietly truncated a page, while still returning HTTP 200.
- Returned counts can be inflated by up to 691 times under these faults; agents often report these wrong counts, and a judge flags 77.4% of them.
- Model-in-the-loop fixes (checklist prompts, reviewer models, outcome monitors, LLM judges) leave over 70% of answers wrong — close to an unguarded agent's 74.0% baseline.
- SilentGuard runs checks in the harness, not the model: exact checks (e.g. a count identity evaluated at every filter position, per-record filter conformance, no duplicate records, list size matching the reported total, spec/parameter checks) plus learned checks mined from clean traces.
- Each check carries an estimated false-alarm rate (rule of succession, 1/(n+2); exact checks get rate 0). After one re-check, results are released, withheld (failed check with alarm rate ≤ 1%), or passed through with a warning.
- On new, unseen fault types, the harness alone cuts wrong answers from 61.1% to 24.5%; it avoids wrong answers mainly by abstaining rather than by recovering.
- A warning from the same check leaves 70.1% of answers wrong — enforcement, not notification, drives the improvement.

## Details

**Method.** SilentGuard separates detection from action. For count queries it issues two extra queries itself to verify the identity N(F) + N(F_{<k} ∧ ¬C_k) = N(F_{<k}) at every position of the condition list, so an ignored filter anywhere in the list is caught. For list-returning endpoints it checks that every returned record satisfies the filter, that no record repeats, and that the list size matches the reported total. When an API publishes its parameter list, requests with unknown parameters are rejected before they run. Learned checks, mined from clean traces as in prior work, cover field presence and type, echoed arguments, positive values, categorical values, linear relations between fields, and date order.

Detection and action are split: each check maps a result to pass/fail with an estimated false-alarm rate α̂ = 1/(n+2) where n is the number of clean examples it held on (exact checks have n = ∞). After one re-check, the harness releases results that pass all checks, withholds a result when a failed check's alarm rate is at most the cutoff τ = 1%, and warns otherwise. New checks can plug into this policy without changing it. Of 84 documented operations in 13 public APIs, 61 allow an exact check and all allow the spec check.

**Results.** In the authors' evaluation, silent failures were found in 11 of 15 public research APIs. Current model-in-the-loop fixes leave over 70% of answers wrong, and agents report 77.4% of the counts a judge flags. A judge shown the consistency-check evidence flags 82.4% of faulted runs (and 13.9% of clean runs), confirming the problem is visible but the model answers anyway. Across 7 open models, SilentGuard cuts wrong answers on its target faults from 74.0% to 1.7% with no loss on fault-free tasks. On three frontier models, wrong answers fall from 70.2% to 0.5%. A warning from the same check leaves 70.1% wrong. On new fault types not covered by the checks, the harness alone cuts wrong answers from 61.1% to 24.5%. The system avoids wrong answers by abstaining rather than by recovering them.
