# GH-AWTrace: A Large-Scale Dataset of GitHub Agentic Workflow Execution Logs

**Source**: [arXiv:2611.06866](https://arxiv.org/abs/2611.06866) · **Published**: 2026-11-04
**Authors**: Jasem Khelifi, Hao Li, Ali Ouni, Mohammed Sayagh, Mohamed Aymen Saied

## Overview

GitHub Agentic Workflows (gh-aw) let AI agents perform recurring repository tasks on schedules or in response to repository events. Existing studies of such workflows examine their definitions and outputs — how developers write and maintain the Markdown/YAML specifications, what the runs produce — but provide little evidence of what actually happens during execution. Workflow definitions describe intended behavior, and run-level outcomes summarize execution without explaining the intervening actions. The execution logs, which record tool interactions, access restrictions, infrastructure failures, and recovery attempts, are exactly the evidence that could close this gap — and GitHub's retention policies delete them: run records after 400 days, public workflow execution logs after at most 90 days.

GH-AWTrace is a preservation-and-linking effort that captures this perishable evidence at scale. The dataset links 25,014 verified gh-aw workflows across 5,051 repositories to 4,112,526 run records and 562,877 nonempty execution log archives (56.1 GB of ZIP archives downloaded within the 90-day retention window), together with repository metadata and the generated workflow configurations. Verification was deliberate: of 25,227 candidate files in 5,059 repositories found by search, each blob was accepted only when the generator phrase appeared in an opening YAML comment before any configuration key, and 63 files lacking the required header plus 150 unretrievable blobs were dropped.

The paper is candid about what the logs are not: partial observations rather than complete agent trajectories. Coverage varies across workflows (the 6,040 workflows with logs have a median of 16 log archives each, IQR 6–60), 821,672 of the selected runs have no downloaded archive, and 1,070,338 downloaded ZIPs are empty — an early audit of 2,900 such empties found 2,699 showing only skipped jobs and 195 listing no jobs at all. Even so, the illustrative cases show the data exposing phenomena invisible in definitions or run conclusions: tool denials that change an agent's behavior mid-run, provider authentication failures with retries, and within-run delegation among background agents.

## Key points

- Scale: 25,014 verified gh-aw workflows in 5,051 repositories, linked to 4,112,526 run records (August 14, 2025 – September 21, 2026, bounded by the 400-day run-retention policy) and 562,877 nonempty execution log archives from 561,367 runs.
- Log preservation window: because GitHub deletes public workflow execution logs after at most 90 days, the collection targeted the 2,453,263 run records created June 23 – September 21, 2026 and downloaded 1,633,215 ZIP archives (56.1 GB), each with recorded SHA-256 hash and file list.
- Pipeline attrition is documented end to end: 25,227 candidates → 25,014 verified workflows; 11,396 workflows with recorded runs vs 13,618 without; 1,659,263 run records outside the 90-day window; 821,672 runs without a downloaded archive (retention, deletion, access restrictions, or unfinished runs); 1,070,338 empty ZIPs vs 562,877 archives containing log files; 18,337 archives from rerun attempts after the first.
- Failure surface: 178,151 (31.7%) of nonempty log archives link to run records with a failure conclusion — a rate the paper explicitly declines to attribute entirely to agents, illustrating a blocked task and a provider authentication failure (HTTP 403, one retry after partial execution) as distinct causes.
- Agent behavior under restriction: logged cases show an agent changing its publishing command after a tool denial, and another inspecting a dependency update before posting a review verdict — evidence of adaptation after denial that run conclusions do not reveal.
- Within-run coordination: a review run dispatched three background reviewers and used agreement between two respondents to select findings, demonstrating delegation and synthesis inside a single run, while providing no evidence of memory shared across runs.
- What logs contain: a prompt-file path and size, visible agent messages, tool calls, and responses — not full prompt text or private reasoning, so traces should not be treated as complete prompts.
- Research directions the data enables: failure taxonomies for agentic workflows, recovery behavior after tool denials, and the agreement between reported run conclusions and visible task progress; the dataset (linked tables, archives, schema, access instructions) is public on Hugging Face with a Python example that reproduces the 31.7% figure.

## Details

### Three-phase collection design

Phase A discovers and verifies workflows: GitHub code search finds candidate files, and verification requires the gh-aw generator phrase as an opening YAML comment preceding any configuration key, with each accepted blob fetched at the exact revision returned by search. Phase B collects runs through the GitHub REST API by workflow ID, saving all returned fields, and links each run to the YAML revision indexed during discovery by repository ID and exact path — noting that a run's actual workflow revision may differ, which is why head_sha is retained. Phase C downloads log archives within the 90-day window, identifies each archive by run ID and attempt number (reruns keep the run ID and get new attempt numbers), and stores integrity metadata. The three phases are connected through explicit keys (repo_id, workflow path, run_id, attempt), making the dataset relational rather than a flat log dump.

### Reading the coverage gaps

The dataset's own statistics are a lesson in preservation under policy constraints. Of 4,112,526 run records, only the 2,453,263 inside the 90-day log window could ever have downloadable logs; of the 1,633,215 ZIPs downloaded, two-thirds are empty or absent for reasons the authors cannot always determine — GitHub's audit shows skipped jobs dominate. Analyses must therefore distinguish workflow runs from execution attempts, reported outcomes from observed task completion, and agent behavior from infrastructure failures. The authors position GH-AWTrace as preserved evidence supporting these questions, with broader claims requiring systematic sampling and validation.

### Provenance and scope

This document is written from arXiv HTML v1 (submitted 2026-11-04). The dataset is released at huggingface.co/datasets/jaykay9999/GHAWTrace with linked data tables, the nonempty log archives, schema, and access instructions, and a companion video walkthrough. As with any observability dataset, its value decays: every statistic in the paper is a snapshot taken against retention clocks that keep deleting the underlying evidence.
