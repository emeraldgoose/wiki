# MORSE: Optimizing Streaming Memory Design via Open-World Auto-Research

**Source**: [arXiv:2611.30011](https://arxiv.org/abs/2611.30011) · **Published**: 2026-11-23 (v1)
**Authors**: Ce Zhang, Jianshu Zhang, Jinxi He, Xiyuan Yang, Pan Wang, Han Liu, Katia Sycara, Yaqi Xie

## Overview

A streaming video system answers questions about an ongoing stream in a single pass, keeping only a bounded frame store — so it must decide what evidence to keep before knowing what future questions will ask. The "streaming harness" (write policy that selects and organizes retained evidence + read policy that retrieves it for the VLM) has traditionally been researcher-designed, and recursive self-improvement methods automate only revisions the editor can devise from prior knowledge and a predefined tool set. MORSE (Memory Optimization with Recursive Self-Evolvement) closes this gap with open-world auto-research: when failures recur across training videos, an LLM-based Editor searches papers, model pages, and code online for solutions it can adapt, and can request pretrained perception models (host-reviewed for provenance; benchmark data and QA annotations are blocked by a broker to prevent leakage).

The framework has two roles. A streaming Solver runs the harness around a frozen answering VLM; the Editor inspects training traces, groups failures by cause, and each round runs a four-step loop: Diagnose (failure groups from traces, distinguishing missing memory from failed retrieval/perception), Research (external collection W within budget B_res), Propose (up to B executable candidates plus tool requests; approved tools join the tool set T), Validate (host scores candidates on private validation streams; the Editor sees only aggregate scores, never validation questions or item-level feedback).

Selection uses two gated stages on held-out streams: K_acc accuracy rounds that accept a candidate only if the mean correct-option probability P̄ rises by at least δ, then K_eff efficiency rounds that accept only if latency drops to at most a fraction ρ of the parent while quality losses stay within per-update bounds ε, κ (and totals ε_tot, κ_tot against the stage-entry harness). Accuracy selection maximizes P̄ (ties favor lower latency); efficiency selection minimizes latency ℓ (ties favor higher P̄); passing candidates that share a parent can be merged and revalidated, and accuracy rounds also pool archived qualified-but-unselected candidates.

## Key points

- Highest answer accuracy within each frozen backbone on all three streaming benchmarks. OVO-Bench (1,468 questions, real-time + backward-tracing): Qwen3-VL-8B + MORSE 75.1% overall (RT 82.4 / BT 65.3) vs MemEvo 72.0, StreamScout 69.7, OASIS 69.2, FluxMem 61.6, bare backbone 60.1; Qwen2.5-VL-7B + MORSE 69.9 (vs 64.4 MemEvo); Qwen3.8-27B + MORSE 79.4 (vs 71.1 MemEvo, 75.8 FluxMem). StreamingBench question-weighted avg with Qwen2.5-VL-7B reaches 75.8 (MemEvo 71.9, StreamScout 71.3).
- Fast: on OVO-Bench the Qwen3-VL-8B harness answers in 0.30 s on average — 6.0x faster than MemEvo, 3.5x faster than OASIS, 1.6x faster than answering from sampled frames directly. After accuracy rounds the harness needs 0.82 s per answer; efficiency rounds move reusable computation into memory construction (write cost 0.87→1.19 s per 8 s of video, still 33% below MemEvo because VLM calls drop 1.49→0.77 s) and cut answer latency to 0.30 s (2.7x faster than the post-accuracy harness).
- Component ablation on OVO-Bench (25 rounds from the same seed, seed overall 67.4%): without online research 72.9% (+5.5), without tool requests 70.6% (+3.2), full MORSE 75.1% (+7.7) — both open-world components contribute, research more than tools.
- Setup: videos sampled at 1 fps, persistent store capped at 64 frames plus a 16-second recent window; each VLM call uses at most 32 frames / 256 visual tokens per frame; seed harness answers from 16-second VLM captions plus the 4 most recent frames; initial perception tools are CLIP ViT-L/14 and OCR; Editor is Claude Opus 5.5 in a fresh sandboxed Claude Code session per round.
- Data hygiene: Editor diagnoses on 780 training questions / 370 streams (NExT-GQA, STAR, ReXTime, COIN, YouCook2, OVBench-COIN); candidate selection on a disjoint 388-question / 182-stream validation set with only aggregate scores exposed; test benchmarks (OVO-Bench, StreamingBench, StreamBench) never used in development; broker blocks benchmark repos, dataset pages, and QA annotations; models trained or fine-tuned on evaluation videos are excluded; only non-generative tool additions are admitted.

## Details

P̄(H) is the mean over validation questions of the correct-option probability renormalized over valid option letters at the answer position — unlike hard accuracy c/N it detects gains before predictions flip. Gates: accuracy g_acc requires ΔP̄ ≥ δ; efficiency g_eff requires ℓ' ≤ ρℓ(H), ΔP̄ ≥ −ε, Δc ≥ −κ; both also require ℓ' ≤ L, ω' ≤ 1, and completion of all validation streams with unchanged question counts. Test protocol: question-weighted multiple-choice accuracy on OVO-Bench and StreamingBench, official LLM-judged free-form protocol on StreamBench; every query sees only observations available at its timestamp. Answering models are served by vLLM with greedy decoding.
