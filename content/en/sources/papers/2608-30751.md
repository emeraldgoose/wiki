# Autoregressive Mosaics: Probing 2D Spatial Reasoning in Text-Only Language Models

Source: Ashwin Nedungadi, Stefan Oehmcke, Stefan Lüdtke (Institute for Visual & Analytic Computing, University of Rostock), arXiv:2608.30751v2, Sep 1, 2026.

**Lead**: Text-and-code-only LLMs can sometimes generate programs that draw recognisable images — but is that an internal representation of 2D spatial layout, or just the ability to **translate spatial descriptions into code**? AM-Bench separates the two with two complementary tasks: a **translation task** that hands the model a fully specified geometry and asks for the code, and a **layout task** that requires composing an image from an underspecified prompt. Across **eight open-weight text-and-code-only models**, all reliably translate specified geometry into code, but **open-ended layout performance differs substantially** — so the differences are not explained by code-generation ability. An output-medium ablation adds a third finding: **replacing procedural code with raw SVG improves layout scores across all models**. Probing activations shows a coarse plan exists before generation but reflects only the prompt's layout, and during generation models **track the evolving geometric state** rather than executing a fixed plan.

## The ambiguity worth separating

The motivating observation is familiar: ask GPT-4 for a unicorn in TikZ and you get something recognisable, from a model that has never seen an image. Explanations abound, and they are not the same claim.

An LLM-generated image alone cannot tell you whether a poor layout results from:

- failing to **compose** the spatial arrangement,
- being unable to **express** a suitable layout in the required language, or
- the **output medium** itself constraining what can be expressed

Existing evaluations entangle these. Recognition benchmarks need visual input, so they miss text-only models entirely. Generative evaluations score only the final output, never separating spatial composition from description-to-code translation. The paper's contribution is a benchmark where those factors come apart.

## Design: two tasks, one control

AM-Bench represents an image as an **autoregressive mosaic** — a small raster produced by a program and rendered by a deterministic executor. The pipeline is four stages: prompt → internal plan → program code → rasterised geometry.

| Task | Prompt | Measures |
|---|---|---|
| **Translation** | Complete geometry stated in words | Code-generation ability (the control) |
| **Layout** | Underspecified | Additional challenge of composing the arrangement |

Translation is the control that makes layout interpretable. Because both use the same model and the same output format, a layout gap cannot be code-generation ability — it has to be spatial composition.

Scoring differs by task, necessarily. Translation uses an **exact-area geometric metric in continuous coordinates**, so the score does not depend on canvas resolution. Layout has no reference geometry, so it is scored by **vision language models**, validated by human scorers who provide supporting evidence for the judge's ranking signal.

## Findings

**Translation is solved; layout is not.** Every model reliably turns specified geometry into code. Open-ended layout performance varies a great deal between them. This is the paper's central empirical claim: layout ability is not a proxy for coding ability.

**The output medium matters, and it matters for everyone.** Replacing procedural code with **raw SVG improves layout scores across all models**. So part of what looked like spatial reasoning was an artefact of the expression format — the same underlying capability, expressed in a medium that fits it better.

**The internal plan is not what you would hope.** Probing model activations shows a coarse layout plan present *before* generation — but it reflects **only the layout implied by the prompt**. And during generation, models **track the evolving geometric state** rather than executing an initially fixed plan.

That last result is the interesting one. There is no clean "layout-then-render" pipeline internally; the model is doing something more incremental. The pre-generation plan is not a blueprint the model then follows.

## Scope

The authors are careful about what the benchmark measures: **allocentric 2D layout at mosaic granularity**. It is a **necessary-condition probe** for embodied spatial competence, not a sufficient one, and it does not cover metric egocentric continuity, depth, or occlusion. The activation-level claims are behavioural; the authors flag direct causal analysis via activation patching as future work.

## Relevance to SW engineers

- If you evaluate a model's drawing or diagram output, you are measuring the output medium as much as the reasoning. The SVG-vs-code gap here is a warning about your own evals.
- Build a control into the benchmark. Translation is what makes the layout number mean "spatial composition" rather than "can code".
- Score in continuous coordinates where you can, so your metric does not silently depend on raster resolution.
- VLM-as-judge needs human validation behind it. The paper does this and says so; many papers do not.
- "There is a plan before generation" is not the same as "the model executes a plan". Probe the trajectory, not just the state at t=0.
