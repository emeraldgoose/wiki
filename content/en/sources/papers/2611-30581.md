# A Pipeline-Parallel System for Depth-Recurrent Models

**Source**: [arXiv:2611.30581](https://arxiv.org/abs/2611.30581) · **Published**: 2026-11-23 (v1)
**Authors**: Yunjia Xi, Jiarui Qin, Di Yin, Xing Sun

## Overview

Depth-recurrent (looped) models raise effective depth by applying a shared stack of blocks several times, but scaling them needs pipeline parallelism (PP), and conventional PP schedules assume an acyclic stage graph. Megatron's interleaved 1F1B is drawn for that acyclic case: each micro-batch enters each stage once. Once the shared stack is split across stages, the same stage is visited several times by one micro-batch and later stages feed earlier ones, so native 1F1B has no slot for the extra visit, cannot order a first iteration against a second, and its neighbour-only send/receive order has no back edge to the first stage — the arrangement stalls or fires out of order. Inserting an independent local loop per stage is also insufficient: that computes stage-local repetition (F_P-1^T ∘ ... ∘ F_0^T) instead of the required T end-to-end recurrent steps ((F_P-1 ∘ ... ∘ F_0)^T).

Loop-PP rebuilds both the timetable and the communication for this cyclic layout. Given the recurrent model structure, the number of micro-batches M, and the PP/VPP placement, a three-stage compiler produces static per-rank action streams: (1) Semantic Graph Construction builds a dataflow graph whose nodes record micro-batch, recurrent step, compute role, stage, and VPP placement, with prelude/coda visited once per micro-batch and the recurrent region contributing new logical nodes at every step; (2) Native-Guided Schedule Synthesis uses native interleaved 1F1B as a compute template and constrains it with the semantic dependencies to produce a Global Compute Order that schedules different iterations of the same stage separately; (3) Communication-Aware Stream Compilation expands the order and a communication plan into a cross-stage action DAG of compute, nonblocking POST, WAIT, and EnsureBatch actions, then linearizes it into deterministic per-rank streams that separate posting from waiting so communication overlaps local compute.

## Key points

- Correctness: on an 8B MoE model with T = 2, Loop-PP at PP2 matches a PP1 recurrent oracle bit-exactly in language-model and auxiliary loss over five steps; after 1,000 steps with T = 3 the losses differ by 5.43e-4 (1.813975 vs 1.814518) with no accumulating drift. Appendix B proves semantic-order preservation, communication-matching safety, and deadlock freedom of the compiled streams.
- Models and setup: three full-loop MoE models on Megatron-LM — 8B-A1B, 30B-A3B, 60B-A5B with 32, 48, 48 unique layers, executed for T = 2 steps (effective depths 64/96/96); 32 GPUs, sequence length 4096, global batch 512; throughput in tokens/s and peak GPU memory in GiB.
- Memory: Loop-PP uses less peak memory than the Unrolled and Tied baselines at every plotted point, saving up to 32.8%; at 60B PP2 the Unrolled, Tied, and Lockstep baselines run out of memory while Loop-PP completes.
- Throughput: at PP2 Loop-PP is 12.4% faster than Unrolled on 30B, but slower at PP8 (the "PP8 performance cliff"); relative to the conservative Lockstep baseline it is 1.9x faster at PP2 and more than 6x faster at PP8 on 30B.
- Equal-budget result: with model, batch size, and the 32-GPU budget fixed and each method free to choose PP/VPP/micro-batch size, Loop-PP's best throughput beats Unrolled by 1.110x on Dense 14B (96.6k vs 87.0k tok/s) and 1.127x on MoE 30B (170.7k vs 151.5k tok/s) — the headline +12.7% — using only slightly more peak memory at the optimal point, showing the memory saving converts into a faster operating point.
- PP8 cliff analysis: iteration time splits into local, exposed, and tail components; Loop-PP trades lower local/tail cost (parameter and runtime-object reuse) for higher exposed pipeline cost from recurrent cross-stage dependencies. At PP8, thinner chunks expose dependencies more often — 99.98% of measured PP8 receive-wait time is dependency-limited — and growing the chunk (VPP2 to VPP1, 3 to 6 unique layers) raises throughput from 64.7k to 71.3k tok/s. Loop-PP should avoid overly fine pipeline partitions.
- Workload sensitivity: on a Dense-FFN variant of the 30B model, Loop-PP is 7.2% faster at PP2 and 0.9% faster at PP4 and also shortens all-to-all event duration (4.195s to 3.451s at PP2; 4.498s to 3.779s at PP4), so the savings are not solely MoE load balancing; MoE benefits more. Recurrent structure matters: relative throughput weakens as T grows to 4 and varies non-monotonically with the recurrent fraction (50% and 100% beat 25% and 75%), so performance depends on how the recurrent region maps to stages, not on the fraction alone.
- Implementation optimizations: payload localization rewrites each payload schema to the fields remote consumers actually need, and compilation caching reuses the Global Compute Order, Communication Plan, and per-rank streams across training steps keyed by the semantic graph and configuration.

## Details

Baselines: Unrolled materializes the same effective depth with independent parameters under Megatron's interleaved 1F1B (optimistic native-schedule reference, no parameter sharing); Tied keeps the physical expansion but ties weights across recurrent visits and syncs gradients/replicas (preserves looped semantics at the cost of replicated parameters); Lockstep runs the same semantic graph with a conservative dependency-respecting 1F1B schedule that bounds live micro-batches (correctness-oriented reference). Under matched configuration, Tied is close to Unrolled but usually slightly slower due to the extra gradient/parameter synchronization. Affiliation: Tencent Youtu Lab.
