# JustRUA: A Controlled Study of GPT-6 Robot-Use Agents

**Source**: [arXiv:2611.16009](https://arxiv.org/abs/2611.16009) · **Published**: 11 November 2026
**Authors**: Zefan Wang, Yufan Dang, Xuanwei Shi, Mingqi Gao, Cheng Yin, SikYuen Tam, Hanyu Liu, Yasheng Wang, Yaxi Lu, Songyang Zhang, Xin Cong, Yuan Yao

## Overview

Frontier multimodal models can now control robots without any robot-specific training. GPT-6 Astra drives a bimanual arm through a harness, the software that turns each of its decisions into end-effector targets for a motion planner, with no vision-language-action model in between; by analogy with computer-use agents, such systems are called robot-use agents. Scores of GPT-6 Astra-based systems on the RoboDojo simulation benchmark have risen quickly, but each reported system starts from a different harness, runs on a different test subset, and often changes several designs at once, making it hard to tell which choices produce the gains.

JustRUA answers with a controlled study. Starting from L3 Inspect EEF, the official L3 harness behind GPT-6 Astra's RoboDojo entry, the authors group recent designs along four axes: the harness around the model, the action interface, the reuse of experience from other episodes, and the scene geometry in each observation. Designs are tested one at a time along a single path, so each alternative is compared with the configuration kept at that point, which is the question a system builder actually faces. The evaluation uses a fixed set of 111 episodes covering all 42 tasks, with the 23 highest-variance tasks run on four layouts each.

The result is a deliberately lean agent. Keeping the full episode history and stopping each motion after 20 control steps, feeding the model its own grip readings and RGB-predicted depth, and letting it run code that solves 3D coordinates from pixels raise the official harness's evaluation-set score from 29.7 to 50.3, with no learned policy, no self-improvement loop, and no task-specific tuning. The study's sharpest finding is negative: reusing experience changes how the model acts but never clearly beats the default, and scene geometry, not experience, is the axis that helps most.

## Key points

- The lean harness goes a long way: keeping the full episode history and capping each motion at 20 control steps (about 0.8 seconds) lifts the score from 29.7 to 38.0, against the official harness's 29.0 on its full 2,100-episode evaluation.
- Depth images cut empty grasps from 41 to 16 in the first round, even when Depth Pro predicts the depth from RGB alone and is off by tens of centimetres (raw mean absolute error 73.7 cm on the head camera).
- Code that solves 3D coordinates from pixels and camera calibration, plus removing the decision cap, brings the score to 50.3; in one insert_tubes layout, predicted depth scored 40 while coordinate solving scored 100 with fewer decisions.
- Almost every code run does geometry: 123 of 132 reviewed code runs (93.2%) triangulate or solve coordinates, and the code never reads the depth images.
- Relative targets score lower than absolute ones, with the arm striking objects almost three times as often, and named semantic operations changed behavior more than competence: the model moved its cameras over three times as often, dropped more objects, and the score did not rise.
- Allowing up to four moves per decision raised the score mostly on Long-horizon tasks, but the gain traces to the few episodes that ran out of the 100-decision budget, so the final configuration removes the budget instead.
- Experience reuse is rejected: demonstrations (16-keyframe visual and text-trajectory forms) and a self-written library of four operations (grasp, transport, place, push) changed behaviors such as handovers through the table, but neither clearly beat the default and both made episodes more expensive.
- Precomputed affordances, the most elaborate form of scene geometry tested, did not help; drawn affordance variants raised empty grasps to between 25 and 39 versus 16 to 17 with plain depth.
- One episode reads several million input tokens and writes only a few thousand, with nearly every input token already sent earlier in the episode, so cost is reported as a lower bound with all cacheable tokens billed at the cached-input price.
- With the final configuration, 21 of 42 first-round tasks score below 50, and most failures are task-specific long-tail cases: plans that do not suit the arm, unplanned knocks, and slipping grasps.

## Details

### Harness and action interface

The official L3 harness calls the model API directly, keeps images from only the last two observations, and ends episodes at the benchmark limit of 500 control steps; the model receives no depth, object poses, or scoring signal. JustRUA keeps the full history of observation text, notes, calls, and results in context (earlier images drop out), and executes at most the first 20 control steps of each planned motion. Reasoning effort matters too: medium effort scores highest overall, low effort gives up most of the Precision score, and high effort trades precision for memory.

### Reusing experience

Both demonstration forms are looked up by task name, and the model is told to follow the demonstration's order and geometry rather than copy its coordinates. In the make_kong case, both demonstration runs copied a handover through the table centre but neither copied the final upright-grip push, knocking the row over and scoring 0, so the demonstration fixed the plan and the episode failed somewhere else. The self-improvement loop, which wrote and refined its own skill library from RoboDawn demonstrations, carried the greatest risk of gaming the benchmark because experience is drawn from the tasks being scored; JustRUA keeps no form of experience reuse.

### Scene geometry

The axis breaks into four steps: compact robot readings of finger positions, forces, and wrist loads; depth images (simulator depth serves only as a reference, as the leaderboard does not accept it for agent entries); drawn affordances; and model-written code. The model's own grip readings, predicted depth, and a little coordinate-solving code go a long way without simulator ground truth, with code triangulating points seen by two cameras or meeting a known surface height.

### Evaluation and error analysis

The evaluation set was designed after eight rounds of the default testbed showed that most score swings come from high-uncertainty tasks, where a single near-miss moves a task by 50 points or more. The 111-episode set varies less than running every task three times with 126 episodes. Behaviour is reviewed separately from score: GPT-6.1 Sol, taking no part in running the robot, counts physical events from action logs and three camera videos, with only evidence-settled events counted, so reported counts are lower bounds.
