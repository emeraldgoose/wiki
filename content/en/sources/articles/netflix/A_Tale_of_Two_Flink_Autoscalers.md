# A Tale of Two Flink Autoscalers

Netflix runs Flink since 2017 — over 30,000 jobs across regions in 2026, mostly generated by the managed Data Mesh platform, plus custom stateful jobs (personalization, Ads, Live) with terabytes of state. Peak provisioning is wasteful, average provisioning lags during surges, and rescaling a large stateful job (savepoint, stop, restart) takes minutes. Two autoscalers exist today; the post explains why and how Netflix is converging on the open-source one.

## Background: the first (homegrown) autoscaler

Built ~2019 on Mantis, it consumed cluster-level Atlas telemetry (CPU, network, Kafka lag, input/consume rates) and combined lag-derived catch-up time, utilization thresholds, performance history, and input-rate regression to scale total TaskManager count. It cut resource usage 25–45% across thousands of managed pipelines. Ceilings: it reasoned about whole clusters through coarse container metrics with a single knob (every operator scaled together), fitting single-operator pipelines but not multi-operator stateful DAGs; and its external metrics could miss real trouble (a job fully busy without showing CPU; a networking migration silently broke metric coverage).

## Methodology: the second (open-source) autoscaler

The Apache Flink Autoscaler reasons from *inside* the job via each operator's true processing rate (TPR): observed throughput divided by busy fraction (e.g. 700 rec/s at 70% busy → TPR 1,000 rec/s). Walking the job graph from sources with TPRs, input/output ratios, and a target utilization, it computes per-vertex parallelism so no operator bottlenecks — scaling exactly the stateful multi-operator jobs the homegrown system could not, with per-job tunable configuration.

**Netflix-scale adaptation.** The OSS autoscaler was built for the Flink Kubernetes Operator, but Netflix runs its own control plane; the community's refactor into a standalone library (context, state store, event handler, realizer interfaces) allowed direct integration. A Spring Boot service orchestrated by Temporal polls the control plane ~1/minute and runs one durable per-job workflow (isolating blast radius vs the earlier fragile single batch loop). Three engineering gaps were closed: metric collection to 3,000 subtasks (JobManager metric-name caching, server-side filtering — partly upstreamed, e.g. FLINK-36172); forward-chaining preservation (forward-connected subgraphs scaled as a unit, else Flink silently converts the edge to a network shuffle); async-sink backpressure detection so jobs don't scale into a saturated sink. A realizer runs safety checks (no scale-down during region evacuation, checkpoint-disk verification, standby buffer).

## Results

- General availability for custom jobs; e.g. client telemetry/logging cut annualized Flink compute ~58% (~$1.1M/year) via adapting to daily cycles, continuous right-sizing, and uniform containers enabling finer-grained bin-packing.
- Deliberate stability trade: target utilization 0.45 (below the 0.7 community default) — fewer, calmer rescales for large stateful jobs.
- Remaining bottleneck is Flink core state restoration, not scaler logic; Flink 2.2's disaggregated state backend is next for evaluation.

## Limitations / open questions

- Scaling still means restart + state recovery for large stateful jobs; scaler quality is capped by recovery speed.
- Lower utilization target trades efficiency for stability — the optimal point per workload class is still empirical.
- Full migration of internal-scaler use cases is in progress, not complete.

## Relevance to SW engineers

- Metric choice matters more than algorithm sophistication: debug which signal to trust before tuning math.
- One good default covers platform-managed jobs; pair defaults with per-job overrides and hide expert knobs.
- Adopt-then-extend beats build-forever or rip-and-replace: adopt the community project for new workloads, contribute fixes upstream, migrate deliberately.
- Isolate per-tenant control loops (workflow-per-job) so one misbehaving job can't stall the fleet.
