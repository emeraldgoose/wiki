# From Silos to Insights - Federated Data Access Patterns for AI Agents

**Authors**: James Wu · **Published**: Sep 4, 2026 · **Source**: [AWS Big Data Blog](https://aws.amazon.com/blogs/big-data/from-silos-to-insights-federated-data-access-patterns-for-ai-agents/)

## Problem

Enterprise data is fragmented across systems with incompatible access models: batch data on Amazon S3 needs engines like Athena or Trino, real-time telemetry on Amazon Kinesis needs streaming expertise, OLTP/CRM records need SQL against a relational database, and each SaaS app has its own API and auth model. Only a few data engineers can navigate this, so every one-off cross-system question ("which titles drove subscriber growth last quarter?", "does marketing spend correlate with completion rates?", "is churn spiking among users who ignore new content?") lands in a ticket queue. Traditional fixes — central data lakes or a full data mesh — demand heavy engineering investment and ongoing maintenance, and dashboards only answer yesterday's questions.

## Solution: federated access via MCP + Bedrock AgentCore

Instead of moving all data to one place, let AI agents talk directly to the systems where data lives. The Model Context Protocol (MCP) standardizes tool discovery, invocation, and response handling, so a Strands agent fronted by natural language can reach the right store without the user knowing the API, auth model, or query language.

Reference architecture (streaming-media example, synthetic data, code at `aws-samples/sample-aws-semantic-data-access-ai-agents`):

- **Generative AI layer** — Strands agent on **Amazon Bedrock AgentCore Runtime** (LLM: Claude Haiku 4.5 via Bedrock), with an intent-based system prompt + mandatory schema-discovery workflow. **AgentCore Gateway** aggregates all MCP servers behind one endpoint (tool discovery incl. semantic search, auth, routing).
- **Compute/MCP layer** — three MCP servers, each on AgentCore Runtime behind the Gateway: (1) **Data Processing MCP server** wrapping Glue Data Catalog metadata + Athena query execution (`manage_aws_glue_tables` tool); (2) **Aurora MCP server** translating tool calls into SQL via the RDS Data API against Aurora MySQL, auth via Secrets Manager, exposing just `run_query` + `get_table_schema`; (3) **AWS Documentation MCP server** for service context.
- **Data/governance layer** — batch datasets (customer profiles, content titles, ad campaigns) generated by **Lambda on an EventBridge schedule** as Parquet on S3; streaming telemetry (watch/pause/drop-off events) via **Kinesis Data Streams → Data Firehose → S3**; CRM records (plans, support tickets, account status) in **Aurora MySQL**. **Glue Data Catalog** unifies S3 metadata (schemas, business context, quality, lineage); **Lake Formation** enforces fine-grained access. Frontend: React app on **S3 + CloudFront**, auth via **Cognito** (identity token travels with the request).
- **Three patterns** on a governance↔flexibility spectrum: **Pattern 1 catalog-first** (governed S3 via Glue + Athena), **Pattern 2 direct source access** (Aurora via dedicated MCP server, no catalog), **Pattern 3 hybrid** (both behind one orchestrator — the recommended real-world shape).

## Implementation

1. **Prerequisites**: AWS account with Bedrock AgentCore access (see AgentCore Runtime permissions docs), AWS CLI configured, Python 3.10+, Docker or Finch. Deploy per the sample repo README (data CDK stack, then agent stack; destroy agent-first on cleanup, plus orphaned Kinesis streams/CloudWatch log groups).
2. **Pattern 1 — catalog-first (example: "how many streaming events in Feb 2026 by type?")**: (a) routing rules match "streaming events" to the Glue/Athena path (Gateway semantic search as fallback); (b) agent calls `manage_aws_glue_tables` to fetch schema, types, partition keys (`year, month, day, hour`), storage format; (c) agent writes Presto/Trino SQL with partition filters (`WHERE year='2026' AND month='02'`) and runs it via Athena; (d) new tables/columns appear live via the catalog with no routing-logic changes. Trade-off (shared with e.g. Databricks Unity Catalog MCP servers): everything must be cataloged first, which can bottleneck fast-changing environments.
3. **Pattern 2 — direct access (example: "open critical support tickets by category")**: agent matches "support tickets" to the MySQL path and calls `run_query` with `SELECT ... WHERE status='open' AND priority='critical'`; the MCP server executes against Aurora via the RDS Data API and returns through the Gateway. System prompt carries only lightweight hints (table names, key enum values); for joins/unfamiliar columns the agent calls `get_table_schema` first. No cataloging step — Aurora schema changes are immediately visible; best for stable, well-understood operational tables. Generic alternative: the GA **AWS MCP Server** (Agent Toolkit for AWS) with `aws___run_script` (sandboxed Python, SigV4, IAM-scoped) reaching Aurora via RDS Data API or Kinesis via `GetShardIterator`/`GetRecords`.
4. **Validate**: hit the CloudFront URL from stack outputs, log in with the test user, and try: (a) *"chart of customer breakup by subscription type"* → Athena `customers` table + agent-generated bar/pie charts; (b) *"support-ticket breakdown by category and priority"* → Aurora-only path; (c) *"top-5 highest-rated titles and their streaming hours"* → federated: `content_ratings` from Aurora correlated with `streaming_events` + `titles` in Athena.
5. **Production hardening**: review the identity the agent assumes against backends (Cognito covers the user, not the agent-to-data hop); put Lake Formation policies over catalog assets; add a semantic layer (Glue catalog business context + semantic search, announced June 2026) so the agent resolves business terms instead of hallucinating joins.

## Why it matters

- **Self-service over tickets**: users ask in natural language; the discover-then-query workflow (catalog tools or `get_table_schema` before SQL) hides APIs, partition schemes, and credentials.
- **No forced centralization**: governed sources get catalog discipline, operational sources get direct speed — both behind one protocol, one gateway, one agent. Onboarding a source = deploying an MCP server, not redesigning pipelines.
- **Governance preserved where it counts**: Glue + Lake Formation still gate S3 data; Secrets Manager + IAM scope the direct path.

## Takeaways for the seminar

- The spectrum framing is the talk's backbone: catalog-first (governance, Athena joins, partition-aware SQL) → direct (speed, `run_query`/`get_table_schema`, RDS Data API) → hybrid (one orchestrator, same protocol).
- The "mandatory schema discovery" system-prompt rule plus Gateway semantic tool search is what makes it robust to new tables and servers without code changes.
- Open problems to name honestly: cross-source lineage of agent-composed answers, agent-as-consumer identity/authorization, and audit trails capturing *why* an agent accessed data — with pointers to AWS Labs MCP servers, the MCP Gateway Registry, and Agent Toolkit docs.
