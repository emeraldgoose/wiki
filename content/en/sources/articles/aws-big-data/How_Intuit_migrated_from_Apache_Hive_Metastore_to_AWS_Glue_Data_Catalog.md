# How Intuit migrated from Apache Hive Metastore to AWS Glue Data Catalog

**Source**: [AWS Big Data Blog](https://aws.amazon.com/blogs/big-data/how-intuit-migrated-from-apache-hive-metastore-to-aws-glue-data-catalog) · **Published**: 2026-11-11

## Overview

Many enterprises began their big data journey on Apache Hive Metastore (HMS), which reliably stored table definitions and metadata. As analytics scale and cloud adoption grows, requirements shift toward fine-grained access control and fully managed, serverless infrastructure — which is why organizations including Intuit are modernizing their catalogs by moving from HMS to the AWS Glue Data Catalog (GDC), gaining native integration with AWS analytics and AI services plus centralized management and governance. This post, by nine AWS and Intuit authors, documents Intuit's migration as part of its journey to an open, secure lakehouse architecture, with the motivating benefits: reduced operational overhead, improved data discovery, and enhanced integration with AWS analytics services.

The groundwork is catalog hygiene and quota math. Intuit audited the HMS catalog and removed or flagged unused tables and views so migration started clean; estimated GDC read/write API limits from the P99 read/write numbers in HMS's internal tables, submitted quota increases, and load-tested to confirm peak rates without throttling, with retries for whatever throttling remained. Only databases, tables, and partitions were in scope — column statistics, privileges, roles, functions, and transactions were explicitly out of scope. Because GDC does not support table or database renames, pipelines that rename non-partitioned, non-open-table-format tables for atomic updates are advised to write to a new S3 location and run ALTER TABLE ... SET LOCATION instead.

The architecture is hub-and-spoke: a source spoke account where HMS manages metadata for data in Amazon S3, a central data governance account where a sync process propagates metadata into the central GDC (governed by AWS Lake Formation, with AWS CloudTrail recording catalog operations), and consumer spoke accounts where Athena, Redshift, and EMR query through role-based access using Lake Formation and a local Glue Data Catalog. The migration strategy has four moving parts: a one-time full migration; ongoing HMS-to-GDC sync so teams can migrate pipelines independently of upstream and downstream systems; ongoing GDC-to-HMS sync so pipelines still pointed at HMS keep working while upstream tables have already moved; and an hourly parity tool that compares the catalogs and an ad hoc migration process that repairs any discrepancy without a full resync.

The subtle engineering problem in bidirectional sync is preventing circular updates, solved by giving every table a single source of truth recorded as a sourceCatalog flag (HMS or GDC) in an Amazon DynamoDB arbitration table: the HMS-to-GDC sync only picks up tables whose source of truth is HMS, and the GDC-to-HMS sync checks the flag to confirm a change genuinely originated in GDC rather than cascading from HMS. Each table's metadata flows in only one direction at any given time.

## Key points

- One-time migration: the AWS Glue Hive metastore migration utility (customized for batching and retries) runs a Glue ETL job that reads databases, tables, and partitions from the Aurora MySQL database behind HMS over JDBC, transforms them into DynamicFrames, and writes them to GDC; a Lambda starts the job with settings (worker count, database/table/partition write factors) from a cdk.json file, and CloudWatch captures metrics. Planned over a weekend, with nine orchestration steps including stopping incremental sync, cleaning GDC, running full and delta syncs, and enabling parity jobs.
- Rate-limit math: RatePerSecond = catalog.ratePerDPUSecond / DefaultExecutorsPerDPU; with defaults (10, 2) each DPU submits 5 calls/sec, so a 200-DPU job submits roughly 500 calls/sec when the DataFrame is well partitioned. Setting catalog.overwriteIfExists=false skips existing tables; writes use BatchCreatePartitions to keep API volume down; exponential backoff and retry absorb throttling.
- HMS-to-GDC incremental sync: event-driven near-real-time propagation via a Debezium connector doing change data capture on the HMS MySQL instance (no polling or application hooks). Changes are routed to dedicated Kafka topics by object type — HMS-HIVE-DBS (databases), HMS-HIVE-TBLS (tables), HMS-HIVE-TABLE_PARAMS (table parameters), HMS-HIVE-PARTITIONS (partitions), HMS-HIVE-SDS (partition or table location events) — so each type is processed, scaled, and retried independently. Partition events use a 10-second rolling window per table, submitting accumulated events as one batch call to cut throttling under high partition churn. A DynamoDB schema opt-out check lets teams exclude databases or tables; opted-out changes are dropped. When a CDC event lacks context (for example, building a complete table definition from a partition update), the system falls back to JDBC extraction from the source Aurora MySQL database.
- GDC-to-HMS incremental sync: an EventBridge rule matching database/table/partition add-delete events triggers a Lambda that publishes raw events to the Amazon MSK topic central-gdc-raw-events; an Apache Flink pipeline buffers events in a one-minute rolling window per schema or table, sorts by event timestamp, and republishes ordered events to central-gdc-ordered-events. Two consumers then proceed in parallel: a Flink gdc-to-hms-sync pipeline checks a DynamoDB allow list (unpermitted entities are dropped) and pushes changes to HMS using Amazon Athena as the execution engine, and a data lake crawler updates the data lake control plane metadata inventory database. Metadata is synced to HMS via the Thrift SDK with a Thrift client running on an Amazon EMR cluster.
- Parity tool (hourly): a four-stage pipeline — extraction (primary list from DynamoDB; HMS metadata from its MySQL database; GDC metadata via the Glue API), storage (both extracts written to S3 as Iceberg tables), comparison (databases present in both catalogs; tables present in both databases; table structures including columns and types; table locations and SerDe paths; partition values and S3 locations; view definitions), and results (difference tables, aggregation views, parity-health and sync-status views, and history tables tracking changes over time).
- Ad hoc migration: an enhanced version of the one-time utility that accepts database, table, and partition names as input, so a discrepancy found by the parity tool can be repaired without a full sync.
- GDC table requirements to check before migrating: table data must live in S3 (only databases with S3 locations migrate); S3 location names up to 701 characters; only MANAGED_TABLE, EXTERNAL_TABLE, and VIRTUAL_VIEW table types import; column names must be non-blank, up to 255 characters (HMS allows 256), and free of ?, newline, and backslash characters; column type names up to 131,072 characters.
- Post-migration direction: Intuit is implementing fine-grained access control in AWS Lake Formation — row-level, column-level, and cell-level — which it calls critical for its complex solutions and applications; moving the catalog to GDC was an important step in that journey.

## Details

### Why bidirectional sync instead of a cutover

Intuit's central team runs the data catalog as a platform for many teams, and at that scale a hard cutover is not viable. The bidirectional design decouples teams: once the one-time migration completes, a team can migrate its pipelines to GDC whenever ready (the HMS-to-GDC sync keeps the central catalog current), while downstream pipelines still reading from HMS are shielded by the reverse sync. The DynamoDB arbitration table is the linchpin — it both prevents circular update loops between the two sync directions and encodes governance (opt-outs for HMS-to-GDC, allow lists for GDC-to-HMS), so metadata only flows where a team has agreed it should.

### Event ordering as a first-class concern

Both sync directions treat ordering as a problem to solve explicitly. On the HMS side, partition events are coalesced in a 10-second rolling window per table because partition churn is the highest-volume change type. On the GDC side, events can arrive out of sequence, so a Flink pipeline buffers for one minute per schema or table, sorts by event timestamp, and republishes in order before any consumer acts. These choices trade a bounded amount of latency for correct semantics and dramatically fewer API calls — the difference between a sync that works in a demo and one that survives enterprise churn.

### Parity and repair as a safety net

The hourly parity tool is what makes the bidirectional design trustworthy: with two catalogs accepting writes, drift is a matter of when, not if. Comparing Iceberg representations of both catalogs with Spark covers structural facts (existence, columns and types, locations and SerDe paths, partition values, view definitions) and produces difference, aggregation, status, and history views. When drift appears, the ad hoc migration repairs exactly the affected databases, tables, or partitions rather than rerunning a full sync — keeping the reconciliation cost proportional to the discrepancy.
