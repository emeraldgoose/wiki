# AscendGYM: Ascend NPU의 실제 워크로드를 위한 비용 인식 커널 최적화 벤치마크

**Source**: [arXiv](https://arxiv.org/abs/2611.17621)
**게시일**: 2026-11-13

## Overview

AscendGYM(SLAI Training Platform)은 측정이 부족했던 구체적인 과제, 즉 올바르게 동작하는 Ascend NPU 커널 구현이 주어졌을 때 에이전트가 정합성을 유지하면서 허용 가능한 예산 안에서 대상 워크로드 성능을 더 개선할 수 있는지를 평가하는 벤치마크다. KernelBench·NPUKernelBench·CANN Bench 같은 커널 생성 벤치마크와 달리, AscendGYM은 실제 학습·추론 워크로드에서 가져온 입력 구성으로 기존 구현을 최적화하는 능력에 초점을 맞추므로 개선 효과가 해당 배포 환경으로 직접 이어진다.

초기 스위트는 3단계 난이도의 48개 커널로 구성되며, 각 커널은 실제 워크로드에서 수집한 dtype·텐서 형상의 테스트 케이스와 실행 가능한 초기 소스 코드를 제공한다. 내장 실행 샌드박스 AscendForge는 후보 컴파일·정합성 검사·성능 측정을 프로그래밍 가능한 평가 서비스로 통합하고 최적화 궤적을 기록한다. 두 가지 평가 모드를 지원한다 — 고정된 Default 하네스를 쓰는 model evaluation과 커스텀 에이전트를 쓰는 model–harness evaluation. 새 지표 Speedup–Token Score(STS)는 속도 향상을 토큰 비용과 함께 정량화하여 빡빡한/보통/넉넉한 예산(태스크당 10M/20M/50M 토큰)에서의 평가를 가능하게 한다. https://github.com/SLAI-AITP/AscendGYM 에서 공개된다.

## 핵심 내용

- 지표 체계: 성능–예산 결합 지표(STS, Cost-to-Gain), 성능 지표(fast_p, GM Speedup), 예산 지표(토큰 소비, 상호작용 라운드, 경과 시간), 신뢰성 지표(Candidate Pass Rate, Task Pass Rate).
- 현재 시스템은 고전 중: 평가된 모델–하네스 조합의 약 70%가 GM speedup 1.2x 미만이며, 이득은 완만한 개선과 높은 임계값에서의 제한된 커버리지에 집중된다.
- Claude Code/Opus 5와 Codex/GPT-5.6은 모든 태스크를 가속하지만 2x 초과 태스크는 각각 7개와 3개 — 동일한 커버리지가 동일한 크기를 의미하지 않으며 fast_p가 이를 구분한다.
- 빡빡한 예산(10M 토큰): GPT-5.6 Luna의 Warm 구성이 세 예산 모두에서 최고 STS를 달성. cold는 더 많은 탐색으로 격차를 일부 회복하지만 50M 토큰에서도 warm이 더 높은 점수와 성능 구성요소를 유지.
- Code only는 세 예산 모두에서 no lessons보다 우수하지만 둘 다 전체 cold 구성에는 못 미침 — Default 하네스 구성 자체가 결과에 영향을 준다.
- 50M 토큰 예산·10% 이득 목표에서 Opus 5의 OpenCode 대 Claude Code는 달성 태스크 기준 중위 비용 3.8M 대 6.6M 토큰이지만, OpenCode는 일부 태스크에서만 목표를 달성하고 Claude Code는 Batch 1의 17개 전체를 커버한다.
- GPT-5.6은 세 하네스 모두에서 전 태스크를 통과하지만 GM speedup은 크게 다르다: Codex ~1.69x 대 Claude Code ~1.05x — 정합성이 성능을 보장하지 않는다.
- OpenCode/Qwen-35B는 토큰·라운드 수가 적지만 태스크당 약 11.1시간 소요 — 토큰 비용과 경과 시간은 서로 다른 선택을 유리하게 만든다.

## 상세

- 태스크 설계: 커널과 입력 형상/dtype/파라미터는 실제 학습·추론 워크로드에서 선정되며, 각 태스크는 구체적 최적화 목표와 검증 조건을 갖고, 이득은 동일 조건의 초기 구현 지연 대비로 측정한다.
- 신뢰성: 컴파일·정합성·속도는 NPU에서의 실제 실행으로 각각 별도 확인한다. AscendForge는 호스트·디바이스 코드를 빌드하고 측정을 실행하며, 사전 정의된 검증 조건 아래 피드백을 반환한다.
- STS: 각 개선 시점의 최종 성능 이득과 누적 토큰 소비를 결합한다. CTG는 달성 횟수와 함께 달성 비용을 보고하여 조건부 중앙값만으로 선택하는 오류를 막고, fast_p는 속도 임계값을 초과한 태스크 비율을 측정한다.
- 평가 모드: model–harness evaluation은 에이전트 스택을 비교하고, model evaluation은 모델을 고정(GPT-5.6 Luna)한 채 Default 구성(cold, warm, no lessons, code only)을 경험 관리·탐색 오케스트레이션과 함께 비교한다.
- 보고 관행: GM speedup은 fast_p 커버리지와 함께 읽어야 하며, 예산 지표(토큰·라운드·경과 시간)는 서로 괴리되므로 별도 보고해야 한다. 비통과 실행도 누적/평균 비용에 포함한다.
- 결론: AscendGYM은 의미 있는 도전 과제다 — 주어진 초기 구현과 평가 조건에서 광범위한 태스크에 걸친 실질적 개선은 현재 시스템의 능력 밖에 있다.
