# ProgramDistill: 대화형 웹 앱에서 검증 가능한 레퍼런스 기반 SWE 태스크로

## 초록

코딩 에이전트는 보통 이슈나 지시문 형태로 원하는 동작이 명시된 상태에서 평가된다. 그러나 실제 웹 개발에서는 에이전트가 동작 중인 소프트웨어를 보고 동작을 추론한 뒤, 미완성 애플리케이션에 구현해야 할 때가 있다. 본 논문은 완전히 동작하는 레퍼런스 애플리케이션과의 상호작용을 통해 발견한 기능들을 대상으로 코딩 에이전트를 평가하는 벤치마크 ProgramDistill을 제안한다. 애플리케이션을 서로 다른 세분도(granularity)의 기능들로 분해(factorizing)하고, 각 기능에 gold 패치로 실행 가능한 리플레이 가능한 행동(replayable behavior)을 연결하는 방식으로 ProgramDistill을 구축한다. 제안 파이프라인 mine-craft-patch는 26개 애플리케이션에서 리플레이 검증된 행동 1,975개를 발견하고, 사람의 개입 없이 4,063개 태스크를 구성한다. 9개 최신 코딩 에이전트를 평가한 결과, 전체 애플리케이션 재구축(reconstruction)의 누적 워크플로에서 GPT-6 Astra와 Claude Opus 5가 각각 49.2%, 28.8%의 성공률을 기록했다. 부분 애플리케이션 재구축에서는 복원 깊이(restoration depth)가 1에서 8로 증가함에 따라 성공률이 100%에서 64.0%로, 96%에서 32%로 하락했다. ProgramDistill은 이에 따라 난이도가 조절되는 확장 가능한 벤치마크를 제공하며, 코딩 에이전트의 평가·진단과 향후 커리큘럼 기반 학습의 자연스러운 토대가 된다.

## 배경 및 문제 설정

대부분의 SWE 벤치마크(SWE-bench와 후속 연구들)는 에이전트에게 미리 작성된 명세를 건넨다: GitHub 이슈, 지시문, 숨겨진 테스트가 그것이다. 에이전트는 소프트웨어가 무엇을 해야 하는지 스스로 발견할 필요가 없다. 본 논문은 이것이 일반적인 웹 개발 워크플로를 놓치고 있다고 주장한다: 개발자는 동작하는 레퍼런스 — 이전 제품 버전, 인터랙티브 프로토타입, 유사 앱, 데모 영상 — 와 미완성 현행 코드베이스를 함께 받고, 레퍼런스와 상호작용하며 의도된 동작을 추론하고, 구현한 뒤, 레퍼런스 기준으로 검증해야 한다. 카드 하나를 드래그하는 동작조차도 눈에 보이는 효과와 영속화된 애플리케이션 상태를 함께 추론해야 한다.

최근 연구들도 이 방향을 가리킨다. ProgramBench는 컴파일된 C/C++, Go, Rust 프로그램을 탐색(probe)해 관측된 실행 결과로부터 재구축하도록 요구하지만, 각 프로그램을 통째로 재구축하는 단일 타깃으로 취급한다. 반면 대화형 웹 앱은 더 풍부한 구조를 갖는다: 기능은 UI 액션과 애플리케이션 상태를 통해 전개되며, 명시적 전제조건(객체를 만들기 전 로그인, 편집 전 생성)을 갖는다. 이러한 상태 의존성은 전제조건 계보(prerequisite lineage)를 이룬다. 본 논문이 던지는 질문은 다음과 같다: 이 잠재된 행동 구조를 발굴해, 동작하는 웹 앱 하나를 세분도가 조절되는 검증 가능한 SWE 태스크 다수로 바꿀 수 있는가? 이 변환을 application-to-task factorization이라 부르고, 실행 가능한 레퍼런스에서 동작을 추론해 코드로 실현하는 평가 능력을 reference-to-current distillation이라 부른다. 성공 여부는 에이전트의 패치 적용 후에도 동일한 리플레이 가능한 상호작용 트레이스가 통과하는지로 판정한다.

## 방법론

**설정: 결정적·관측 가능한 인스턴스.** 코퍼스는 26개 웹 애플리케이션으로 구성된다: OSWorld 웹 스위트에서 가져와 자체 완결적으로 만든 앱들에, 코드베이스가 더 크고 워크플로가 깊으며 아키텍처가 이질적인 실제 오픈소스 프로젝트와 SaaS 클론을 더했다. 각 앱은 두 번 서빙된다: 에이전트에게 소스가 숨겨진 고정 프로덕션 빌드를 레퍼런스 인스턴스로, 핫 리로드되는 개발 서버 버전을 편집 가능한 인스턴스로 제공한다. 데이터베이스·백엔드·프론트엔드에 걸친 공유 결정적 클럭을 사용하고, 수집과 리플레이 전에 상태를 리셋해 순서와 타임아웃 의미를 보존하면서 시간 의존적 flakiness를 제거한다. 공유 Playwright 기반 브라우저 헬퍼가 고수준 액션을 실행하고 구조화된 관측(가시 텍스트, 접근성 트리, 상호작용 요소)을 반환하며, 변덕스러운 DOM ID가 아니라 안정적인 관측 가능 속성으로 요소를 식별하고 앱이 안정될 때까지 기다린 뒤 기록한다.

**마이닝: 행동 목표에서 검증된 트레이스로.** 현재 트레이스 뱅크가 주어지면 Planner가 소스와 UI 근거에 입각한 새로운 행동 목표를 제안하고, 각 목표에 선택적으로 부모 트레이스를 붙인다. 부모 계보를 리셋 상태에서 리플레이해 전제조건 상태를 수립한 뒤, LLM 에이전트(파이프라인 전 단계에 GPT-5.6 Sol 사용)가 실제 앱을 탐색하며 목표를 추구해 탐색 트레이스를 기록한다. 이어 Collector가 탐색 경로를 특권 컨텍스트로 참조해 깨끗한 리셋 상태에서 해당 행동을 다시 수집하며, 우회(detour)를 제거하고 관측된 상태에서 기대 결과 신호를 선별한다. 채택된 트레이스는 리플레이 안정적인 액션, 기대 신호, 부모 참조를 담아 계보 `L_d = (tau_1, ..., tau_d)`를 확장한다. 리플레이 검증기 `V(A, L_d)`는 LLM 개입 없이 리셋 상태에서 계보를 리플레이해, 모든 액션이 완료되고 모든 신호가 성립할 때만 1을 반환한다. 온전한 앱에서 `V = 1`인 트레이스만 채택한다(총 1,975개). 역할 분담: Planner, Collector, Relabeler(실제로 달성된 것을 라벨링), Reflector.

**크래프팅: 검증된 행동에서 복구 태스크로.** 두 가지 제어축이 있다. 마스크 범위: 로직만 제거(UI는 그대로, 구현만 제거) vs. 로직+UI 모두 제거. 태스크 구성: 원자적(단일 행동) vs. 누적(계보를 따른 여러 행동). 목표 트레이스 `tau_d`에 대한 트레이스 조건 마스크 `m_d`는 마스킹된 앱 `A[m_d]`와, 사용자 관점 목적을 간결히 서술하되 구현·복구 절차·정확한 신호는 숨긴 행동 문제 서술을 만든다. 원자적 검증 조건은: 마스킹된 앱이 빌드·실행되고, 모든 전제조건이 여전히 리플레이되며(`V(A[m_d], L_{d-1}) = 1`), 목표는 실패한다(`V(A[m_d], L_d) = 0`) — SWE-bench식 fail-to-pass 타깃에 pass-to-pass 전제조건을 곁들인 형태다. 별도 LLM 마스크 깊이 비평가(mask-depth critic)가 피상적 마스크(기능 플래그 토글, 구현은 살려둔 채 호출부만 제거)를 거부하며, 실패한 제안은 제한된 수정 라운드를 거친다. 검증된 마스크를 뒤집으면 gold 패치가 되며, 전체 계보가 리플레이를 통과해야 한다는 조건으로 검증된다. 누적 마스크 `M_L = m_{j1} ⊕ ... ⊕ m_{jr}`는 계보를 따라 검증된 원자적 마스크들을 결합하며, 복원 깊이 `r_L`은 복구 타깃 수를 센다(마스킹되지 않은 트레이스가 리플레이 브릿지로 쓰이므로 계보 깊이 `d`가 `r_L`을 초과할 수 있다). 겹치지 않는 편집은 git three-way merge를 일관성 검사로 삼아 결정적으로 병합하고, 불일치 시 LLM 병합 에이전트가 겹침을 해소한다.

**패칭: 평가 설정.** 부분 애플리케이션 재구축은 에이전트에게 마스킹된 저장소와 문제 서술을 주고, 브라우저를 통해 레퍼런스와 비교하면서 핫 리로드되는 현행 앱을 편집하게 한다. 마스킹 diff, gold 패치, 채점 트레이스, 레퍼런스 소스는 숨기고 외부 네트워크 송신은 차단한다. 전체 애플리케이션 재구축은 최소 실행 가능 스캐폴드에서 출발해 전체 워크플로를 다시 쌓아야 한다. 트레이스 수준 검증은 마이닝 트레이스를 리플레이하고, 계보 스코어링은 행동 체인의 얼마나 많이가 복구됐는지를 잰다(원자적 vs. 체인/누적 스코어).

## 결과

- **벤치마크 규모**: 26개 앱의 리플레이 검증 행동 1,975개에서, 사람이 작성한 이슈·테스트·어노테이션 없이 4,063개 태스크를 얻었다. 누적 태스크 1,201개 중 629개는 결정적으로 합성됐고 572개는 LLM 병합 에이전트가 필요했다(마스크 구성요소 탈락 없이 전부 성공). 병합 에이전트 사용률은 깊이와 함께 상승한다: `r = 2`에서 25.6%, `r = 8`에서 89.7%, 그 이상에서 100%.
- **전체 애플리케이션 재구축**(9개 최신 코딩 에이전트): GPT-6 Astra가 평가 워크플로의 49.2%, Claude Opus 5가 28.8%를 복구했다. 궤적 분석에 따르면 관측 전략이 중요하다: Astra는 가장 강한 복구 성능과 함께 가장 활발한 관측 활동, 가장 적은 편집/쓰기 스텝을 보였다.
- **부분 애플리케이션 재구축**: 복원 깊이에 따른 체계적 성능 저하. Astra는 깊이 1에서 100%, 깊이 8에서 64.0%로 하락하고, Claude Opus 5는 같은 구간에서 96%에서 32%로 하락한다. 태스크가 깊어질수록 요구 행동당 관측 노력이 감소한다 — 재구축 부담과 에이전트 노력 사이의 벌어지는 간극이며, 순수 코딩 능력을 넘어 관측·검증·편집 간 노력 배분이 핵심 차원임을 보여준다.
- **진단**: 행동 수준 결과, 마스크 범위 분리(로직만 vs. 로직+UI), 체인 스코어 뷰, 컨텍스트 길이 통제(깊이 효과는 컨텍스트 길이만으로 설명되지 않음), 지름길 시도 분석(격리 상태에서 채점 트레이스나 레퍼런스 소스를 탐색하려는 에이전트)을 부록에 보고한다.

## 한계 및 향후 과제

- 파이프라인 모델 의존성: 마이닝·크래프팅 전 단계에 GPT-5.6 Sol을 쓰므로, 행동 커버리지와 마스크 품질이 해당 모델의 탐색 편향을 물려받는다. 코퍼스는 26개 앱이며, 더 넓은 스택, 인증/결제 연동, 모바일-웹 하이브리드는 검증되지 않았다.
- 레퍼런스 기반 설정은 실행 가능한 레퍼런스와 결정적 리플레이 하네스를 가정한다. flaky한 실제 백엔드, 서드파티 서비스, 타이밍 민감 상호작용은 실험실 밖에서 검증기를 깨뜨릴 수 있다.
- Gold 패치는 구성상 원래 구현을 복원하므로, 태스크가 풀 수 있음을 증명할 뿐 레퍼런스 해법이 유일하거나 관용적임을 보장하지 않는다. 격리에도 불구하고 리플레이 신호에 대한 지름길·과적합은 여전히 적대적 우려로 남는다.
- 저자들은 잠재적 오용(관측 가능한 동작으로부터 독점 웹 앱의 자동 복제)을 명시하고, 깊이 축을 해결된 평가가 아니라 궤적 증류나 RL 학습용 미래 커리큘럼 소재로 자리매김한다.

## 소프트웨어 엔지니어에의 시사점

프론트엔드·풀스택용 코딩 에이전트를 만들거나 도입하는 팀에게 헤드라인은 운영적이다: 이슈-투-패치 벤치마크는 레퍼런스 기반 태스크("스테이징 배포를 보고 이 플로를 재구현하시오")에 대한 준비도를 과대평가한다. 하네스에 레퍼런스 기반 평가를 추가하라: 레퍼런스 소스는 숨기고 실행 중인 앱만 브라우저 관측으로 노출하며, 리플레이 가능한 상호작용 트레이스와 전제조건 pass-to-pass 검사로 채점하라. 단일 집계값이 아니라 복원 깊이(본 연구에서는 1~8)에 대한 성공률을 추적하라 — 가파른 감쇠를 예상하고 관측·검증 스텝 예산을 그에 맞춰 잡아야 하며, 여기서 최고 에이전트는 더 많이 관측하고 더 적게 편집해서 이겼다. mine-craft-patch 레시피는 재사용 가능하다: 리플레이 검증 트레이스는 그대로 회귀 테스트가 되고, 마스크 깊이 비평가와 gold 패치 리플레이 패턴은 자사 앱에서 내부 학습 태스크를 생성하는 저렴한 템플릿이다. `concepts/ai-engineering/agent.md`, `concepts/ai-engineering/agent-evaluation.md`, `guides/ai-engineering/build-agent.md`의 확장이다.
