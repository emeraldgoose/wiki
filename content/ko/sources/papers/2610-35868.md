# Retriever 없는 검색: 의사결정 모델로 문서 탐색하기

**원문**: [arXiv:2610.35868](https://arxiv.org/abs/2610.35868) · **게시일**: 2026-10-26
**저자**: Chao Wan, Paul Jünger, Beixi Du, Bodong Liu, Navaneetha Krishnan, Kilian Q. Weinberger
**라이선스**: CC BY 4.0

## 개요

대형 언어 모델은 빠르게 강해졌지만, 검색기가 모델에게 보여 줄 증거를 결정하는 방식은 크게 바뀌지 않았다. 대부분의 검색 시스템은 여전히 BM25 같은 어휘 휴리스틱이나 고정된 임베딩 공간의 유사도에 의존한다. 이로 인해 능력 격차가 생긴다. 검색기가 찾아내지 못한 것은, 아무리 강한 생성 모델도 복구할 수 없다. 논문은 **DecisionRAG**를 제안한다. **의사결정 모델**(토큰을 생성하지 않고 미리 정한 선택지의 확률을 반환하는 모델)을 사용해 코퍼스의 고유한 구조를 주제 수준에서 개별 패시지 수준까지 **탐색**하는 검색기 없는 프레임워크다.

DecisionRAG는 내부 노드가 문서 묶음이나 패시지를 요약하는 트리로 코퍼스를 본다. 각 수준마다 후보들을 **공유 컨텍스트**에서 함께 평가해, 형제 노드 사이의 관련성 추정이 서로 비교 가능하도록 한다. 코퍼스 자체의 구조나 임베딩 기반 군집화에서 출발해 매 단계마다 탐색 범위를 좁히며 관련 없는 가지를 잘라낸다. 과제 전용 학습과 전통적인 1단계 검색기가 모두 필요 없다. 기본 구성은 사전학습된 의사결정 모델(Jev)만 사용하고도 8B 리랭커를 붙인 dense retrieval을 뛰어넘는다.

네 개 벤치마크—MultiDoc2Dial, ConditionalQA, MTRAG, Natural Questions—에서 방식은 뚜렷한 검색 향상과 속도를 함께 달성한다. 질의당 0.68~1.76초 안에 검색을 끝내며, Qwen3-Reranker-8B를 쓴 dense retrieval의 3.3~14.3초와 비교된다. 2.68백만 개의 위키백과 단락 집합에서는 제목의 16%만 읽고도 검색하고, 코퍼스 규모가 커져도 단계 수가 로그 스케일로만 늘어나므로 질의당 처리 시간이 늦게만 증가한다.

## 핵심 내용

- **DecisionRAG** 도입: 평면 인덱스에서 검색하는 대신 의사결정 모델로 코퍼스 계층을 탐색해, 언어 모델 성능을 검색으로 바로 가져온다.
- 의사결정 모델의 두 모드를 사용한다. **병렬 이진 판단**(각 후보에 Yes/No 확률을 독립 산출해 점수가 합이 1이 될 필요가 없음)과 **다중 선택 판단**(후보들 사이의 softmax 분포).
- 후보들을 **공유 컨텍스트**에서 평가해 관련성 추정을 비교 가능하게 한다. 공유 컨텍스트의 이점은 요청당 후보가 약 50개에 이를 때까지 늘어난다.
- 과제 전용 학습이나 1단계 검색기 없이도, dense retrieval + 8B 리랭커 대비 MultiDoc2Dial **R@1 +13.8포인트**, Natural Questions **Hit@1 +17.4포인트**를 달성한다.
- GPT-5로 dense top-20을 리랭킹한 것과 비교해 동등하거나 높은 순위-1 정확도를 보이며, ConditionalQA R@10과 MTRAG R@5에서는 우위를 보인다.
- Dense retrieval과 깔끔히 결합한다. 최종 단계에 dense-retrieved 패시지를 추가하면 R@10이 MultiDoc2Dial 83.6 → 84.7, ConditionalQA 71.9 → 76.3, Natural Questions 86.7 → 88.9로 상승한다.
- 108,626개 위키백과 페이지를 1,000개 클러스터로 군집화해 2.68M 단락을 처리하고, 끝까지 1.73초를 유지한다.
- 과제 전용으로 학습한 open-weights 의사결정 모델(Qwen3 기반 1.7B~8B)도 지원하며, 8B 판단기가 MultiDoc2Dial에서 60.7 R@1을 기록해 발표된 task-trained retriever보다 5.7포인트 높다.

## 상세

### 방법

**문제 정식화.** 코퍼스는 리프가 패시지이고 내부 노드가 점점 더 큰 묶음을 나타내는 트리다. 묶음 단위는 help center, 주제 클러스터, 문서, 섹션 제목, 개별 패시지 등이다. 각 노드에는 짧은 텍스트 설명이 붙는다. 패시지면 그 자체 텍스트, 문서면 제목, 클러스터면 한 문장 요약이다. 트리의 깊이는 **수준(level)**, 의사결정 모델 요청 한 라운드는 **단계(stage)**라 부른다. 이전 대화 턴을 포함할 수 있는 질의가 주어졌을 때目標는 필요한 증거가 들어 있는 패시지를 찾는 것이다.

**의사결정 모델 판단.** Jev(TypeSafe AI)나 OpenAI의 의사결정 모델 같은 시스템은 컨텍스트와 질문을 평가해 미리 정한 선택지의 확률을 자동회귀 토큰 생성 없이 반환한다. **병렬 이진 판단**은 여러 후보를 한 번에 평가하며 `p_i^bin = P(Yes | s, Q_i)`를 산출한다. 이는 Yes/No 사이에서만 정규화되므로 점수가 합에 구애받지 않으며 요청 크기 안에서 목록을 크게 둘 수 있다. **다중 선택 판단**은 대신 후보들 사이의 분포 `p_i^mul = P(a_i | s, Q, A)`를 반환하며, 서로 경쟁하는 대안 중에서 결정한다. 두 모드 모두 같은 공유 컨텍스트 `s`를 쓰기 때문에 관련성 추정이 서로를 기준으로 비교 가능해진다.

**계층적 검색.** 각 수준마다 가장 유망한 노드를 유지·확장해 다음 수준으로 나아간다. 문서 선별(document screening)에서 상위 패시지를 유지하고, 패시지 채점과 선택적 리랭킹이 정답을 정밀화한다. 대화 벤치마크에서는 마지막 여섯 턴을 유지하고, 이전 턴의 증거를 이어받는 **노트패드(notepad)**를 운영한다.

**계층 구조와 규모 확장.** 계층은 기존 문서 구조와 메타데이터에서 뽑거나, Natural Questions의 위키백과처럼 구조가 없는 경우 108,626개 페이지를 제목과 첫 문장 임베딩에 대한 k-means로 1,000개 그룹으로 나누어 만든다. 각 클러스터는 Qwen3-8B가 한 문장 요약을 생성한다. 한 요청에 들어가지 않는 수준은 병렬 요청으로 쪼개고 점수를 합친다. 더 정밀한 비교가 필요하면 상위 후보만 한 요청에 다시 채점한다. 트리는 균일할 필요가 없으며, MTRAG에서는 60개 이상의 패시지를 가진 페이지 아래에만 heading 수준을 삽입한다. 컨텍스트 한도를 넘는 노드는 여러 요청으로 분할된다. DecisionRAG는 dense retriever의 상위 패시지를 최종 후보로 받아들이는 것과도 결합할 수 있다.

지연 시간은 코퍼스 크기와 아니라 깊이에 좌우된다. 노드당 자식이 최대 `b`개인 대략 균형 잡힌 계층을 가정하면, 질의당 순차 결정 횟수는 `ceil(log_b N)`(Equation 4)이며, 요청당 `t_req ≈ 0.2초`다. `b = 100`에서 10^9개 패시지에도 다섯 번의 결정만 쓰면 된다.

### 실험 설정

413개 help-center 페이지부터 108,626개 위키백과 페이지에 이르는 네 개 벤치마크. MultiDoc2Dial: 4 centers / 4,110 passages / 4,201 turns, 금 패시지 1개. ConditionalQA: 652 pages / 58,483 paragraphs / 285 questions, 금 패시지 1~22개. MTRAG IBM Cloud: 172 products / 8,578 pages / 72,442 passages / 205 turns, 금 패시지 1~7개. Natural Questions (DAPR): 1,000 clusters / 108,626 pages / 2.68M paragraphs / 500 test questions, 금 패시지 1~3개.

데이터셋별 계층과 유지 예산(budget)은 설계 집합(design set)에서 선택해 생성기 입력 없이 적용한다. MultiDoc2Dial: help center → page → passage, 상위 10 페이지 + 노트패드의 최대 2 페이지. ConditionalQA: page → paragraph, 상위 3 페이지. MTRAG: page → heading → passage, 모든 페이지 제목을 병렬 채점, 상위 50 재채점, 상위 10 유지, 긴 페이지는 제목을 먼저 선택. Natural Questions: cluster → page → paragraph, 1,000 중 150 클러스터, 상위 30 페이지의 단락. 모든 Jev 구성은 상위 20 패시지의 다중 선택 리랭킹으로 끝나며(Natural Questions는 5개), MTRAG는 선택된 패시지만 1순위로 승격한다.

베이스라인에는 BM25, SPLADE++, Qwen3-Embedding-8B(dense), dense top-100 위에서 bge-reranker-v2-m3와 Qwen3-Reranker-8B, dense top-20 위에서 RankGPT 스타일 프롬프트로 GPT-5 리랭킹이 포함된다. 발표된 참조 결과(DPR, SFRe2g, ELSER)는 재실행하지 않고 참조값으로 포함된다.

### 결과

과제 전용 학습 없는 검색(Table 2). MultiDoc2Dial에서 DecisionRAG (Jev)는 47.4 R@1에 도달하며, dense + Qwen3-Reranker의 33.6을 13.8포인트 앞선다. Natural Questions에서는 Hit@1이 17.4포인트 향상(65.4 대 48.0)된다. GPT-5 리랭킹과 비교해 두 개 벤치마크에서 순위-1 정확도가 동등하거나 높고(Natural Questions 65.4 대 60.8; MultiDoc2Dial 47.4 대 47.5), 다른 벤치마크에서는 R@10/R@5가 더 높다. Dense 후보를 DecisionRAG에 더하면 레이블된 세 벤치마크 모두에서 R@10이 상승한다.

Qwen3.5-27B를 생성기로 쓴 downstream 정답 품질(Table 3)에서는 MTRAG 개선이 가장 크다. judged answer correctness가 Qwen3-Reranker의 39.4%에서 44.1%로, dense 후보 추가 시 47.3%로 오른다(GPT-5 리랭킹 34.0% 대비). ConditionalQA exact match은 47.6%, Natural Questions는 54.8%에 이르러 금패시지 상한에 가까워진다.

과제 전용 의사결정 모델(Table 4, Appendix G)은 MultiDoc2Dial 데이터로 Qwen3-8B를 적응 학습하며 60.7 R@1(85.8 R@10)을 달성해, 발표된 task-trained retriever를 5.7포인트 넘어선다. 프레임워크가 지도 학습도 활용할 수 있음을 보여준다.

지연 시간과 비용(Table 5): DecisionRAG는 질의당 0.68~1.76초, dense + Qwen3-Reranker 3.3~14.3초, GPT-5 리랭킹 11.8~15.0초. API 비용 질의당 0.22¢~2.33¢. Natural Questions 지연(1.73초)은 페이지가 15배 많은데도 MTRAG과 같다. 계층 구조가 비선형 지연을 제공함을 보여준다.

### 한계

방법은 코퍼스 계층의 구조와 노드 설명이 의사결정 모델로 관련 가지를 식별할 수 있어야 한다. 문서 구조가 엉성하거나 설명이 정보가 적으면 검색 품질이 떨어진다. 가지를 자르는 것(pruning)은 되돌릴 수 없으므로, 조상이 버려지면 관련 패시지가 놓칠 수 있다. 더 큰 탐색 예산과 dense retrieval 보완이 이를 완화한다. 극단적인 선택성은 각 수준의 후보 다양성에 의존한다.

### 소프트웨어 엔지니어 관점

- **패턴**: 의사결정 모델(확률만, 토큰 생성 없음)로 수준별 탐색을 하면, 인덱스 크기가 아니라 계층 깊이로 코퍼스 규모를 처리한다. 임베딩 기반 검색을 대체하거나 보완할 수 있다.
- **복잡도**: `log_b N`개 단계라 코퍼스 규모가 커져도 지연 시간이 느리게 늘어난다. 대략 균형 잡힌 계층이 있으면 십억 패시지도 몇 단계 더 추가될 뿐이다.
- **통합**: DecisionRAG는 dense retrieval을 대체하지 않고 보완한다. 최종 단계에 dense 후보를 추가하면 모든 실험 조건에서 R@10이 상승했다.
- **엔지니어링 선택**: 후보는 병렬로 채점할 수 있다. 공유 컨텍스트는 후보가 약 50개를 넘어가면 추가 후보보다 강한 효과를 내니, 큰 수준은 혼잡하게 채우기보다 요청을 나누어 splits해야 한다.
- **운영**: downstream RAG 품질은 측정 가능한 수준으로 개선하지만, 생성 모델은 여전히 금패시지에 가까운 근거를 원한다. DecisionRAG는 격차를 상당히 줄이나 완전히 닫지는 못한다.
