# GH-AWTrace: GitHub 에이전트 워크플로 실행 로그 대규모 데이터셋

**Source**: [arXiv:2611.06866](https://arxiv.org/abs/2611.06866) · **게시일**: 2026-11-04
**Authors**: Jasem Khelifi, Hao Li, Ali Ouni, Mohammed Sayagh, Mohamed Aymen Saied

## 개요

GitHub Agentic Workflow(gh-aw)는 AI 에이전트가 일정에 따라 또는 저장소 이벤트에 반응해 반복 저장소 작업을 수행하게 한다. 기존 연구는 워크플로의 정의와 출력 — 개발자가 마크다운/YAML 명세를 어떻게 작성·유지하는지, 실행이 무엇을 산출하는지 — 을 살폈지만 실행 중 실제로 무슨 일이 벌어지는지에 대한 증거는 거의 없었다. 워크플로 정의는 의도된 동작을 서술하고, 실행 수준 결과는 중간 과정을 설명 없이 요약할 뿐이다. 도구 상호작용, 접근 제한, 인프라 장애, 복구 시도를 기록하는 실행 로그가야말로 이 간극을 메울 증거인데, GitHub 보존 정책은 이를 지운다. 실행 기록은 400일 후, 공개 워크플로 실행 로그는 최장 90일 후 삭제된다.

GH-AWTrace는 이런 유실되기 쉬운 증거를 대규모로 포획하는 보존·연결 사업이다. 데이터셋은 5,051개 저장소의 25,014개 검증된 gh-aw 워크플로를 4,112,526개 실행 기록, 562,877개 비어 있지 않은 실행 로그 아카이브(90일 보존 창 안에서 내려받은 56.1GB ZIP), 저장소 메타데이터, 생성된 워크플로 구성과 연결한다. 검증은 엄격했다. 검색으로 찾은 5,059개 저장소의 25,227개 후보 파일 가운데, 생성기 문구가 어떤 구성 키보다 앞서 여는 YAML 주석에 나타날 때만 블롭을 받아들였고, 필수 헤더가 없는 63개 파일과 회수 불가한 150개 블롭은 제외했다.

논문은 로그가 아닌 것도 솔직하게 밝힌다. 부분 관찰이지 완전한 에이전트 궤적이 아니다. 커버리지는 워크플로마다 다르고(로그가 있는 6,040개 워크플로의 중앙값은 워크플로당 16개, 사분위 범위 6-60), 선택된 실행 중 821,672개는 내려받은 아카이브가 없으며, 내려받은 1,070,338개 ZIP이 비어 있다. 비어 있는 2,900개 초기 감사에서 2,699개는 스킵된 작업만 보여주고 195개는 작업 자체가 없었다. 그럼에도 사례 연구는 정의나 실행 결론에서 보이지 않는 현상 — 실행 중 도구 거부로 바뀌는 에이전트 행동, 재시도가 딸린 공급자 인증 장애, 배경 에이전트 간 실행 내 위임 — 를 이 데이터가 드러냄을 보여준다.

## 핵심 내용

- 규모: 5,051개 저장소의 25,014개 검증된 gh-aw 워크플로가 4,112,526개 실행 기록(400일 실행 보존 정책의 한계인 2025-08-14~2026-09-21)과 561,367개 실행의 562,877개 비어 있지 않은 로그 아카이브에 연결된다.
- 로그 보존 창: GitHub가 공개 실행 로그를 최장 90일 후 삭제하므로, 수집은 2026-06-23~09-21에 생성된 2,453,263개 실행 기록을 대상으로 하고 SHA-256 해시와 파일 목록을 기록한 1,633,215개 ZIP(56.1GB)을 내려받았다.
- 파이프라인 감소가 끝까지 문서화됐다. 후보 25,227 → 검증된 워크플로 25,014, 실행 기록이 있는 워크플로 11,396 대 없는 13,618, 90일 창 밖 실행 기록 1,659,263, 아카이브가 없는 실행 821,672(보존·삭제·접근 제한·미완료), 빈 ZIP 1,070,338 대 로그 파일이 있는 아카이브 562,877, 첫 시도 이후 재실행에서 온 아카이브 18,337.
- 실패 지형: 비어 있지 않은 로그 아카이브의 178,151개(31.7%)가 실패 결론 실행 기록에 연결된다. 논문은 이를 전부 에이전트 탓으로 돌리지 않으며, 차단된 작업 사례와 공급자 인증 장애 사례(부분 실행 후 HTTP 403, 한 번 재시도)를 별개 원인으로 제시한다.
- 제약 아래 에이전트 행동: 기록된 사례에서 한 에이전트는 도구 거부 후 배포 명령을 바꾸고, 다른 에이전트는 리뷰 판정 전에 의존성 업데이트를 살핀다. 실행 결론은 알려주지 않는 거부 후 적응의 증거다.
- 실행 내 조율: 어떤 리뷰 실행은 배경 리뷰어 셋을 파견하고 두 응답자의 합의로 발견을 골랐다. 단일 실행 내 위임과 종합을 보여주지만 실행 간 공유 메모리의 증거는 없다.
- 로그에 담긴 것: 프롬프트 파일 경로와 크기, 가시적 에이전트 메시지, 도구 호출과 응답이다. 전체 프롬프트 텍스트나 비공개 추론이 아니므로 완전한 프롬프트로 취급해선 안 된다.
- 데이터가 가능하게 하는 연구: 에이전트 워크플로 실패 분류학, 도구 거부 후 복구 행동, 보고된 실행 결론과 가시적 과제 진행의 일치 여부. 데이터셋(연결 테이블, 아카이브, 스키마, 접근 안내)은 Hugging Face에 공개되어 있고 파이썬 예제가 31.7% 수치를 재현한다.

## 상세

### 3단계 수집 설계

A단계는 워크플로를 발견·검증한다. GitHub 코드 검색이 후보를 찾고, 검증은 gh-aw 생성기 문구가 모든 구성 키에 앞서 여는 YAML 주석으로 존재해야 하며, 받아들인 블롭은 검색이 돌려준 정확한 개정판에서 내려받는다. B단계는 워크플로 ID로 GitHub REST API를 통해 실행을 수집해 반환된 모든 필드를 저장하고, 각 실행을 저장소 ID와 정확한 경로로 발견 시 인덱싱된 YAML 개정판에 연결한다. 실행이 실제로 쓴 개정판은 다를 수 있으므로 head_sha를 보존한다. C단계는 90일 창 안에서 로그 아카이브를 내려받아 실행 ID와 시도 번호로 식별하고(재실행은 실행 ID를 유지하고 새 시도 번호를 받음) 무결성 메타데이터를 저장한다. 세 단계는 명시적 키(repo_id, 워크플로 경로, run_id, attempt)로 연결되어 평면적 로그 덩어리가 아니라 관계형 데이터셋이다.

### 커버리지 공백 읽기

데이터셋 자신의 통계는 정책 제약 아래 보존의 교과서다. 4,112,526개 실행 기록 중 90일 로그 창 안의 2,453,263개만 내려받을 수 있는 로그를 가질 수 있었고, 내려받은 1,633,215개 ZIP의 상당수는 저자도 원인을 특정할 수 없는 이유로 비어 있거나 없다 — GitHub 감사에서는 스킵된 작업이 지배적이다. 따라서 분석은 워크플로 실행과 실행 시도, 보고된 결과와 관찰된 과제 완수, 에이전트 행동과 인프라 장애를 구분해야 한다. 저자들은 GH-AWTrace를 이런 질문을 뒷받침하는 보존된 증거로 위치시키며, 더 큰 주장은 체계적 표본 추출과 검증을 요구한다고 밝힌다.
