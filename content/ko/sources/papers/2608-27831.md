# RealSWE: 실제 사용자 요청 환경에서 코딩 에이전트를 성분 분해 평가하기

**원문**: [arXiv:2608.27831](https://arxiv.org/abs/2608.27831) · **게시일**: 2026-08-28
**저자**: Gyuhyeong Kim, Hyojung Gwon, Jeonghyeon Kim 외 2인

## 개요

코딩 에이전트는 SWE-bench 계열 벤치마크로 평가되는 것이 일반적이다. 이 벤치마크의 태스크는 정리된 GitHub 이슈에서 만들어져 길고 구조화되어 있으며 정보가 풍부하다. 반면 프로덕션에 실제로 도착하는 요청은 정반대다. 짧고 비격식적이며, 문제 진술 하나만 담고 있는 경우가 많다. 이 논문은 두 세계 사이의 간극을 정량화하고, 그 간극이 보고되는 에이전트 성능을 얼마나 왜곡하는지 측정한다.

간극을 규정하기 위해 저자들은 6범주 정보 분류 체계(문제 진술, 원하는 동작, 동기부여, 환경 정보, 재현 단계, 그 외)와 4차원 문체 체계(문법적 정합성, 명령 강도, 전문성 수준, 형식성)를 정의하고, 이를 SWE-chat의 실제 사용자 프롬프트와 SWE-bench Verified·Pro의 문제 진술에 각각 적용한다. 문제 진술만 있거나 추가 맥락이 거의 없는 요청은 실제 프롬프트의 88%를 차지하지만 벤치마크 문제에서는 7%에 불과하고, 실제 프롬프트의 87%는 비격식 문체인 반면 벤치마크 문제의 94%는 격식 문체다.

이 관찰을 바탕으로 저자들은 SWE-bench Verified·Pro에서 파생한 381개 다변종 태스크 패밀리, RealSWE를 제안한다. 한 패밀리 안의 변종들은 동일한 기반 태스크와 동일한 정답 패치를 공유하고 정보 구성과 문체만 다르다. 정답이 고정되어 있으므로 해결률의 변화는 태스크 난이도가 아니라 입력 형식에 귀속된다 — 에이전트 성능을 성분 분해(compositional)해서 보는 설계다.

7개 최신 LLM을 RealSWE로 평가한 결과, 현실적 입력은 해결률을 평균 6.4%p 낮추고 모델 순위를 바꿀 수 있다. 통제 분석에서는 원하는 동작(Desired Behavior)과 동기(Motivation)를 포함하는 것이 성능에 유의미한 영향을 주는 반면, 환경 정보와 재현 단계는 측정 가능한 이득 없이 토큰만 추가하는 것으로 나타났다. 문체의 효과는 작고 모델에 의존적이다.

## 핵심 내용

- 벤치마크 태스크는 실제 요청을 대표하지 못한다. 문제 진술만 담은 요청이 실제 프롬프트의 88%인 반면 벤치마크 문제는 7%에 불과하고, 실제 프롬프트는 87%가 비격식인 반면 벤치마크 문제는 94%가 격식 문체다.
- RealSWE는 SWE-bench Verified·Pro에서 파생한 381개 다변종 태스크 패밀리로, 변종들은 기반 태스크와 정답 패치를 공유하고 정보 구성과 문체만 다르다.
- 현실적 입력은 평균 해결률을 6.4%p 낮추고 모델 순위를 바꿀 수 있다 — 이 벤치마크의 존재 이유다.
- 원하는 동작과 동기를 포함하면 성능에 유의미한 영향이 있고, 환경 정보와 재현 단계는 측정 가능한 이득 없이 토큰만 추가한다(재현 단계가 여기 포함된다는 점이 실용적 함의를 만든다).
- 문체(형식성)의 효과는 작고 모델에 의존적이다. 비격식 문체라는 사실 자체가 큰 문제는 아니다.

## 상세

6범주 정보 분류 체계와 4차원 문체 체계를 SWE-chat 실제 사용자 프롬프트와 SWE-bench Verified·Pro 문제 진술에 적용해 비교했다.

| 축 | 실제 사용자 프롬프트 | 벤치마크 문제 |
|---|---|---|
| 문제 진술만(맥락 없음 또는 최소) | 88% | 7% |
| 비격식 문체 | 87% | 4% |
| 격식 문체 | — | 94% |

방법: RealSWE 패밀리마다 하나의 기반 태스크와 하나의 정답 패치를 공유하고, 이를 여러 "어떻게 요청할 것인가" 변종으로 확장한다. 그래서 해결률 변화를 정보 부족 탓과 문체 탓으로 분리할 수 있다. 7개 최신 LLM 평가에서 현실적 입력으로 인한 평균 하락은 6.4%p였고 순위가 바뀔 수 있었다. 원하는 동작과 동기를 포함하면 유의미한 효과가 있었고, 환경 정보와 재현 단계는 측정 가능한 이득 없이 토큰만 추가했다. 문체 효과는 작고 모델에 의존적이었다.

실용적 결론은 이렇다. 원하는 동작과 그 동기를 명시적으로 말하는 것 — 실제 프롬프트 대다수가 누락하는 바로 그 정보 — 이 모델의 소프트웨어 엔지니어링 성능을 뚜렷하게 높인다. 에이전트를 만들 때는 입력을 정돈된 이슈처럼 가정하지 말고, 프롬프트를 설계할 때는 환경 정보와 재현 단계를 성실히 채워 넣어도 측정 가능한 이득이 없다는 점을 기억하고, 평가할 때는 실제 워크로드와 동떨어진 입력 분포로 평가하면 에이전트가 실제로 더 나쁘다는 잘못된 결론에 이를 수 있다.
