# LuthorSQL: 느린 LLM 에이전트의 시스템 1로서의 단일 패스 텍스트-SQL 모델

**원문**: [arXiv:2611.17780](https://arxiv.org/abs/2611.17780) · **게시일**: 2026-11-13
**저자**: Ibrahim Memon, Armin Karamzade, M. Hanif Jhaveri, Roy Fox

## 개요

도구로 데이터베이스를 조회하는 프론티어 LLM 에이전트는 가장 정확한 텍스트-SQL 시스템에 속하지만, 호스팅 모델에 질의마다 호출하는 방식은 느리고 비용이 크며 조직의 민감한 질의를 외부 API에 노출한다. 저자들은 클로드 Opus 5.5 에이전트가 하루 1만 건을 처리하면 정가 기준 연간 7만 달러가 넘게 든다고 계산한다. 질문은 이럴 때다. 조직이 이미 보유한 로컬 하드웨어가 정확도를 해치지 않고 이 부담을 얼마나 떠안을 수 있는가.

LuthorSQL은 비자기회귀 7B 텍스트-SQL 모델로, 더 느린 LLM 에이전트(시스템 2) 앞에서 빠른 시스템 1 게이트 역할을 하고 불확실할 때만 질의를 에스컬레이션한다. 단일 순전파로 유계 문법의 질의 계획에 대한 슬롯 점수를 예측하고, 후보 계획을 최대 32개 컴파일해 실행한 뒤, 학습된 검증기가 답을 고른다. 설계는 카너먼식 시스템 1/시스템 2 구도를 따른다. 값싸고 빠른 로컬 처리가 일상을 담당하고, 비싼 에이전트가 어렵고 불확실한 꼬리를 담당한다.

단독으로 LuthorSQL은 GPU 한 장에서 질문당 0.84초로 BIRD 비공개 테스트 집합에서 68.03% 실행 정확도를 낸다. Opus 학습 컷오프 이후 공개된 데이터베이스의 227개 질문에 대한 사전등록 확신 캐스케이드에서 Claude Opus 5.5와 결합하면 전체 질문의 절반 가까이를 로컬로 답하고 같은 정확도에서 API 비용을 33.3% 줄인다.

## 핵심 내용

- 단독 정확도·지연: BIRD 비공개 테스트에서 68.03% 실행 정확도, GPU 한 장 기준 질문당 0.84초. 8비트 양자화 가중치로 9GB 안에서 정확도를 유지한다.
- 이식성: Snowflake, BigQuery, MySQL, PostgreSQL, DuckDB로 네이티브 SQLite 정확도의 3.1포인트 이내에서 제로샷 전이된다.
- 캐스케이드 경제성: 사전등록된 확신 캐스케이드(컷오프 후 질문 227개)에서 LuthorSQL은 전체 질문의 절반 가까이를 로컬로 답하고 같은 정확도에서 API 비용을 33.3% 절감한다.
- 구조: 유계 질의 계획 문법 위의 슬롯 점수를 한 번의 순전파로 예측하고, 질문당 최대 32개 후보 계획을 컴파일·실행하며, 학습된 검증기가 최종 답을 고른다.
- 오염 탐지가 대표 결과다. 스키마를 보지 않고도 Claude Opus 5.5가 공개 벤치마크 정답 쿼리의 48–92%를 그대로 재현한다. 그럼에도 도구 지원 정확도는 이름을 바꾼 스키마에서 유지되고 컷오프 후 데이터베이스에서 95.6–97.4%에 달해, 캐스케이드를 컷오프 후 데이터로 평가한 논문의 선택을 뒷받침한다.

## 상세

유계 문법과 슬롯 점수는 자유 형식 SQL 디코딩을 제약되고 검증 가능한 계획 생성으로 바꾸고, 검증기는 실행된 후보를 보정된 확신 신호로 바꿔 에스컬레이션 게이트에 넘긴다. 배포본에는 부수 파일(decision_ids.json, reserved_ids.json)이 동반된다. 사전등록 평가 프로토콜과 오염 분석이 이 연구를 벤치마크 전용 주장과 구별한다. 캐스케이드 질문 집합과 이름 변경 스키마 강건성 검사 모두 호스팅 에이전트가 암기했을 수 있는 것을 전제로 설계됐다. 코드와 데이터는 초록에서 링크된다. 출처 비고: 작성 시점에 arXiv HTML v1을 구할 수 없었고(404) ar5iv는 초록 랜딩 내용만 제공해, 이 요약은 arXiv 초록 페이지에서 작성했다(2611-05843·2611-08379 선례). 위 수치는 모두 초록이 밝힌 값이다. 이 문서는 HF 등록 v1(2026년 11월 13일)을 다룬다.
