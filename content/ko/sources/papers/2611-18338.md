# MEM-SQL: 메모리로 강화된 Text-to-SQL

**원문**: [arXiv:2611.18338](https://arxiv.org/abs/2611.18338) · **게시일**: 2026-11-13
**저자**: Xiaoqi Wang, Wenqi Pei, Shizheng Hou, Yilai Liu, Han Chen, Boyan Li, Yuyu Luo, Hongyang Du

## 개요

Text-to-SQL은 자연어 질문을 SQL 쿼리로 바꾸는 작업이다. 벤치마크는 Spider의 교차 도메인 일반화에서 BIRD의 데이터베이스 값 의존 질문, 그리고 1,000개가 넘는 컬럼을 가진 기업용 스키마를 다루는 Spider 2.0까지 확장됐다. 그러나 이런 벤치마크들은 질문을 하나하나 독립적으로 채점하는데, 실제 사용자는 같은 데이터베이스를 반복해서 조회하는 경우가 많다. 이전 요청에서 검증을 통과한 쿼리가 새 질문에 필요한 조인이나 중간 계산을 이미 담고 있을 수 있고, 큰 데이터베이스에서 그 로직을 매번 스키마부터 다시 만드는 비용은 크다. 게다가 쿼리의 일부 로직이 새 요청과 맞지 않아도 실행 자체는 성공할 수 있어, 단순 실행 성공만으로는 올바른 재활용을 판단하기 어렵다.

홍콩대학교 NICE Lab, 싱가포르국립대학교, 홍콩과기대학교 광저우 캠퍼스의 공동 연구팀은 이 문제를 두 갈래로 공략한다. 첫째는 HARE(History-AwaRe Text-to-SQL BEnchmark)다. Spider, BIRD, Spider 2.0, BEAVER에서 모은 823개 검증 쿼리로 1,600개 요청을 만들고, 각 요청이 기록에서 무엇을 유지하는지 어떤 편집을 요구하는지 표시한다. 재사용 유형은 질문만 다시 표현하는 재구성(rephrase)부터 조인 경로나 컬럼 매핑만 공유하는 경우까지 여섯 개 단일 범주와 여섯 개 복합 범주로 나뉜다. 덕분에 쿼리 전체를 고치는 적응과 부분 증거를 조립하는 작업을 구분해 평가할 수 있다.

둘째가 제안 시스템 MEM-SQL이다. 데이터베이스별로 고정된 메모리를 세 층으로 유지한다. 타입이 지정된 슬롯(slot)을 갖춘 쿼리 전체 템플릿, 재사용 가능한 SELECT 블록 단위의 컴포넌트, 도메인 용어를 컬럼과 조인 관계로 연결하는 스키마 개념이 그것이다. 검색은 요구 사항별 커버리지 게이트(coverage gate)를 통과해야 해당 층이 증거에 참여하고, 온디맨드 스키마 링킹(On-demand Schema Linking, OSL)은 어떤 층도 기준을 충족하지 못하거나 생성기가 검색된 증거가 부족하다고 판단할 때만 원본 스키마 정보를 조회한다.

여섯 개 언어 모델을 대상으로 한 HARE 평가에서 평균 실행 정확도(execution accuracy, EX)는 기록 없이 생성하는 Direct Generation의 37.1%에서 MEM-SQL의 50.0%로 올라갔고, 입력 토큰은 76.6%, 지연 시간은 68.8% 줄었다. 요청의 95.4%는 메모리만으로 처리된다.

## 핵심 내용

- HARE는 Spider, BIRD, Spider 2.0, BEAVER의 823개 검증 쿼리로 1,600개 요청을 구성한다. 단일 범주 요청 1,300개, 두 범주를 결합한 복합 요청 300개(복합 범주당 50개)이며, 재구성, 파라미터 변경, 컴포넌트 파라미터 변경, 구조 변경, 공유 조인, 공유 개념의 여섯 가지 단일 재사용 범주를 둔다.
- 세 층 메모리의 구성: 템플릿은 리터럴, 정렬 방향, LIMIT/OFFSET 절, 집계, 윈도우 함수, 그룹화 키를 타입이 있는 슬롯으로 바꾼 쿼리 전체 형판이고, 컴포넌트는 SELECT 블록의 FROM·JOIN·절 구조를 그대로 유지하며, 스키마 개념은 의미 역할, 컬럼 매핑, 조인 키를 기록한다. 새 항목은 기존 항목과 설명 코사인 유사도가 0.9 이상이고 저장된 SQL이나 스키마 매핑이 동등할 때만 병합된다.
- 커버리지 게이트 선택: 질문을 층별 검색 원자(retrieval atom)로 분해해 각각에 독립적인 검색 예산을 준다. 한 층은 가장 약하게 커버된 원자마저 층 임계값을 넘을 때만 받아들여진다. 한 원자의 강한 매칭이 다른 요구 사항의 빈틈을 가릴 수 없다.
- 비용 절감의 원천은 스키마 접근 회피다. MEM-SQL은 평균적으로 요청의 95.4%를 메모리만으로 처리하고 4.3%만 상위 경로로 넘어간다(커버리지 게이트 통한 1.1%, 생성기 판단 통한 3.2%).
- 주요 결과: 평균 실행 정확도는 Direct Generation의 37.1% 대비 50.0%(+12.9포인트)이고, 여섯 백본(GLM5.3-Flash, Gemini4-Argon, GPT6-Luna, Qwen3.8-27B, Qwen3.5-9B, Granite4.2-8B) 평균으로 입력 토큰은 76.6%, 지연은 68.8% 감소했다. 무조건 스키마 링킹을 쓰는 메모리 베이스라인 DAIL-SQL, A-MEM, BIRD-History를 모든 백본에서 앞선다. 예컨대 GLM5.3-Flash에서 EX 54.2%, Gemini4-Argon에서 57.5%다.
- 소거 실험: 템플릿 층을 빼면 정확도 타격이 가장 크다(평균 5.3 EX포인트)이며 모든 백본에서 토큰이 늘어난다. 컴포넌트 제거는 복합 요청에서 3.7포인트, 단일 범주에서는 1.1포인트의 손실을 낸다. 스키마 개념은 정확도에는 거의 영향이 없지만 여섯 백본 모두에서 토큰을 늘린다. 240개 보정 질문에서 검색 원자는 마이크로 재현율을 56.67%에서 94.58%로 올리면서 플랫 검색보다 질문당 항목 수를 37.7% 줄인다.
- 다중 소스 결합이 병목이다. 여러 검증 쿼리를 재활용하는 요청에서 정확도는 56.7%에서 29.7%로 떨어지며, 모든 백본에서 최소 21.7 EX포인트 낮다. 구조 변경의 경우 다중 소스 요청의 90.8%에서 모든 소스를 검색하는데도 정확도는 9.9%에 그쳐, 실패 원인은 검색이 아니라 생성 단계다.
- OSL 전이성: 세 가지 다른 메모리 설계에 OSL을 적용하면 어떤 설계에서든 입력 토큰이 최소 60%, 지연이 최소 34% 줄어든다. 다만 정확도 이득은 검색 완결성에 좌우된다. 재현율이 완전한 요청에서는 DAIL-SQL +6.0포인트, A-MEM +5.1포인트를 얻지만 BIRD-History는 여섯 백본 중 다섯에서 정확도가 떨어진다.

## 상세

HARE 구축은 새 요청이 유지해야 할 증거를 담은 리드(lead) 쿼리를 고르는 것에서 시작해, 같은 데이터베이스에서 동반 쿼리를 더한다. 구조 변경과 공유 조인은 리드와 테이블을 공유하는 동반 쿼리를 최대 두 개까지 허용하고 복합 요청은 최대 여섯 개 쿼리를 쓸 수 있다. 날짜, 임계값, 랭킹, 측정값, 그룹화, 조인 경로에 대한 허용 편집을 BR0~BR17 비즈니스 규칙으로 제한한 뒤, GLM5.3-Flash가 요청당 세 개의 후보를 생성한다. 후보는 실행에 성공하고 NULL이 아닌 행을 최소 하나 반환해야 하며, Claude Opus 5.5가 질문-SQL 일치, 도메인 지식과의 일관성, 범주 제약 준수를 검토하고 실패한 후보를 최대 세 번까지 수리한다.

추론 단계에서 MEM-SQL은 질문을 층별 검색 원자로 분해하고, 각 원자에 대해 코사인 유사도로 가장 가까운 항목을 찾은 뒤 기준을 통과한 층들의 증거를 합친다. 모든 층이 커버리지 게이트를 통과하지 못하면 즉시 스키마 링킹 경로로 넘어가고, 그 외에는 메모리만으로 생성을 먼저 시도한 뒤 모델이 증거 부족을 선언할 때에만 스키마를 보충한다. 생성된 쿼리는 데이터베이스 드라이런(dry run)으로 검사하고 실패하면 수리를 시도한다.

오류 분석에 따르면 메모리 경로의 오답에서 집계 오류가 여전히 가장 큰 클래스다(MEM-SQL 36.1%, 가장 강한 베이스라인 A-MEM 38.2%). 반면 테이블 오류는 31.4%에서 21.4%로 줄었고(BEAVER에서는 55.0%에서 33.7%), 스키마 접근이 없으면 실행 실패가 A-MEM의 3.2% 대비 10.8%로 늘어난다. 소스 벤치마크별로는 조인이 많은 BEAVER(+8.6 EX포인트)와 BIRD(+3.0포인트)에서 이득이 집중되고, 공유 개념과 구조 변경이 지배적인 Spider(−0.6포인트)와 Spider 2.0(−0.7포인트)에서는 소폭 뒤진다. 저자들은 세 가지 한계를 밝힌다. HARE는 스키마 드리프트(예: 회계연도 시작 월의 변경)를 모델링하지 않았고, MEM-SQL은 정적 메모리로 평가되었으며, 실행 정확도는 반올림처럼 형식만 다른 답을 거절하는 동시에 올바른 행을 잘못된 이유로 반환하는 SQL은 잡아내지 못한다.
