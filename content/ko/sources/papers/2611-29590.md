# KernelShift: 진화하는 하드웨어에 걸친 커널 최적화 벤치마크

**Source**: [arXiv:2611.29590](https://arxiv.org/abs/2611.29590) · **게시일**: 2026-11-22 (v1)
**Authors**: Shuaiwei Huang, Weihua Du, Allen Wu, Ivan Fox, Manupa Karunaratne, Yiming Yang, Sean Welleck

## 개요

AI 하드웨어는 진화하고, 그에 따라 고성능 코드를 구현하는 데 필요한 최적화 전략도 바뀐다. CPU 커널에서는 사용 가능한 아키텍처 확장 집합이 핵심 변수다. KernelShift는 코딩 에이전트가 새롭고 생소한 확장을 얼마나 잘 활용하는지 연구한다. 파이프라인이자 환경인 KernelShift는 에이전트 보조 + 인간 검증 구축 파이프라인으로 실제 개발 중인 저장소(ncnn, llama.cpp, Arm SIMD Loops, KleidiAI)를 99개 벤치마크 커널로 바꾼다. 실제 모델 실행에서 얻은 추론 워크로드를 포함한다. 환경은 실제 타깃 하드웨어(Graviton4, Apple M4)에서 피드백을 주며 통일된 인터페이스로 에이전트를 실행하고,측정 프로토콜과 무결성/정확성 검사를 갖추고, 라이브러리와 프로세서가 진화함에 따라 새 커널과 하드웨어 설정을 추가할 수 있다.

실험은 독점 및 오픈 가중치 모델을 Neon, SVE, SVE2, SME2라는 명령어 사다리에서 평가하며, 고정 머신 사다리와 세대 간 매칭 태스크 쌍에서 Speedup@40(40회 도구 호출 예산 후 experts 참조 대비 속도 향상)을 사용한다.

## 핵심 내용

- 기존 확장: 평가된 모든 시스템이 4개 저장소 모두에서 -O3 자동 벡터화 참조(에이전트의 시작 코드이기도 함)보다 2.4-19.8배 빠르다. SVE에서 최고 시스템은 ncnn 참조의 2.74배, llama.cpp 1.95배, SIMD Loops 1.56배에 달한다. -O3+SVE조차 experts 참조의 최대 0.47배에 그친다. KleidiAI SVE 커널 6개에서는 어떤 시스템도 Arm의 수작업 벤더 커널을 기하평균에서 이기지 못한다(최고는 Claude Code/Claude Opus 4.8의 0.70배).
- 진화하는 하드웨어 적응: 점진적 확장(SVE→SVE2, SIMD Loops 8개 커널)은 Almost 비용이 없다(After/Before 비율 전 모델 0.94-1.05; Graviton4 고정 머신 사다리에서 Neon 1.105배/SVE2 1.101배). SME2의 변화(스트리밍 모드 + ZA 행렬 타일, 프로그래밍 모델 자체의 변화)는 훨씬 어렵다. SME2/SVE 비율이 DeepSeek-V4-Pro, GLM-5.3, GPT-5.6-luna에서 0.42/0.46/0.41로 하락하지만 Claude 모델은 유지된다(1.29/1.03). Apple M4의 KleidiAI SME2 커널 20개에서 스트리밍 SVE를 노출하면 Speedup@40이 0.141(Neon만)에서 0.059로 추락하고, 전체 SME2는 0.085로 부분 회복된다. 컴파일 실패율은 13%→20%→24%로 오른다. 최종 SME2 커널 중 ZA outer product를 성공적으로 쓴 것은 없다(ZA 코드는 두 번만 작성됐고 둘 다 실패). 사례 gemm_bf16_n512_k512: Opus 4.8은 스트리밍 MOPA/ZA 누적을 써 experts의 0.94배를 달성했지만 Sonnet 4.6/DeepSeek-V4-Pro는 구 벡터 스타일에 머물러 0.06배/0.05배에 그쳤다. 18개 최종 SME2 해 중 ZA 타일을 주로 쓴 것은 Opus(15개)뿐이었다.
- experts 여유가 에이전트 이득을 결정: 79개 SVE 커널에서 experts 참조가 스칼라 대비 강할수록 중앙값 Speedup@40이 떨어진다(Spearman rho = -0.69, llama.cpp 내에서는 -0.75). llama.cpp RMSNorm은 참조가 스칼라의 1.3배에 불과해 에이전트가 중앙값 6.0배로 이기지만, q4_K_M GEMM/MoE는 experts가 이미 스칼라의 25-29배라 에이전트는 0.57-0.69배에 머문다.
- 테스트 타임 스케일링: 대부분의 진전은 40회 도구 호출 내에 이뤄진다. Claude Sonnet 4.6은 100회에서 40회보다 23-25% 더 높다(대부분 40-60회 사이에 소수 커널이 구조적으로 재작성되기 때문). 60회 이후 곡선은거의 수렴한다.
- 절제(nanobot + GPT-5.6-luna): SIMD intrinsics 사용을 금지하면 1.074→0.300으로 붕괴(에이전트 이득의 대부분은 intrinsics를 올바르게 쓰는 데서 온다). Arm 문서는 SVE에서 도움 안 되지만 SME2에서는 0.083→0.130으로 올라가는데, 이는 더 나은 SME2 코드가 아니라 컴파일 오류 감소(102→54)와 Neon 폴백 증가 때문. SME2 함정을 실패 예와 함께 프롬프트에 넣으면 SME2 Speedup@40이 두 배(0.083→0.167)가 되지만 20개 중 5개는 나빠진다. 크로스 커널 노트패드와 디스어셈블 도구는 별 기여가 없다(에이전트는거의 디스어셈블하지 않지만 전문가는 고급 커널 설계 시 자주 쓴다).
- 종단간: 에이전트가 최적화한 셰이프 특화 양자화 GEMM 커널( Qwen3.5-4B용 11개, Llama-3.1-8B-Instruct Q4_K_M용 7개, Claude Code + Fable 5.1)을 Graviton4에서 llama.cpp로 서빙하면 원본 llama.cpp의 i8mm 패스트 패스 대비 1-16 스레드에서 prefill 1.30-1.57배, decode 1.04-1.10배, perplexity 동일. 18개 커널 모두 i8mm과 셰이프별 타일링/레이아웃/프리페치를 사용한다. 이는 experts 라이브러리보다 배포 시점 특화의 잠재력을 보여준다.

## 세부 사항

2장은 태스크 구축(커널+참조+워크로드 구축, 검증 스크립트, 인간 검증, 정확성 기준, 부록 B의 인간의 수고 기록), 벤치마크 구성(부록 A: 소스별 구성, 태스크 집합 — 32커널 부분집합, 세대 간 SIMD Loops, 테스트 타임 스케일링 부분집합, 종단간 커널, 커널 인벤토리 포함 기준), 평가 환경(부록 C: 하드웨어 인 더 루프 타깃 — 머신, 명령어 사다리, 통일 에이전트 인터페이스/하네스/프롬프트,측정 프로토콜과 무결성, 부록 H 오염 진술)을 다룬다. 3장은 모델/하네스, 태스크 집합, 하드웨어/예산, 지표(Speedup@t, 하드웨어 피크 대비 비율은 부록 D)를 설명한다. 4장은 위 결과를 보고한다. 부록 E는 사례 연구(종단간 LLM 서빙 레짐, SME2 학습 궤적), 부록 F 타깃별 intrinsics 사용, 부록 G M4의 SME2 커널 SIMD 클래스를 다룬다.
