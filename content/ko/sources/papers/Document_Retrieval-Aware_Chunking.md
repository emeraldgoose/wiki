# Document Retrieval-Aware Chunking



**arXiv**: [2609.24220](https://arxiv.org/abs/2609.24220) | **HuggingFace**: [papers/2609.24220](https://huggingface.co/papers/2609.24220) | **발행**: 2026-09-21 | **소속**: Yellow.ai AI Research Team | **제출**: Uday Allu | **추천**: 51

**저자**: Abhivanth Sivaprakash, Pratik Singh, Aman Manocha, Uday Allu

## 초록

기업 지식 베이스 대상 RAG 시스템은 PDF, Word, 프레젠테이션, 스캔 등 시각 레이아웃과 다단 구성, 밀집 표 안에 내용이 갇힌 이종 문서 형식을 섭취해야 한다. 규칙 기반 추출과 OCR은 읽기 순서를 깨고 표를 평탄화하며见出し 계층을 잃고, 추출 텍스트 위의 완전 에이전틱 청킹은 높은 토큰 비용과 환각 위험을 수반한다. 본 논문은 Web Retrieval-Aware Chunking (W-RAC) 프레임워크를 임의 문서 형식으로 확장한 Document Retrieval-Aware Chunking (D-RAC)을 제시한다. D-RAC은 사실상 모든 형식이 충실하고 결정적인 PDF 렌더링을 갖는다는 점을 이용해 입력 문서를 먼저 PDF로 정규화한다. 이어서 단일 멀티모달 LLM 패스가 렌더링된 페이지를 검색 최적화 Markdown으로 변환한다 — 표는 자족적 서술문으로 재작성하고见出し 계층은 보존한다 — 이후 청킹은 W-RAC과 동일하게 진행된다: ID로 주소 지정 가능한 단위로 결정적 파싱한 뒤 텍스트가 아닌 식별자 위에서 경량 LLM 기반 청크 계획을 수행한다. 청킹 중 원문 텍스트를 재생성하지 않으므로 W-RAC의 비용·결정성·관측 가능성 이점을 유지하면서 렌더링 가능한 모든 형식을 1급 입력으로 풀어준다. 5개 기업 도메인에 걸친 RAG-Multi-Corpus 벤치마크의 236개 문서·795페이지 PDF 부분집합에서 D-RAC은 전체 코퍼스를 72분 만에 오류 없이 변환·청킹하여 1,748개의 검색-ready 청크를 생성한다. 프론티어 LLM 기반 에이전틱 청킹 대비 청킹 단계 출력 토큰을 95.7% 줄이고, 청킹 비용을 77.8% (GPT-4.1 요금) ~ 85.6% (Gemini 2.5 Pro 요금) 절감하며, 청킹 시간을 75% 단축한다. 500페이지 이상 문서에도 선형 확장된다.

## 배경과 문제 설정

기업 RAG에서 검색 품질은 청킹 품질이 결정한다. 저자들의 선행 시스템 W-RAC은 청킹을 텍스트 생성이 아닌 의미 계획 문제로 재정의했다: 웹 페이지를 구조화된 ID 주소 지정 단위로 결정적 파싱한 뒤 LLM이 식별자 순서 리스트만으로 청크 경계를 계획한다. 출력 토큰 84.6% 감소, 지연 약 60% 감소, 비용 51.7% 절감과 함께 검색 정밀도까지 올렸다. 그러나 W-RAC은 복원 가능한 구조(HTML→Markdown 변환 가능)를 가정하는데, 기업 PDF에는 그런 것이 없다.

PDF는 의미 형식이 아니라 표현 형식이며, 기존 섭취 경로는 각자 뚜렷하게 실패한다:

- **규칙 기반 추출** (PyMuPDF, pdfminer, pdfplumber): 빠르고 무료지만 다단 레이아웃에서 조각이 뒤섞이고 머리말/바닥글이 본문에 끼며 하이픈 아티팩트가 생기고, 표는 위치 모호한 토큰으로 붕괴하며见出し 계층은 글꼴 크기 휴리스틱으로만 남는다.
- **레이아웃 분석·OCR 파이프라인** (LayoutLM, LayoutLMv2, Docling): 영역과 읽기 순서를 복원하지만 전용 배포가 필요하고, 보험 브로슈어·제품 원페이저 같은 비정형 마케팅 레이아웃에 깨지며, 표를 여전히 그리드로 내놓는다 — 행·열 맥락이 떨어진 셀은 임베딩 노이즈가 된다.
- **추출 텍스트 위 에이전틱 청킹**: LLM이 추출 손상 복구와 전문 재생성을 동시에 떠맡아 출력 토큰(입력 토큰의 약 4배 가격), 지연, 환각 표면이 모두 최대가 된다.
- **비전 유도 청킹**: 페이지 이미지를 읽는 멀티모달 모델이 추출 파이프라인을 이기지만, 이해와 청크 생성에 대형 비전 모델을 쓰면 에이전틱 청킹의 출력 토큰 비용이 그대로 남는다.

논문의 질문은 단순하다: 렌더링된 페이지에서 멀티모달 1회 패스로 W-RAC 기계장치 전체가 그대로 돌아갈 만큼의 구조를 복원할 수 있는가? 답은 긍정적이다.

## 방법론

D-RAC은 W-RAC 원칙(청킹 중 텍스트 재생성 금지, 비용 효율, 결정성·관측 가능성)을 계승하고 PDF 정규화를 통한 형식 불가지론, 단일 변환 패스, 검색 인식 정규화를 추가한다. 4단계 중 LLM을 쓰는 것은 2단계와 4단계뿐이다.

**1단계 — PDF 정규화와 페이지 렌더링 (결정적).** 비-PDF 입력은 범용 도구로 PDF 변환한다 (오피스 형식은 headless LibreOffice, HTML은 print-to-PDF, 스캔은 이미지 래핑). LLM 없음, 형식별 파서 없음. 각 페이지를 200 DPI PNG로 렌더링하고 한 변이 1,568 px을 넘지 않게 축소한다 (비전 인코더 입력 한계 대응). 비용은 문서당 1–7초로 추론 대비 무시 가능하다.

**2단계 — 멀티모달 Markdown 변환 (LLM 1회).** 렌더링 페이지를 5페이지씩 묶어 멀티모달 LLM에 보낸다 (평가: AWS Bedrock 경유 Gemma-3 27B·12B, temperature 0.1, 배치당 최대 출력 8,192 토큰, 5배치 병렬). 검색 인식 프롬프트 규칙:

- verbatim 보존: 요약·생략 금지.
- 표→서술 정규화: Markdown 표 문법 금지. 모든 행이 열见出し를 맥락으로 담은 자족적 한 문장이 된다. 서로 다른 행을 절대 병합하지 않는다 (Policy Term 16/PPT 8 행과 20/10 행은 두 문장으로 유지, "16년 또는 20년" 금지).
- 이미지 억제: 로고·차트·장식 그래픽은 캡션 대신 통째로 제외하여 환각 캡션이 인덱스를 오염시키지 않는다.
- 명시적 계층:见出し를 `#`/`##`/`###`로 재구성하여 PDF 추출이 파괴한 구조 신호를 복원한다.
- 페이지 출처: 페이지마다 `<!-- Page N -->` HTML 주석으로 추적성을 남긴다 (파싱에 영향 없음).

결정적 후처리로 코드 펜스와 이미지 참조를 제거하고, 빠져나온 표 문법은 규칙 기반 표→서술 폴백으로 변환한다. 실패한 페이지 범위는 문서 전체를 중단시키지 않고 인라인 오류 마커로 기록한다.

**3단계 — 결정적 파싱과 섹셔닝.** 변환된 Markdown을 W-RAC과 동일하게 ID 주소 지정 요소로 파싱한다:见出し (`h1`, `h2`, …)와 내용 블록 (`p1`, `p2`, …). 계획 예산(호출당 60 요소) 초과 시 재귀 분할이见出し 경계에서 자른다 — 가장 거친见出し 레벨 우선, 필요할 때만 더 세밀하게,见出し 없는 구간은 고정 크기 폴백 — 인접한 작은 섹션은 병합한다. 각 섹션은 부모见出し 체인을 함께 전달받아 (수십 입력 토큰) 플래너가 내용 재전송 없이 문서 계층상 위치를 안다.

**4단계 — LLM 청크 계획과 재구성.** 플래너는 요소 ID, 200–400자 미리보기, 계층 메타데이터만 보고 청크 계획을 ID 순서 리스트로 반환한다 (예: `[["h1","h2","p1","p2"],["h1","h3","p3","p4","p5"]]`). 단일 주제 중심으로 내용 블록 3–8개를 묶고, 맥락용见出し ID를 재사용하며, 모든 내용 ID를 정확히 한 번씩 커버한다. 커버리지는 프로그래밍 방식으로 검증하고, 누락 ID는 섹션见出し와 함께 폴백 청크로 모아 무손실 섭취를 보장한다. 섹션별 병렬 계획. 최종 청크는 변환 텍스트를 verbatim 매핑으로 로컬 재구성하고, 전체 조상见出し 체인과 breadcrumb (예: *Plan Overview > Eligibility > Age Limits*)를 접두사로 붙인 뒤 임베딩·인덱싱한다.

변환된 Markdown과 요소 ID는 영속 아티팩트이므로, 검색 정책 변경에 따른 재청킹은 ID 레벨 재계획 호출만으로 끝나고 재변환·재OCR 비용을 다시 내지 않는다.

## 결과

RAG-Multi-Corpus의 236개 문서·795페이지 PDF 부분집합 (5개 가상 기업 버티컬: 자동차, 학술, 클라우드 서비스, 기업 기술, 은행. 제품 시트, FAQ, 정책·절차 문서, 부품 카탈로그, 서비스 가이드)과 503페이지 금융 투자설명서 스트레스 테스트로 평가했다. 임베딩은 Titan Text Embeddings V2 (1,024차원), 조직별 인덱스 내 코사인 top-K 검색. 관련성 판정은 supporting fact의 내용어 60% 이상이 청크에 포함될 때.

- **처리량**: 전체 코퍼스 변환 누적 3,758초 (62.6분, 청킹 포함 wall clock 71.7분), 236개 문서 오류 0건. 페이지당 비용은全部 도메인에서 3.9–5.5초로 안정적 (내용 복잡도가 아니라 파일당 API 지연이 지배). 503페이지 스트레스 문서는 21.6분 (27B) / 13.4분 (12B)에 변환 — 선형 확장, 초선형 열화 없음.
- **계획 효율**: 전체 코퍼스 청크 계획 542초 (변환의 14%, 문서당 2.3초). 청크 크기는 하드 제한 없이 581–846자로 자연 수렴 (dense retriever sweet spot). 1,748개 청크, 청킹 오류 0건. 5,060요소 스트레스 문서는 95개 병렬 섹션 호출로 68.7초에 계획 (변환 시간의 약 5%).
- **검색 품질** (supporting-fact 정답付き 762개 쿼리, 7개 유형): PyMuPDF 추출 위 고정 크기 청킹 대비 명확히 우위 — Recall@6 0.717→0.798 (+11.3%), MRR 0.602→0.690 (+14.6%), NDCG@6 0.764→0.801. 가장 어려운 입력(렌더링 PDF 페이지)으로 작업했음에도 깨끗한 구조화 원문에서 만든 에이전틱 청킹 레퍼런스와 7개 전체 지표에서 동등 이상. 경계 민감 쿼리에서 이득 최대: 시간형 (Recall@6 0.85 vs 0.73), 비교형 (0.79 vs 0.72), 분석형 (0.61 vs 0.56). 불리언 쿼리는 에이전틱이 앞서는 유일한 유형. 조직 간 Recall@6 편차仅 0.022 (0.790–0.812).
- **비용**: 청킹 단계 출력 토큰 270,454→11,714 (−95.7%). GPT-4.1 요금 ($2/$8 per 1M 입출력) 기준 −77.8%, Gemini 2.5 Pro ($1.25/$10) 기준 −85.6%. 계획 입력은 미리보기 절단 덕분에 베이스라인보다 오히려 적다 (265k vs 326k 토큰). 실측 계획 시간 541.8초 vs 에이전틱 2,167.5초 (−75.0%). 100만 페이지 코퍼스로 외삽하면 전체 재인덱싱 1회가 약 $3,540→약 $785 (GPT-4.1). 11.7k 출력 토큰은 요소 테이블에 검증된 순수 ID 배열이라 청킹 중 서술 환각 표면이 0이다.

## 한계와 열린 질문

- 변환 품질이 모든 것을 상한짓는다: 멀티모달 1회 패스가 표·계층·읽기 순서를 맞혀야 하며, 본 논문은 Gemma-3 12B/27B로 평가했을 뿐 프로덕션 규모에서 프론티어 비전 모델의 페이지당 단가는 다루지 않는다.
- 이미지 억제는 의도적 정보 손실이다 — 차트·도표·스캔 도면은 인덱스에서 사라지므로, 도면 자체가 팩트인 코퍼스에는 캡셔닝·VQA 확장이 필요한데 파이프라인은 현재 그 비용을 거부한다.
- 검색 평가는 고정 판정기(내용어 60% 겹침, Titan 임베딩) 기준이라 절대 수치는 벤치마크 상대값이며, 불리언 쿼리 열위는 행-서술이 논리형보다 회상형 쿼리에 더 유리함을 시사한다.
- 벤치마크 입력이 전부 네이티브 PDF라 실험에서 1단계 정규화는 항등 함수였다. DOCX/PPTX/XLSX→PDF 충실도의 엔터프라이즈 규모 측정은 본 논문에 없다.

## 소프트웨어 엔지니어를 위한 시사점

- PDF 대상 RAG를 운영한다면 그대로 쓸 수 있는 청사진이다: PDF로 정규화 → 비전 1회 패스로 검색 최적화 Markdown 변환 (행 단위 표 서술, 명시적见出し, 출처 주석) → ID 위 청크 계획 → verbatim 재구성. 비싼 1회성 이해 단계와 저렴한 반복 청킹 단계를 분리하는 것이 핵심이며, 변환 Markdown+요소 ID를 영속화하면 청킹 정책 변경이 계획 전용 비용으로 끝난다.
- 비용 레버는 출력 토큰이다: 텍스트 재생성 대신 ID 배열을 내보내는 것이 청킹 비용 77–86%를 무너뜨리고 동시에 환각 표면을 제거한다. 원문을 재생성하는 에이전틱 파이프라인은 그 이유를 정당화해야 한다.
- 바로 훔칠 규칙 두 가지: 서로 다른 표 행을 선언적 문장으로 병합 금지 (조용한 정밀도 킬러), 모든 청크 앞에 조상见出し 체인을 붙여 임베딩에 제품·섹션 맥락을 싣기.
