# 에어갭은 있어도 데이터 공백은 없다: Bright Machines가 공장을 열지 않고 실시간 대시보드를 제공하는 방법

**원문**: [Databricks 블로그](https://www.databricks.com/blog/air-gapped-not-data-dark-how-bright-machines-gives-customers-live-factory-dashboards-without) · **게시일**: 2026-11-11

## 개요

Bright Machines는 고객 공장 안에서 소프트웨어로 정의된 자동화 우선 생산 라인을 구축하며, 그 공장들은 설계상 완전히 잠겨 있다. 인바운드 접근 없음, 최소한의 아웃바운드, 위험 무허용이다. 각 라인은 사내 MES, 고객 MES 연동, 작업자 화면, 로봇 워크플로 오케스트레이터, 조립 대시보드로 이어진 온프레미스 스택을 공장 클러스터의 PostgreSQL에 저장하고, KPI 대시보드, 재무 보고, 운영, 품질, 협력사 부품 품질, NCR 추적, 계보(genealogy), OEE, 시프트별 다운타임과 사이클 타임 분석을 움직인다. 문제는 조립 대시보드 앞에 선 고객들이 그 뒤의 데이터를 원했지만(스테이션별 수율, 사이클 타임 추이, 원인별 다운타임, 배치 계보) 공유 방법이 온프레미스에서 보고서를 다시 돌려 이메일로 보내는 것뿐이었고, 새 보고서 하나가 데이터 엔지니어링 시간을 몇 시간에서 며칠씩 잡아먹었다는 점이다.

첫 시도는 애플리케이션 이벤트에서 각 공장 데이터베이스의 클라우드 사본을 아홉 개의 느슨히 결합된 서비스로 재구축하는 것이었다. 공장 안에서는 동작했지만 그 밖에서는 실패했다. 스키마가 바뀌면 깨지고, 장애가 눈에 띄지 않았고, 실질적인 접근 통제도 없었다. 재설계는 파이프라인이 아니라 보안 모델에서 출발한다. 공장 엣지에서 Debezium 변경 데이터 캡처가 PostgreSQL 변경을 잡아 Apache Iceberg로 쓰고, 단일 감사 가능 아웃바운드 경로로 내보낸다. 엣지에서 버퍼링해 WAN 순단이 생산 데이터베이스 사고로 번지지 않게 한다. Databricks는 AWS Glue와의 Unity Catalog 페더레이션으로 Iceberg 테이블을 제자리에서 읽고, 공장에는 인바운드 포트가 하나도 열리지 않는다. 이제 하나의 거버넌스 플랫폼이 Bright Machines의 SSO 페더레이션과 연동된 역할 기반 AI/BI 대시보드와, Databricks 계정이 있는 고객에게 제로카피 거버넌스 실버 테이블을 공개하는 OpenSharing을 함께 제공한다. 브론즈 뷰, 실버 모델, 잡, 대시보드, 공유는 모두 하나의 Databricks Asset Bundle로 배포된다.

수치가 재설계의 논거다. 라인에서 커밋된 행은 정상 상태에서 1~2분 안에 Databricks에서 쿼리할 수 있고, 실버 모델과 대시보드는 10분마다 새로 고쳐진다. 하트비트 점검은 깨진 파이프라인을 며칠이 아닌 30분 이내에 잡아낸다. 개념 증명은 엔지니어 두 명으로 약 6주가 걸렸고, 첫 고객용 대시보드는 착수 약 2개월 만에 열렸다. 다음 로드맵은 이 거버넌스 데이터를 AI로 열어 주는 것이다. Genie 자연어 분석, Databricks Apps나 Agent Bricks를 통한 운영 전용 AI 에이전트(SQL을 쓰지 않는 라인 리더가 "이번 시프트에 4번 스테이션 다운타임이 왜 높았나"를 같은 거버넌스 실버 데이터에 근거해 묻게 하기), 그리고 공장 데이터를 미래 지향적 의사결정으로 바꾸는 예측 분석.

## 핵심 내용

- 기존 아키텍처는 애플리케이션 이벤트에서 클라우드 사본을 아홉 개 느슨 결합 서비스로 재구축해 공장 데이터를 공유했다. 스키마 변경에 취약하고, 장애가 조용히 지나가고, 접근 통제도 없었다.
- 새 엣지 경로는 최소이면서 감사 가능하다. Debezium CDC, 로컬 오브젝트 스토어, 동기화 구성요소 하나. Apache Iceberg 테이블을 단일 감사 가능 아웃바운드로 내보내고 공장 인바운드 포트는 0이다.
- Databricks는 데이터를 복사하지 않는다. Unity Catalog 페더레이션이 AWS Glue의 Iceberg 테이블을 제자리에서 읽으며, 아홉 서비스 파이프라인이 하나의 거버넌스 플랫폼으로 줄었다.
- 잠긴 사이트에서 데이터를 공유하는 다섯 가지 교훈. 이미 갖고 있는 보안 모델에서 출발한다. 먼저 하나의 외부 경로를 설계하고 그 뒤에 버퍼를 둔다. 포인터에 가드를 둔 자기 소유의 카탈로그 홉으로 테이블이 언제 앞으로 가는지 통제한다. 데이터를 한 번 만들고 나머지는 권한으로 해결한다. 행 수가 아니라 하트비트로 신선도를 단언한다.
- 하트비트 원칙이 중요한 이유는 의미 때문이다. 새 행이 없으면 라인이 쉬고 있는 것일 수 있지만, 하트비트가 없으면 파이프라인이 깨진 것이다.
- 신선도: 라인 커밋은 1~2분 안에 쿼리 가능, 실버 모델과 대시보드는 10분 주기. 진정한 실시간 뷰가 필요한 작업자는 온프레미스 조립 대시보드를 계속 쓴다.
- 포인터 가드가 있는 카탈로그 홉 덕분에 레이크하우스는 팀이 검증한 테이블 버전만 본다.
- 이식성: 엣지 동기화 대상, 교차 계정 복제, 카탈로그 홉만 AWS 종속이고 Databricks 쪽은 어느 클라우드에서나 동일하다.
- 배포도 통합됐다. 브론즈 뷰, 실버 모델, 잡, 대시보드, 공유가 단일 Databricks Asset Bundle에서 나온다.

## 세부 사항

- 에어갭 제약은 설계상 절대적이다. 인바운드 없음, 통제된 외부 경로 하나, 내부 접근도 제한하는 역할 기반 규칙.
- 고객 공유는 두 계층이다. SSO 페더레이션과 연동된 역할 기반 AI/BI 대시보드와, 고객의 Databricks 계정에 제로카피 거버넌스 실버 테이블을 공개하는 OpenSharing.
- 모니터링 변화의 본질은 도구가 아니라 의미다. 행 수 기반 신선도 점검은 쉬고 있는 라인과 깨진 파이프라인을 구분하지 못하므로, 팀은 하트비트로 신선도를 단언해 30분 이내에 파이프라인 장애를 잡는다.
- AI 로드맵은 같은 거버넌스 실버 데이터 위에 선다. Genie 자연어 분석, SQL을 쓰지 않는 작업자·품질 엔지니어·정비 기술자를 위한 운영 에이전트(Databricks Apps 또는 Agent Bricks), 공장 데이터를 예측으로 바꾸는 분석.
- 타임라인: 엔지니어 2명 개념 증명 약 6주, 착수 약 2개월 만에 첫 고객용 대시보드 서비스.
