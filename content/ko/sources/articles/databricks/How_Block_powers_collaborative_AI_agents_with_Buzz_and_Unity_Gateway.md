# 블록의 협업형 AI 에이전트: Buzz와 Unity Gateway

**원문**: [Databricks 블로그](https://www.databricks.com/blog/how-block-powers-collaborative-ai-agents-buzz-and-unity-gateway) · **게시일**: 2026-11-12

## 개요

AI 에이전트가 일상 업무의 일부가 되면서 블록의 팀들은 동료와 협업하는 바로 그 자리에서 에이전트와도 일하고 싶어 했다. Bradley Axen, Brandon Kvarda, Julia Powell, Kelly Albano가 소개하는 그 결과물이 Buzz다. 직원과 AI 에이전트가 채널·스레드·다이렉트 메시지를 공유하는 오픈소스 협업 공간으로, 사용자는 에이전트를 만들고 그 뒤에 놓일 모델이나 코딩 하네스를 선택해 동료와의 대화에 데려올 수 있다. AI 도구 사이를 오가는 대신 한 환경에서 여러 에이전트와 함께 일하는 방식이다. 직원이 코딩이나 분석 도움을 에이전트에 요청하면, 동료들이 같은 스레드에서 그 작업을 검토하고 정보를 보태거나 후속 질문을 던지는 식이다.

Buzz는 블록의 코딩 에이전트 Goose의 경량판을 통합한 자체 내장 에이전트를 갖추고 있으며, 다른 코딩 하네스와 도구도 지원한다. 오픈소스 프로젝트로서 모델 중립적이고 셀프호스팅이 가능해 조직의 자체 네트워크나 시스템에서 비공개로 운영할 수 있다. 블록에서 직원들은 코딩, 분석, 기타 일상 업무에 Buzz를 쓰며, 많은 이들이 이미 동료들과 대화 중인 곳에 에이전트를 데려온다.

모델 접근은 Databricks Unity Gateway가 담당한다. 직원이 Buzz에서 에이전트를 만들 때 Databricks를 추론 제공자로 선택하면 Unity Gateway가 노출하는 모델 목록에서 고를 수 있다. OpenAI·Anthropic·Google의 프런티어 모델과 선별된 오픈 가중 모델이 단일 통합으로 제공된다. 모델 선택을 에이전트 생성에서 분리해 둔 것이 핵심이다. 코딩 과제, 분석 질문, 가벼운 일상 요청은 각각 다른 모델이나 하네스가 어울릴 수 있으므로, 모든 에이전트를 같은 모델 중심으로 설계하는 대신 특화된 에이전트 컬렉션을 만들 수 있다.

가장 흥미로운 실험은 멀티 에이전트다. 복잡한 과업의 모든 단계가 가장 비싼 모델을 필요로 하지는 않으므로, 블록은 더 유능한 모델이 소형·고효율 모델로 구동되는 에이전트 팀을 조율하는 구성을 탐색해 왔다. 조율 에이전트가 까다로운 추론을 맡고 나머지는 각자 능력에 맞는 과업을 처리하며, 사람들은 같은 Buzz 환경 안에서 에이전트 간 협업을 지켜보고 참여할 수 있다. 블록은 이런 에이전트 팀의 벤치마킹을 위한 내부 방법도 개발해 엔지니어들이 여러 구성을 시험하게 한다. 글은 이를 더 넓은 변화로 규정한다. 이제 질문은 어떤 단일 모델이 가장 잘하는가가 아니라, 모델·하네스·에이전트를 어떻게 결합해 일을 효과적으로 끝낼 것인가다.

## 핵심 내용

- Buzz는 직원과 AI 에이전트가 채널·스레드·DM에서 함께 일하는 블록의 오픈소스 협업 워크스페이스다. 사용자는 에이전트를 만들고 모델이나 코딩 하네스를 고르며, 여러 에이전트·동료와 한 환경에서 협업한다.
- 내장 에이전트는 Goose의 경량판을 통합하며, 다른 코딩 하네스와 도구도 지원한다.
- 오픈소스·모델 중립·셀프호스팅 가능 — 조직은 자체 네트워크나 시스템에서 비공개로 운영할 수 있다.
- Unity Gateway가 모델 접근 계층이다. 직원은 Databricks를 추론 제공자로 선택하고 단일 통합으로 프런티어 모델(OpenAI·Anthropic·Google)과 선별된 오픈 가중 모델을 고른다.
- 과업별 모델 선택: 서로 다른 과업에는 서로 다른 모델·하네스가 어울리므로, 에이전트를 획일적으로 만들기보다 특화할 수 있다.
- 실험 중인 멀티 에이전트 패턴: 더 유능한 조율 모델이 소형·고효율 모델 기반 에이전트 팀을 조율하고, 사람은 같은 협업 환경에서 에이전트 간 작업을 보고 참여할 수 있다.
- 블록은 에이전트 팀의 모델·하네스 구성을 성능과 비용으로 비교하는 내부 벤치마킹 방법을 쓴다.
- 관점의 전환: AI 개발은 '최고의 단일 모델 고르기'에서 '모델·하네스·에이전트의 결합으로 일 완수하기'로 이동하고 있다.
- 시작 방법: GitHub에서 Buzz 오픈소스 프로젝트를 살펴보고, 자신의 애플리케이션과 에이전트를 위해 Unity Gateway로 단일 API상의 프런티어·오픈 가중 모델을 활용한다.

## 세부 사항

### 사람과 에이전트를 위한 하나의 환경

Buzz는 에이전트를 외부 도구가 아니라 참여자로 다룬다. 그 자리에서 만들고, 모델과 하네스를 지정하고, 이미 대화가 진행 중인 작업에 초대할 수 있다. 협업 모드는 그룹 논의, 집중 대화, 일대일 교환으로 이어지며 채널·스레드·DM에 자연스럽게 대응한다. 워크스페이스가 공유되므로 에이전트의 중간 작업도 동료가 검토할 수 있고, 글은 이것이 에이전트가 별도 AI 도구가 아니라 기존 대화로 들어오는 이유라고 본다.

### 모델 추상화로서의 게이트웨이

Unity Gateway는 모델 접근을 하나의 통합 뒤로 중앙화해, Buzz의 에이전트 생성 흐름은 단지 모델 목록을 가진 'Databricks' 추론 제공자를 제시하면 된다. 기업 입장에서는 에이전트 설계와 벤더 교체가 분리된다. 새 모델이 나와도 일이 일어나는 장소를 바꾸지 않고 에이전트만 다시 연결할 수 있다. Buzz의 모델 중립·셀프호스팅 설계와 결합하면 하네스 계층과 모델 계층이 독립적으로 진화할 수 있다.

### 멀티 에이전트 경제성

강한 모델이 조율하고 작은 모델이 실행하는 조율 패턴은 완성된 제품이 아니라 비용-성능 실험으로 제시되며, 블록의 내부 벤치마킹 방법이 그 측정 도구다. FAQ도 같은 생각을 기업 일반에 적용한다. 과업 요구·성능·비용에 따라 에이전트에 모델을 배정하고, 모든 워크플로에 하나의 모델을 박아 두는 대신 조합을 실험하라는 것.
