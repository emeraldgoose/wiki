# Databricks에서 자격 증명 기반 공격 탐지하기

**원문**: [Databricks 블로그](https://www.databricks.com/blog/detecting-credential-driven-attacks-databricks) · **게시일**: 2026-11-11

## 개요

현대의 사이버 공격이 항상 무너진 경계선에서 시작하는 것은 아니다. 유효한 로그인에서 시작한다. 공격자가 유출된 세션 쿠키, 개인 액세스 토큰(PAT), 서비스 프린시펄 자격 증명을 손에 넣는 순간 초기 침해는 이미 완료되고, 이후 목표는 오염된 사용자나 서비스의 모습으로 위장하며 활동하는 것이다. 글의 비유를 빌리면 열쇠를 쥐었다고 건물을 아는 것은 아니다. 훔친 출입증으로 보안 게이트를 통과했어도 경비원을 피하고, 어느 층에 출입할 수 있는지 헤아리고, 금고를 찾아야 한다. 공격자에게는 실제 직원의 깊은 현지 맥락이 없기 때문에 행동이 결국 발각된다. 글은 자격 증명 기반 공격이 플랫폼에서 어떻게 전개되는지, Databricks 상세 감사 로그와 Genie로 신원의 행동 변화를 어떻게 탐지하는지, 침해 확인 후 어떻게 대응하는지, 그리고 도난 자격 증명이 할 수 있는 일을 애초에 어떤 통제로 제한하는지 다룬다.

탐지 모델은 비선형 공격 순서를 전제한다. 공격자는 한 세트의 자격 증명으로 환경을 살핀 뒤, 정찰 기록이 없는 새로운 신원이나 워크스페이스로 돌아오기 위해 다른 세트를 회수한다. 지속성 확립 없이 정보만 모으거나, 목표를 마무리하기 전에 재진입 경로를 만들어 두기도 한다. 예시 시나리오는 이렇다. 데이터 엔지니어의 PAT가 잘못 설정된 CI/CD 로그에서 복사된다. 몇 분 안에 새로운 IP에서 이 엔지니어가 해본 적 없는 시크릿 스코프, 카탈로그, 리포 목록 조회가 실행된다. 서비스 프린시펄 자격 증명을 담은 시크릿이 읽힌다. 한 시간 뒤 엔지니어가 아니라 그 서비스 프린시펄이 함수를 만들고, 스스로 관리자 그룹에 자신을 추가하고, init 스크립트 몇 개를 내보낸다. 각 이벤트는 평범한 플랫폼 사용으로 통과되지만, 모으면 하나의 침해가 공격 사슬을 따라 움직이는 것이고 Databricks의 모델은 이를 하나의 조사로 연결한다.

조사는 이미 있는 텔레메트리로 돌린다. 컨트롤 플레인 활동은 system.access.audit 시스템 테이블에 기록되고, Detection App은 감사 로그용 Genie 에이전트를 더해 토큰 오남용부터 관리자 권한 부여까지 30개가 넘는 내장 탐지를 제공한다. 자기 말로 물을 수도 있다("user@example.com이 어제 내보낸 노트북은?") — Genie가 SQL을 써서 실행한다. 목표를 줄 수도 있다("최근 90일 동안 침해됐나?") — 탐지를 하나씩 통과하며 답을 찾는다. 유의점 두 가지. 빈 결과가 곧 무사하다는 뜻은 아니다(시간 창 밖이거나 상세 감사 로그가 꺼져 있을 수 있다). 감사 로그는 무엇이 바뀌었고 누가 바꿨는지를 남기지만, 이전 값과 새 값은 대개 남지 않는다.

## 핵심 내용

- 1단계 — 유효한 자격 증명으로 접근. 자격 증명이 진짜라 로그인 자체는 평범하다. 단서는 로그인 직후 몇 분의 행동이다. 타임라인은 인증 이벤트(user_identity, source_ip_address, user_agent, sessionId, request_id, workspace_id)에서 시작한다. 낯선 클라이언트의 accounts.tokenLogin 폭발 뒤 같은 토큰이 다른 출발지 IP에서 쓰이면 플래그를 올리고, 예상 네트워크에서 예상 밖 사용자 에이전트로 발급된 서비스 프린시펄 OAuth 토큰 — 특히 1분 안에 새 IP 활동이 이어지는 경우 — 도 플래그한다.
- 2단계 — 정찰. 1분 안에 5개 이상의 서로 다른 발견용 API 호출은 사람이 플랫폼을 둘러보는 방식이 아니다. 신원의 기준선과 비교한다(기존 신원의 첫 시크릿 열거, 업무 쿼리에서 접근 통제·설정 스키마 대상 SHOW TABLES로 전환된 SQL 세션). 실패한 요청도 찾는다. accounts.oidcTokenAuthorization 뒤에 처음 기록된 IpAccessDenied는 차단된 네트워크에서 자격 증명이 재생되었다는 가장 이른 기록일 수 있다.
- 3단계 — 자격 증명 추가 수확. 공격자는 시크릿 스코프를 나열하고, 스코프 안의 시크릿을 나열하고, 유용한 것을 읽는다. 회수한 값으로 더 높은 권한의 다른 신원으로 돌아온다. listScopes → listSecrets → getSecret가 여러 스코프에 걸쳐 빠르게 반복되면 수확이다. 거부된 읽기와 이후의 성공 읽기를 연결하고, 컴퓨트 쪽 접근도 살핀다(제출된 명령이 시크릿 유틸리티를 호출하거나 자격 증명 경로에 read_files()를 쓰는 코드). 모든 시크릿 읽기를 그 다음 행동과 연결한다. 이 시점부터 조사는 두 신원을 따라가야 하고, 대응 시에는 그 신원이 닿을 수 있는 모든 자격 증명을 교체한다.
- 5단계 — 지속성 확보. 보안 통제 변경은 실패해도 높은 심각도로 다룬다(setSetting/deleteSetting, IP 액세스 목록 수정, createPrivateAccessSettings). 예상 IdP가 아닌 경로의 SCIM 그룹 변경을 점검하고, 낯선 출발지나 잡 실행 중의 generateDbToken 호출을 플래그한다(토큰 하나하나가 회수해야 할 별개 자격 증명이다). 공격자의 대화형 활동이 멈춘 뒤에도 그룹·권한·설정을 계속 바꾸는 잡은 스스로 접근을 유지하는 것일 수 있으므로, 종료 전에 정의와 산출물을 보존한다.
- 6단계 — 데이터 수집과 흔적 정리. 내보내기는 개수가 아니라 맥락으로 판단한다. workspaceExport는 경로, 형식, 직접 다운로드 여부를 기록한다. 낯선 신원, 특이한 경로나 형식, 처음 보는 네트워크, 시크릿 접근 뒤에 이어지는 내보내기를 우선한다. init 스크립트 몇 개의 표적 내보내기가 벌크 덤프보다 더 많이 유출할 수 있다. 단명 객체의 생성·삭제 반복(같은 세션의 createFunction 후 deleteFunction 등)을 기록하고, 임시 자격 증명·데이터 읽기 폭발을 앞선 정찰과 연결한다. 인코딩된 명령만으로는 알림기준이 되지 않는다.
- Genie 조사. Genie One에서 두 가지 방식으로 일한다. 자연어 질문을 SQL로 바꿔 실행하거나, Detection App의 30개 이상 내장 탐지를 목표("최근 90일 동안 침해됐나?")로 하나씩 통과시킨다.
- 자격 증명이 닿을 수 있는 범위 제한(인그레스). 권한 있는 서비스 프린시펄은 신뢰 네트워크로 제한하고 사람에게는 다른 정책을 적용한다. 워크스페이스와 계정 요청 모두에 정책을 적용한다(워크스페이스 정책은 계정 콘솔과 계정 수준 API를 덮지 않는다). 드라이런 모드에서 system.access.inbound_network의 거부를 검토한 뒤 단계적 강제한다. 광범위 강제 전에 서버리스·프라이빗 연결 워크플로를 시험한다. IP 액세스 목록은 추가 계층으로 둔다. 서비스 프린시펄 자격 증명·통합 자격 증명·PAT에 만료와 교체를 요구하고 쓰지 않는 자격 증명은 은퇴시킨다. 잠자는 자격 증명의 침해는 몇 달씩 눈에 띄지 않을 수 있다.
- 자격 증명이 실행·변경할 수 있는 것 제한. UDF 생성, 시크릿 스코프 ACL 변경, 워크스페이스 권한 변경, 잡 관리, 인그레스 정책 변경 같은 고영향 작업을 승인된 신원과 통제된 자동화로 한정한다. 관리 경로와 컴퓨트 경로를 분리해 일반 잡 런타임이 계정·네트워크 통제를 바꾸지 못하게 하고 시도는 알림을 낸다. 강화된 메타데이터 서비스 설정과 컴퓨트 이그레스 제한으로 클라우드 실행 환경을 보호한다. 감사 로그, 버전 이력, UDF 정의, 권한 변경 이력, 인그레스 거부 로그를 캠페인을 재구성할 수 있을 만큼 오래 보존한다.
- 닫는 원칙. 도난 자격 증명의 폭발 반경은 결국 그 자격 증명에 부여된 권한만큼만 크다.

## 세부 사항

- 감사 이벤트는 service_name.action_name 형식(예: secrets.getSecret)으로 기록된다. 여섯 단계 지침은 각 환경의 정상 자동화에 맞춰 다듬어야 하는 출발점이며, 단계는 거의 직선으로 진행되지 않는다.
- 예 시나리오에서 CI/CD 로그에서 복사된 PAT는 한 시간 안에 서비스 프린시펄의 함수 생성, 관리자 그룹 추가, init 스크립트 내보내기로 이어진다. 각각은 평범하지만 모이면 하나의 침해다.
- 4단계(실행 가능한 경로 찾기)는 수확과 지속성 사이에 있다. 도난 자격 증명이 실제로 어디서 실행될 수 있는지 찾는 단계라서, 시크릿 API만큼 컴퓨트 쪽 텔레메트리(제출된 명령)가 중요하다.
- 시크릿 API 유의점. 상세 감사 로그가 켜져 있으면 제출된 명령 텍스트가 무엇이 실행됐는지 보여주지만, 시크릿 값이 실제로 반환됐는지는 확인해 주지 않는다. 컴퓨트 쪽 증거와 API 증거를 함께 읽어야 한다.
- 흔적 정리 탐지에서 살아남은 객체는 삭제된 것보다 더 그럴듯한 이름을 얻는 경우가 많다. 그래서 원상복구 전에 정의와 시점을 보존하는 것이 대응 지침의 일부다.
- 글은 세 가지 실행 항목으로 끝난다. Databricks 보안 모범 사례 검토, 양쪽 플레인을 덮는 상세 감사 로그와 컨텍스트 기반 인그레스 통제 활성화, Detection App 배포 후 Genie에게 "최근 90일 동안 침해됐나?" 질문하기.
