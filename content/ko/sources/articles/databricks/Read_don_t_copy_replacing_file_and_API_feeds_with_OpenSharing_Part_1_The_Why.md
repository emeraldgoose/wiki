# 복사하지 말고 읽으세요: OpenSharing으로 파일·API 피드 대체하기 - 1부 (왜)

**원문**: [Databricks 블로그](https://www.databricks.com/blog/read-dont-copy-replacing-file-and-api-feeds-opensharing-part-1-why) · **게시일**: 2026-11-06

## 개요

데이터 엔지니어링의 나머지 영역은 크게 바뀌었지만 고객 데이터 수집 방식은 거의 그대로다. 대부분의 팀은 여전히 SFTP 파일 덤프를 요구하거나 고객 API를 폴링하고, 아니면 관리형 커넥터에 의존한다. 세 방식 모두 동작은 하지만 고객이 늘어날수록 조용히 쌓이는 숨은 비용을 안고 있다. 저자들은 그 근원을 복사 자체에서 찾는다. 복사가 있으면 고객마다 파이프라인을 만들어 관리해야 하고, 어디까지 처리했는지 직접 기록해야 하며, 이미 고객이 보유한 데이터를 한 번 더 저장해야 한다.

파일 드롭에서 API 호출로, 다시 관리형 커넥터로 옮겨가는 과정은 실패 유형을 하나씩 바꿔 왔을 뿐이다. SFTP 피드는 고객이 합의한 파일이 아닌 다른 것을 올리면 깨진다. API 엔드포인트는 보통 시간 파라미터를 받는데, 마지막 타임스탬프를 놓치면 소비자 쪽 사본이 어긋난다. 관리형 커넥터는 유연성을 잃는 대가로 여전히 실패할 수 있다. 가장 아픈 지점은 백필이다. 원본 데이터를 저장해 두지 않으면 파일 피드에서는 고객에게 몇 달치 재추출을 요청해야 하고, API 피드에서는 요율 제한에 부딪히며 나눠서 다시 폴링해야 한다. 비용은 고객에게도 돌아간다. 고객은 자체 일정과 실패 유형을 가진 추출 작업을 만들어 관리해야 하고, 자기 데이터가 언제 읽혔는지 알 수 없으며, 사본을 하나 더 저장하는 비용을 부담한다.

OpenSharing은 이에 대한 대안으로 제시된다. Delta Lake와 Iceberg 같은 개방형 테이블 형식 위에 세워진 개방형 프로토콜로 고객의 테이블을 제자리에서 읽기 때문에, 소비자가 Databricks를 쓰지 않아도 된다. 공유된 테이블은 버전 이력을 노출해 증분 읽기를 가능하게 하고, 삽입·수정·삭제를 담은 변경 데이터 피드(change data feed)를 제공할 수 있다. 그러면 처리 완료 여부를 추적하던 테이블이 파이프라인이 관리하는 체크포인트로 바뀐다. 고객이 쓰는 순간 새 행을 볼 수 있고, 전체 이력을 공유받으면 백필이 부탁이 아니라 쿼리가 된다. 2부에서는 실제 설정 과정을 다룬다.

## 핵심 내용

- 기존 고객 피드는 시작은 싸지만 확장은 비싸다. SFTP 전송이나 API 호출 하나하나가 감시할 파이프라인을 늘린다.
- 문서는 전송 방식보다 복사 자체를 문제로 지목한다. 고객별 파이프라인, 직접 관리하는 진행 기록, 중복 저장이 모두 복사에서 따라온다.
- API 피드는 타임스탬프 커서를 잘못 다루면 어긋난다. 타임스탬프를 놓치면 행이 조용히 중복되거나 배치 하나가 통째로 빠진다.
- 백필이 가장 고통스럽다. 파일은 고객 재추출을 요구하고, API는 요율 제한에 걸리는 나눠 폴링을 강요한다.
- 고객도 두 번 비용을 치른다. 자체 일정과 실패 유형을 가진 추출을 만들어야 하고, 이미 가진 데이터의 사본을 저장한다.
- OpenSharing은 Delta Lake·Iceberg 기반 개방형 프로토콜로 공유 테이블을 제자리에서 읽는다. SFTP 엔드포인트도, 고객별 커넥터도 필요 없다.
- 버전 이력과 변경 데이터 피드가 증분 읽기와 삽입·수정·삭제 이벤트를 제공해, 수동 기록을 체크포인트로 대체한다.
- 수신자 추가는 고객이 이미 관리하는 테이블에 대한 권한 부여일 뿐이고, Databricks 시스템 테이블에 수신자의 조회 시점이 기록된다.

## 상세

글은 고객 수집이 여기까지 온 과정, 숨은 비용, OpenSharing이 바꾸는 것, 실제 동작 모습이라는 네 부분으로 전개된다. 비용 부분에서 강조하는 것은 백필 때 정점에 달하는 고통과, 기록이 어긋날 때 생기는 조용한 실패다. 행이 중복되거나 배치가 누락되는데도 알아채기 어려워 디버깅에 몇 시간이 걸릴 수 있다고 지적한다. 고객이 감수하는 비대칭성도 짚는다. 추출 작업은 고객이 만들어야 하지만 누가 읽었는지는 확인할 수 없고, 양쪽 모두 사본을 보관한다.

OpenSharing에서는 소비자가 복사를 만들지 않는다. 공유 테이블이 스스로 순서 있는 이력을 유지하므로, 파이프라인은 스트리밍이나 변경 데이터 피드로 변경을 따라가면 되고 처리 완료 여부를 따로 추적하지 않아도 된다. 고객이 전체 이력을 공유하면 백필은 필요한 데이터를 그대로 조회하는 일이 되며, 별도 저장 없이 매번 최신 결과를 얻는다. 제공자에게도 이점이 있다. 수신자 추가는 새 추출 작업이 아니라 권한 부여이고, 읽기는 제공자의 데이터베이스가 아니라 클라우드 스토리지에서 수신자 자신의 컴퓨팅으로 수행되며, 시스템 테이블이 수신자 접근에 대한 감사 기록을 남긴다. 글은 2부에서 공유 생성부터 증분 읽기까지 고객과의 설정 과정을 다룬다고 맺는다.
