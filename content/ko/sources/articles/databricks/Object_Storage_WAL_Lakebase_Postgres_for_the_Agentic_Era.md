# 객체 스토리지 + WAL: 에이전트 시대의 Lakebase Postgres

**저자**: Cassie Murray, Carlota Soto · **발행**: 2026-08-27 · **출처**: [Databricks Engineering Blog](https://www.databricks.com/blog/object-storage-wal-lakebase-postgres-agentic-era)

## 질문: 트랜잭션 DB 밑에 객체 스토리지가 들어갈 수 있는가?

에이전트는 OLTP 스토리지 계층을 특이하게 두들긴다. 새 배포·복사·복원·복제본마다 대량 데이터를 옮겨야 해서 느리고 비싸다. 객체 스토리지(S3류)는 정반대다: 싸고 빠르고 운영이 거의 보이지 않으며, 에이전트 메모리의 자연스러운 토대다. Lakebase Postgres는 객체 스토리지가 Postgres 밑에 들어가 에이전트 작업을 쉽게 할 수 있는지 묻는다. 답은 객체 스토어의 속도가 아니라 ***source of truth를 어디에 두는지***에 달려 있다.

## 두 가지 OLTP 정신 모델

익숙한 **데이터 중심** 모델: DB는 테이블에 현재 상태를 저장하고, 스토리지는 현재를 담는다. 대안은 **트랜잭션 중심** 모델: DB는 트랜잭션의 저널 — 현재는 타임라인에서 도출되는 한 단면이다. 에이전트 워크로드가 원하는 연산(브랜치, 복사, 특정 시점 복원, 시점 간 diff, 읽기 복제본)은 거의 전부 타임라인 연산인데, 현재만 저장하는 DB는 느리고 비싼 복사로 답할 수밖에 없다. Postgres는 이미 그 타임라인을 갖고 있다: **WAL(Write-Ahead Log)**이다. 모든 변경은 데이터 파일에 닿기 전 WAL에 추가되고, 각 레코드는 단조 증가하는 **LSN(로그 시퀀스 번호)**으로 어느 릴레이션의 어느 8KB 페이지가 타임라인의 어느 지점에서 바뀌었는지 지목한다(`pg_waldump`로 확인 가능). 복구 수단이 아니라 저널로 읽으면, WAL은 바뀐 모든 페이지의 완전하고 순서 있는 바이트 단위 기록이며, LSN 덕분에 "시점 T의 DB"가 Postgres 수정 없이도 잘 정의된다. 필요한 것은 로그를 보관하고 로그에 대한 질의에 답하는 스토리지 계층뿐이다.

## 아키텍처: 컴퓨트는 실행하고 스토리지는 진실을 소유한다

전통 Postgres는 데이터 파일을 DB 본체로 보고 적용된 WAL을 자른다. Lakebase는 이를 뒤집는다: **로그가 DB이고 데이터 파일은 도출된 캐시 표현**이다. 전체 히스토리를 보관하고, 복사는 파일 집합이 아니라 포인터가 된다.

- **컴퓨트 계층**: 표준 Postgres — SQL 파싱·계획·MVCC·락·인덱스. RAM은 공유 버퍼, 로컬 NVMe는 페이지 캐시. 실행을 위해 존재하고 보존을 책임지지 않는다. 시작·정지·확장·죽음 모두 내구성에 무해하다. 쿼리 엔진은 하나도 고치지 않았다.
- **스토리지 계층**(개별 컴퓨트 노드보다 오래 산다): **safekeeper**가 Paxos 기반 프로토콜로 WAL을 복제 — 쿼럼 ack *자체가* 커밋이다(동기 복제의 네트워크 홉을 새로 추가하는 게 아니라 대체한다). **pageserver**가 페이지 버전을 객체 스토리지에 비동기로 구체화해 커밋 경로 밖에 둔다. **객체 스토리지**가 불변 히스토리를 개방형 컬럼형 포맷으로 보관한다. 제자리 업데이트는 절대 없다.
- **읽기 경로(`GetPage@LSN`)**: 모든 읽기는 페이지+LSN을 지목하고 RAM → NVMe → pageserver(레이어에서 재구성) 순으로 서빙된 뒤 로컬에 캐시된다. 최신 버전을 묻는 프라이머리는 웜 캐시 Postgres처럼 동작하지만, 과거 LSN도 완전히 동일하게 동작한다 — 실시간 데이터와 백업의 구분이 하나의 주소 지정 가능한 시스템으로 합쳐진다.

### 비덮어쓰기 레이어와 조회 트릭

pageserver는 데이터를 **델타 레이어**(페이지 범위별 WAL 레코드)와 **이미지 레이어**(재현 체인을 짧게 하고 오래된 델타를 수거 가능하게 하는 페이지 스냅샷)로 조직한다. 백그라운드 컴팩션이 재배열하고, 보존 창 밖의 레이어는 가비지 수집한다 — 무작위 업데이트가 없는 객체 스토리지에 꼭 맞는 구조다. 어려운 문제는 수천만 레이어에서 키 K를 LSN L 이하에서 커버하는 가장 가까운 레이어를 찾는 것이다(R-트리는 다른 질의에 답하고, 세그먼트 트리는 좌표 공간 크기에 비례한다). 해법: 고정된 하나의 LSN에서는 커버리지가 키 공간의 소수 지점에서만 바뀌므로, 그 지점들을 이진 탐색 트리에 기록해 단일 조회로 읽는다. 그리고 이 트리를 **퍼시스턴트**(함수형 퍼시스턴트)로 만든다: 레이어를 LSN 순서대로 아래부터 삽입하면서 건드린 루트 경로 노드만 복사하고 바뀌지 않은 서브트리는 공유한다 — 트리 한 개 값으로 모든 시점의 루트를 누적한다. 과거 읽기가 현재 읽기와 같은 비용이 된다: 원하는 LSN의 루트를 골라 같은 단일 조회를 하면 된다.

## 에이전트 기능과 LTAP

히스토리가 주소 지정 가능하고 복사가 참조가 되므로, Postgres는 에이전트에 필수인 경량 워크플로를 얻는다:

- **브랜칭**: 브랜치는 특정 LSN을 가리키는 포인터 + copy-on-write 분기 — 2TB 브랜치를 수초에, 쓰기 전까지 비용 0, 부모 부하 0. 스무 개 에이전트가 각자 프로덕션을 브랜치해 실제 데이터 규모에 마이그레이션을 시험하고 버릴 수 있다. 브랜칭은 테이블을 넘어 버킷·함수·인증 상태·AI 게이트웨이 설정까지 확장되어 백엔드 전체의 격리 복사본이 된다.
- **즉시 복원/PITR**: 복원은 과거 LSN을 가리키는 것으로, 비용이 DB 크기와 무관하고 보존 설정 범위까지 과거로 거슬러 올라갈 수 있다. 에이전트의 잘못된 쿼리는 복원 윈도우·복구 계획이 아니라 브랜치 되감기로 undo된다.
- **타임트래블 쿼리**: 복원 전에 과거 상태를 직접 조회한다(마이그레이션 전후 diff, 복원 시점 검증).
- **복제본 없는 읽기 복제본**: 읽기 전용 컴퓨트 노드는 같은 스토리지 계층을 읽으므로, 추가는 데이터셋 프로비저닝·따라잡기 없는 메타데이터 연산이다.
- **Scale to zero**: 유휴 컴퓨트는 5분 비활성 후 중단되고 수백 ms 만에 깨어난다. 중단 중 컴퓨트 과금은 멈춘다(스토리지는 계속). 에이전트·세션·브랜치당 DB가 기본값이 될 만큼 저렴해진다.

**LTAP(Lake Transactional/Analytical Processing)**: 내구성 기록이 개방형 컬럼형 객체 스토리지에 있으므로, pageserver는 구체화 시 Postgres 로우 포맷을 Postgres 값 의미론 그대로 컬럼형으로 트랜스코딩한다. 분석 쿼리는 현재 LSN을 가져오고(저렴한 메타데이터 조회), 대부분을 그 LSN 기준 객체 스토리지에서 읽고, 아직 구체화 안 된 최신분만 pageserver에서 가져온다 — Postgres는 숫자 하나 외에 분석 읽기 트래픽을 사실상 서빙하지 않는다. CDC/미러링과 달리 옵트인할 게 없고, 복제 테이블 목록이 없으며, 두 뷰가 어긋날 수 없다. 테이블은 이미 레이크에 존재한다.

## 세미나 시사점

- **source-of-truth 배치가 핵심 트릭이다**: OLTP 밑의 객체 스토리지는 WAL이 내구성 진실일 때만 동작한다. 핫 경로 쿼리는 여전히 RAM/NVMe에서 서빙되고 S3에서 읽지 않는다.
- **주소 지정 가능성(LSN)이 연산을 포인터로 바꾼다**: 브랜치·복원·복제본·타임트래블은 모두 같은 원시 연산 — LSN 지목이다.
- **퍼시스턴트 커버리지 트리**가 하중을 지탱하는 자료구조다: 과거 페이지 조회가 싸지 않으면 싼 히스토리는 무용지물이다 — 경로 복사 퍼시스턴스로 모든 LSN의 인덱스를 거의 공짜로 얻는다.
- **단일 복사본이 파이프라인 부류를 없앤다**: LTAP는 같은 내구성 바이트를 두 엔진이 읽게 해서 CDC/복제/드리프트를 범주째 제거한다.
