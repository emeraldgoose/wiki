# 평가 주도 개발: 대규모 GenAI 평가의 교훈

**출처**: Airbnb Engineering (Medium) · **발행**: 2026-07-28 · **저자**: Rohit Girme, Dan Miller, Mia Zhao, Lifan Yang, Clint Kelly

## GenAI가 기존 테스트 가정을 깨는 이유

LLM 출력은 비결정적이고, "정답"은 주관적이며, 판단에 AI가 필요하고(AI가 AI를 평가, 자체 실패 모드), 한 번의 상호작용이 검색→추론→도구 호출→생성을 연결해 각각 독립적으로 실패한다. Airbnb는 리뷰 하이라이트, AI 고객지원, 게스트/호스트 메시징 등 전 제품에 LLM 기능을 올리고 공통 인프라팀 기반 위에 평가를 쌓는다. 예산 원칙: **전체 프로젝트 노력 중 의미 있는 비중을 평가에 배정** — 동작하는 제품을 만드는 방법이다.

## 하나의 규칙 + 평가 주도 개발(EDD)

**의심스러우면 데이터를 보라.** 프로토타입 → 100개 예제 실행 → 출력·트레이스를 *직접 읽기* → 실수 분류 → eval 구축. 이를 형식화한 것이 TDD의 GenAI 대응물 **eval-driven development**: 실패 모드를 발견·인코딩·지속 테스트하는 인프라와 습관.

5원칙: (1) 목표와 출시 게이트를 사전 정의 (2) 관찰된 실제 오류가 지표 결정 (진공에서 창작 금지, 직군 협업) (3) 평가자는 **적고 날카롭게 — 보정된 3~5개가 노이즈 낀 20~30개보다 낫다**, 차원당 하나, "만능 평가자" 금지 (4) 선악 판정의 인간 최종 결정자 지정 (5) 지속 협업 ("X가 Y보다 나은가? 정확히 뭐가 잘못인가?").

## 3층 평가

1. **프로그래밍/휴리스틱 검사** (빠른 결정적 1차 필터): JSON 스키마 구조화 출력, 프롬프트만으로 포맷 강제 금지.
2. **LLM-as-judge** (어조·일관성·충실도 등 뉘앙스): 루브릭 설계가 전부 — "읽기 쉽고 기준에 맞는가"는 무용, 어조/포맷/문법/복잡도 규칙 + 점수 예시로 `{reason, score}` 반환. **보정 필수**: 50~100개 골든셋(*나쁜 예 포함*), 80% 후반~90% 일치 목표(Cohen's κ/Krippendorff's α), 불일치 분석→프롬프트/퓨샷 개선→반복, 실패 모드 변화 시 재보정. 미보정 저지는 없는 것만 못하다(거짓 확신).
3. **인간 평가** (정답·고위험·타이브레이크의 gold standard): 20~100개 SME 라벨로 시작, 루브릭이 확고하고 물량이 병목일 때만 외주 확대. **전문가 의견이 갈리면 중단** — 자동화 전 인간 불일치부터 해결.

## 에이전트 시스템 평가

최종 출력만으로는 부족: 정답 뒤에 깨진 경로(잘못된 도구 인자, 비효율 궤적)가 숨는다. **트레이스/스팬**(에이전트 종류, 서브에이전트, 입출력, 도구 호출)을 관측 플랫폼에 기록하고 궤적 품질·도구 사용 정확성·최종 결과를 3층으로 평가.

## 반복 루프와 운영 미러링

한 번에 하나의 변수만 변경(모델→프롬프트→서빙 설정), 저지가 후보를 좁히고 상위 후보 샘플이 저지를 개선(상호 정교화). ~5천 예제로 확대 후 **운영에 평가 미러링**: 매일 비식별 라이브 트래픽 ~5%를 프로그래밍+저지층 통과, 플래그는 인간 검토, 주간 PM 리뷰가 새 eval로 환류 (비식별화·목적 제한 준수).

## 10가지 요점 (원문)

데이터를 보라 · 실제 실패 모드용 평가자(일반적 helpfulness 금지) · 50~100행 시작 · 차원당 하나의 평가자 · 80% 후반~90% 보정 · 3층 모두 사용 · 나쁜 예 포함 · 모델이 아닌 시스템(검색/도구/파이프라인), 에이전트는 궤적 평가 · 운영 미러링 · 평가는 팀 스포츠.
