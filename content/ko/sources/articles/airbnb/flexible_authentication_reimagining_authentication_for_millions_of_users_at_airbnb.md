# 유연한 인증: 수백만 사용자를 위한 Airbnb 인증의 재구상

**출처**: Airbnb Engineering (Medium) · **발행**: 2026-08-12 · **저자**: Jose Santos, Mike Barry

## 문제: 드문 로그인이 구조적 특성이다

게스트는 1월에 예약하고 여름에 돌아오고, 호스트는 예약이 있을 때만 접속한다. 로그인 실패 = 예약 상실 = 양측의 매출 손실. 10년간 유기적으로 쌓인(비밀번호 → 소셜 → 이메일 OTP → 전화번호) 경직된 클라이언트 중심 인증은 사용자·지역·실험별 적응이 불가능했다.

## 설계 1: 먼저 식별하고, 그 다음 챌린지

기존 사고방식("본인임을 증명할 수 있는가?")에서 새 질문("이 세션에서 이 사람이 검증하기 **가장 쉬운 방법**은?")으로 전환.

- 브라질 전화번호 사용자에게는 SMS가 아닌 **WhatsApp OTP** (보급률).
- 한국 복귀 호스트에게는 Google이 아닌 **Naver 로그인**.
- 흐름을 2단계로 분리: (1) 식별자(이메일/전화/소셜, 사용자 선택) → (2) **서버 정책 엔진**이 세션+계정 이력으로 성공 확률 최대 챌린지 선택.
- **클라이언트는 절대 챌린지를 결정하지 않음** — 서버 응답 화면을 렌더링만. 클라이언트 배포 없이 지역별 튜닝, 실험이 자명해짐.

## 설계 2: Challenge Picker — 막다른 골목 제거

기존 실패 모드: 제시된 챌린지 실패 ⇒ stuck (비밀번호 재설정은 별도 여정, 별도 이탈). 제품 원칙이 하드 요구사항으로: **모든 인증 화면에 탈출구 필수**.

- 서버가 주 챌린지 + **성공 확률순 대안 목록**(과거 성공, 등록 수단, 플랫폼 가용성 반영) 반환.
- "다른 방법으로 시도"는 흐름 재시작이 아닌 적응.
- 특정 챌린지 장애가 더 이상 사용자를 막지 못함.

## 설계 3: 완전 서버 주도 화면

동기: 개선안마다 앱 심사 수 주 대기 후 실험 시작. 해법: **화면을 추상화의 기본 단위**로 — 식별자 입력, 챌린지, 계정 선택, 오류 복구 모두 서버 정의, Web/iOS/Android는 씬 렌더러 + 서버 스키마 기반 자동 생성 타입(컴파일 타임 불일치 검출).

## 성과

- **코드 -60%**, 웹 번들 -100KB.
- **속도**: 출시 후 3개월 20+ 실험, 아이디어→측정 결과가 수 주에서 수 일로(대부분 클라이언트 변경 제로).
- **인증 성공률 +2.6%** (이미 높은 기저, 수백만 세션), 로그인 소요 시간 단축.
- **중복 계정 -27%**, **OTP 비용 약 -11%**.

## 엔지니어 관점 시사점

- 맥락이 정답 경험을 결정하는 흐름은 **결정 경계를 클라이언트 밖으로** — 지역/실험/개인별 적응력 확보.
- "막다른 골목 없음"을 UX가 아닌 **아키텍처 불변식**으로 (서버 계산 순위 대안).
- 씬 렌더러 + 스키마 생성 타입으로 중앙집중 로직과 안전성 양립.
