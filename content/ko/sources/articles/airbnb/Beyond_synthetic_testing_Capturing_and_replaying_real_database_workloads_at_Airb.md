# 합성 테스트를 넘어서: Airbnb의 실제 데이터베이스 워크로드 캡처와 리플레이

## 개요

Airbnb는 수백 개 MySQL 호환 클러스터에서 초당 수백만 쿼리를 처리한다. sysbench 같은 합성 벤치마크는 실제 운영 행태를 반영하지 못했기 때문에, 팀은 ProxySQL 기반 캡처·리플레이 파이프라인을 구축했다. 프록시 계층에서 실시간 쿼리 트래픽을 수집하고, 오프라인에서 클러스터별 리플레이용 데이터셋으로 가공한 뒤, 대상 데이터베이스에 재생하면서 부하 테스트, 업그레이드 호환성 검증, 성능 문제 분석에 활용한다.

## 프록시 계층에서 캡처하는 이유

초기 방식은 각 애플리케이션 언어 바인딩(Java, Python, Ruby) 내부에서 쿼리를 로깅해 Kafka로 모은 뒤 커스텀 리플레이어로 재생하는 구조였다. 초기에는 동작했지만 언어별 유지보수 부담이 크고 서비스 확장에 불리했으며, 트랜잭션 문맥이 유실되어 동시 실행 문장이 뒤섞인 채 저장되므로 트랜잭션을 충실히 재현할 수 없었다.

모든 DB 트래픽이 이미 ProxySQL을 거치므로, 팀은 캡처 지점을 그곳으로 옮겼다. 애플리케이션 변경 없이 동작하는 단일 캡처 지점이며, ProxySQL 내장 쿼리 로깅을 클러스터 단위로 켤 수 있고 성능 영향이 작다. Log Mover 사이드카가 로그 파일을 오브젝트 스토리지로 옮겨 로컬 디스크 사용량을 관리한다.

## 캡처·가공·리플레이 구조

파이프라인은 세 단계다. Log Mover가 ProxySQL 파드에서 원시 바이너리 쿼리 로그를 수집하고, Log Processor 오프라인 잡이 이를 디코딩해 백엔드별로 섞인 트래픽을 클러스터별 파일로 분리하고, 각 트랜잭션의 문장을 원래 순서대로 재조립한다. 5분 단위 시간 버킷으로 나누어 재생 속도를 세밀하게 제어하고, `INSERT` 문은 캡처된 `last_insert_id`를 명시적으로 포함하도록 재작성해 엔진 간 자동 증가 동작 차이를 흡수한다(대신 대상의 네이티브 ID 생성은 검증하지 못하는 절충이 있다). Log Replayer는 API 서버·태스크 스케줄러·수평 확장 워커로 구성되며, 배치별 공통 시작 시각으로 워커들을 동기화해 원래 타이밍을 재현하거나 배속으로 가속한다.

리플레이 모드는 두 가지다. 결과는 무시하고 에러·지연 히스토그램·자원 사용량을 보는 부하 테스트용 재생 전용 모드, 그리고 동일 트래픽을 두 대상에 동시 실행해 결과를 비교하는 마이그레이션 검증용 재생·비교 모드다.

## 업그레이드와 용량 계획에 미친 효과

이 리플레이 테스트가 MySQL 5.7→8.0 업그레이드를 이끌었다. 이분 탐색식 리플레이로 쿼리 캐시 효과를 분리하고 심각한 지연 회귀(한 패턴이 조인당 0.03초에서 2.6초로 악화)를 찾았으며, 비교 모드로 `ORDER BY`가 불완전한 비결정적 쿼리를 운영 전에 잡아냈다. 용량 계획에서는 성수기 대비 2배속 리플레이로 한계를 조기에 노출했다. 한 대형 클러스터는 쓰기 80% 증가 시 커밋 지연이 약 6ms에서 34ms로 치솟아 천장을 확인했다. 현재 팀들은 셀프서비스 도구로 리플레이를 요청한다.
