# Airbnb의 내장형 워크플로 엔진 Skipper, 오픈소스로 공개

**원문**: [Airbnb 기술 블로그](https://airbnb.tech/open-source/skipper-airbnbs-embedded-workflow-engine-is-now-open-source) · **게시일**: 2026-11-10

## 개요

Airbnb가 사내 여러 팀이 실제 운영 환경에서 사용해 온 내장형 워크플로 엔진 Skipper를 Apache 2.0 라이선스로 공개했습니다. Skipper를 쓰면 여러 단계로 이루어진 비즈니스 프로세스를 평범한 Java나 Kotlin 클래스로 표현하고, 진행 상황을 저장하며, 크래시와 일시적 장애에서 복구할 수 있습니다. 이 모든 것이 프로세스를 소유한 서비스 안에서 이루어지고, 그 서비스가 이미 쓰는 의존성과 데이터베이스를 그대로 활용하므로 별도의 오케스트레이션 클러스터를 추가할 필요가 없습니다. 저장소에는 핵심 엔진과 함께 문서, 바로 실행해 볼 수 있는 예제가 들어 있습니다.

출발점은 프로세스가 여러 서비스를 가로지르거나, 사람의 입력을 기다리거나, 동기 단계와 비동기 단계를 섞어 쓸 때마다 되풀이되는 문제입니다. 이런 프로세스는 이미 무슨 일이 일어났는지, 무엇을 재시도해야 하는지, 무엇이 아직 대기 중인지를 내구성 있게 저장해야 합니다. 이를 프로세스마다 따로 구현하면 부분 실패, 타이머, 복구를 다루는 같은 장치를 테스트와 디버깅까지 포함해 매번 다시 만들어야 합니다. 기존의 답은 직접 운영하든 관리형이든 중앙 오케스트레이션 서비스를 두고 여러 팀이 하나의 플랫폼에서 운영과 모니터링을 처리하는 방식이었습니다. Airbnb가 택한 방향은 달랐습니다. 각 서비스가 워크플로를 자신의 기존 배포와 데이터베이스 안에서 소유하게 하고, 중요한 서비스는 공유 오케스트레이션 의존성을 추가로 떠안지 않게 하며, 단계 사이에 별도 조정자가 없는 프로세스 내 실행을 유지하는 것입니다.

이 제약이 아키텍처를 결정합니다. 서비스의 복제본들이 워크플로 런타임과 스케줄러까지 함께 실행하고, 워크플로 상태와 예약된 작업을 담은 데이터베이스를 공유합니다. 스케줄러는 실행 가능한 작업을 폴링하고 임차(lease)로 소유권을 조정하기 때문에, 복제본 하나가 실패하면 다른 복제본이 그 작업을 이어받을 수 있습니다. 인수 시점은 스케줄링과 임차 설정에 따라 달라집니다. 절충점도 분명합니다. 따로 배포해야 하는 시스템은 줄어들지만, 워크플로 실행과 데이터베이스 용량, 복구에 대한 책임은 해당 서비스 팀으로 옮겨갑니다.

## 핵심 내용

- 프로그래밍 모델은 두 가지 추상화로 이루어집니다. 워크플로는 결정, 순서, 대기를 담은 오케스트레이션을, 액션은 API 호출이나 데이터베이스 갱신처럼 부수 효과가 있는 작업을 맡습니다. Skipper는 액션 결과를 기록해 복구 과정에서 재사용합니다.
- 대기는 저렴합니다. 매물 공개 예제에서 waitUntil은 스레드를 붙잡지 않고 워크플로를 휴면시키고, 시그널 메서드는 API 핸들러나 큐 소비자가 승인 결정을 전달할 수 있게 합니다. 그래서 대기 중 재배포가 일어나도 저장된 워크플로가 사라지지 않습니다.
- 액션은 자신의 부수 효과를 스스로 멱등하게 만들어야 합니다. 예를 들어 안정적인 요청 ID로 공개 처리와 호스트 알림을 각각 중복 제거하는 방식입니다. Skipper가 하위 시스템 호출을 트랜잭션으로 묶어 주지는 않습니다.
- 복구는 재실행으로 동작합니다. 중단된 워크플로가 재개되면 워크플로 메서드가 처음부터 다시 실행되고, 체크포인트가 내구성 있게 저장된 액션은 저장된 결과를 그대로 돌려줍니다. 따라서 워크플로 코드는 결정적이어야 하며, 시계 조회나 난수, 입출력은 액션이나 명시적 체크포인트로 밀어내야 합니다.
- 체크포인트는 기본적으로 실행이 끝나거나 대기·재시도를 위해 멈출 때까지 묶어서 기록합니다. 데이터베이스 쓰기는 줄지만, 그 묶음이 저장되기 전에 크래시가 나면 이미 끝난 액션 몇 개를 다시 실행할 수 있습니다. 액션이 즉시 체크포인트를 요청해 이 구간을 좁힐 수 있지만, 하위 시스템 효과와 체크포인트가 하나의 원자적 동작이 되는 것은 아니므로 부수 효과는 최소 한 번 실행됩니다.
- 실패 처리는 명시적입니다. 개발자가 어떤 오류를 재시도할지와 정책을 정하고, 영구 실패와 재시도 소진은 처리 대상으로 드러납니다. 복구 시도를 모두 소진한 스케줄러 작업은 수동 개입이 필요할 수 있고, 이미 완료된 단계를 되돌려야 하는 프로세스는 Saga 방식 보상을 지원합니다.
- 오픈소스 배포판에는 핵심 엔진, MySQL·SQLite 어댑터, 테스트 유틸리티, 관리 UI, 그리고 상태·이벤트·전이로 표현하는 편이 자연스러운 프로세스를 위한 Kotlin DSL인 Skipper State Machine이 포함됩니다. WorkflowTest는 시간을 제어할 수 있는 격리된 인메모리 런타임을 제공해 대기, 시그널, 재시도, 완료를 시험할 수 있게 합니다.

## 상세

Skipper는 이미 Airbnb의 여러 팀이 운영 환경에서 사용하고 있으며, 저자들은 여러 단계 프로세스를 소유한 Java나 Kotlin 서비스가 기존 배포 구조 안에서 내구성 있는 실행을 원할 때, 특히 새 프로세스마다 재시도 작업과 상태 테이블, 폴링 루프를 직접 유지하는 상황을 대체할 때 적합하다고 설명합니다. 정상 경로에서 워크플로는 저장된 상태와 예약된 복구 작업을 바탕으로 서비스 프로세스 안에서 바로 실행될 수 있어, 액션 사이마다 외부 오케스트레이터로 왕복할 필요가 없습니다. 다만 데이터베이스 접근과 하위 시스템 호출은 여전히 지연 시간에 영향을 줍니다. 내구성이 모든 비즈니스 작업의 성공을 보장하지는 않으며, 워크플로를 실행하고 복구하는 책임이 이제 해당 팀에 있다는 점을 저자들은 강조합니다.

앞으로는 Postgres나 DynamoDB 같은 저장소 플러그인을 추가하고 워크플로 진화와 재실행 디버깅 도구를 개선할 계획입니다. 자동 호환성 검사, 마이그레이션 지원, 더 명확한 재실행 시각화 같은 외부 기여도 재실행 기반 엔진에서 흔한 문제를 푸는 데 도움이 될 것이라고 밝힙니다. 엔진을 어떻게 만들었는지는 이전 심층 글이 다루고, 이번 발표는 아키텍처와 워크플로 개발 도구 생태계에서 Skipper의 위치에 초점을 맞춥니다.
