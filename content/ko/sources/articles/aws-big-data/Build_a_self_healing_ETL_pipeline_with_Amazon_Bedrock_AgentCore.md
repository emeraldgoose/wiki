# Amazon Bedrock AgentCore로 자가 치유 ETL 파이프라인 구축

**원문**: [AWS 빅데이터 블로그](https://aws.amazon.com/blogs/big-data/build-a-self-healing-etl-pipeline-with-amazon-bedrock-agentcore) · **게시일**: 2026-11-13

## 개요

ETL 파이프라인은 조용히 망가진다. 스키마 드리프트, 누락된 필드, 타입 불일치가 하류 분석을 오염시키고, 전형적인 대응은 수동이다. 오류를 감지하고, 분류하고, 레코드를 고치고, 코드를 수정하고, 재배포한다. 데이터 양이 늘수록 이 감지-분류-수정-배포 주기는 감당되지 않는다. 이 글의 패턴은 Amazon Bedrock AgentCore와 AWS Glue 위에 세운 자가 치유 파이프라인으로, 도메인 지식으로 잘못된 레코드를 스스로 고치고 수정본을 데이터 레이크에 저장하며, 선택적으로 같은 오류가 재발하지 않도록 풀 리퀘스트를 제안한다.

실행 예제는 15가지 스키마 유형의 미국 해양대기청(NOAA) 기상 레코드를 흡수하는 가상의 날씨 시스템이다. 여기에는 기온, 강수량, 풍속, 기압, 습도, 가시거리, 운량, 일사량 등이 포함된다. AWS Glue ETL 작업이 품질 관문 역할을 한다. 각 스키마 유형을 전용 검증기에 연결하는 디스패처로 레코드를 검증하며, 검증기는 필수 필드, 데이터 타입, 열거값, 수치 제약을 확인한다. 실패한 레코드는 오류 유형(누락 필드, 타입 불일치, 스키마 위반, 잘못된 형식)으로 분류돼 데드레터 큐 대신 에이전트 시스템으로 라우팅된다.

수정 지식은 서로 보완적인 두 소스에서 나오고, 신뢰도 임계값과 사람 알림 대체 경로가 이 자율적 행동에 대한 기본 감독을 제공한다. 글은 아키텍처, AWS Cloud Development Kit을 이용한 배포, 전후 레코드 비교가 담긴 수정 워크플로 테스트를 다룬다.

## 핵심 내용

- 네 개의 에이전트가 각 오류를 처리한다. 오케스트레이터가 순차 워크플로를 조율하고, 데이터 수정 에이전트가 높은 신뢰도의 수정을 적용하며, 데이터 저장 에이전트가 수정된 레코드를 되돌려 쓰고, 코드 개선 에이전트가 소스 단계의 수정을 제안한다.
- 각 에이전트는 Strands Agents SDK로 만든 컨테이너 애플리케이션이며 AgentCore 런타임으로 배포된다.
- 오케스트레이터는 최소 70퍼센트 신뢰도로 수정할 수 없을 때 사람 알림으로 우아하게 전환하고, 단계가 실패하면 나쁜 데이터를 하류로 흘려보내지 않고 멈춘다.
- 수정 에이전트는 두 지식 소스를 저울질한다. 자연어 질의에 답하는 관리형 RAG 서비스인 Amazon Bedrock Knowledge Bases(Amazon S3 Vectors와 Amazon Titan Embeddings V2에 기반)와, 신뢰도 점수가 적힌 사전 계산 수정 전략 파일을 correction/{schema_type}/{error_type}.json 경로에서 직접 조회하는 S3 Vectors다. 예제 파일의 점수는 0.85였다.
- 에이전트는 점수가 높은 쪽을 고른다(사전 계산 S3 파일의 0.85가 지식 기반의 0.78을 이겼다). 기본 임계값 0.7을 넘으면 수정을 적용하고, 넘지 못하면 오케스트레이터가 Amazon SNS 알림으로 수동 검토를 요청한다.
- S3 Vectors는 알려진 오류 조합에 모델 추론 없이 즉각적이고 결정적인 수정을 주고, 지식 기반은 NOAA 데이터 안내서, 스키마 정의, 오류 패턴 카탈로그 같은 도메인 문서를 근거로 처음 보는 패턴까지 추론한다.
- 수정된 레코드는 원래 필드를 유지하며 선택된 수정 전략이 주석으로 붙고, 저장 에이전트가 transformed와 corrected 두 영역에 모두 기록해 하류 소비자와 감사자가 무엇이 잘못됐고 어떻게 고쳐졌는지 볼 수 있게 한다.
- S3 데이터 레이크는 세 영역으로 나뉜다. raw/는 생산자가 쓴 수정 없는 원본 감사 기록, transformed/는 Glue ETL 작업과 저장 에이전트가 쓴 검증 통과 레코드, corrected/는 수정 메타데이터가 붙은 수정 레코드다.
- 코드 개선 에이전트는 AWS Secrets Manager에 저장된 자격 증명으로 저장소를 읽고, 오류 유형·스키마 유형·적용된 수정을 연관 지어 상류 코드를 찾아내며, 기존 검증을 유지하는 변경을 생성해 GitHub MCP Server로 풀 리퀘스트를 낸다. 저장소 자격 증명이 없으면 개선을 건너뛰었다고 기록할 뿐이다.
- 배포는 AWS CDK(Python)의 cdk deploy 한 번으로 끝난다. CodeBuild가 ARM64 컨테이너 이미지를 빌드하고 지식 기반이 생성되며, AgentCore 런타임 넷이 프로비저닝되고, 지식 소스는 저장소의 knowledge_base/ 폴더에서 자동으로 채워진다.
- 사전 조건: 대상 리전에서 Anthropic Claude(에이전트 추론)와 Amazon Titan Embeddings V2(지식 기반 인덱싱) 모델 접근 활성화, Python 3.10+가 있는 AWS CDK CLI, 로컬 컨테이너 빌드용 Finch 또는 Docker, 모든 리소스를 단일 리전에 배치.
- 정리는 cdk destroy --all로 한다. 스택을 의존성 역순으로 삭제하고, autoDeleteObjects로 버킷을 비우고, ECR 컨테이너 이미지를 지우고, S3 Vectors 버킷과 인덱스를 삭제하며, 저장소 자격 증명이 든 Secrets Manager 시크릿을 강제 삭제한다.

## 세부 사항

### 검증과 오류 라우팅

Glue ETL 작업의 디스패처는 15가지 스키마 유형 각각을 전용 검증기에 연결한다. 실패에는 error_type과 error_details 페이로드가 실리며, 오케스트레이터가 받는 것은 바로 이 페이로드다. 수정이 인라인으로 일어나므로 레코드는 수동 분류를 기다리는 데드레터 큐에 머무르지 않고 소비자에게 계속 흘러간다.

### 수정 결정 로직

수정 에이전트는 지식 기반과 S3 수정 파일을 병렬로 조회하고 신뢰도 점수를 비교한다. 추적된 예제에서는 두 소스가 모두 전략을 돌려줬고, S3 Vectors 파일이 0.85로 0.78보다 높았으며, 0.7 임계값을 통과해 수정이 적용됐다. 신뢰도가 낮으면 설정된 이메일 주소로 오류 세부 정보를 담은 SNS 알림을 보내 수동 검토로 넘긴다. 임계값은 스키마별이나 오류 유형별로 조정할 수 있다.

### 소스에서의 코드 개선

재발하는 오류는 데이터 레이크에서만 고치는 것이 아니라 소스에서 고쳐지므로, 상류 코드가 개선됨에 따라 파이프라인의 오류율이 낮아진다. 에이전트는 브랜치를 만들고 제안 변경을 커밋하며, 설명에 근본 원인 분석을 넣은 풀 리퀘스트를 연다. 선택적인 저장소 연동에는 배포 시점의 git_repo_url 컨텍스트 값과 제공 스크립트로 설정하는 토큰이 필요하다.

### 설계 결정

네 에이전트는 관심사의 분리를 강제한다. 수정 전략은 저장 로직을 건드리지 않고 갱신할 수 있고, 낮은 신뢰도 알림은 수정 로직과 무관하게 오케스트레이터에 산다. 두 지식 소스의 역할도 뚜렷하다. 지식 기반은 보지 못한 오류 조합의 긴 꼬리를 담당하고, S3 Vectors는 흔한 사례를 결정적 속도로 담당한다. 잘못된 수정은 수정하지 않는 것보다 나쁘다는 판단이 바로 신뢰도 임계값에 담겨 있다.
