# 46% 적은 노드, 2배 빠른 인덱싱: Amazon OpenSearch Service에서의 Confluent

**원문**: [AWS Big Data Blog](https://aws.amazon.com/blogs/big-data/46-fewer-nodes-2x-faster-indexing-confluent-on-amazon-opensearch-service) · **게시일**: 2026-11-10

## 개요

Apache Kafka의 원 개발자들이 세운 회사이자 현재 IBM의 일부인 Confluent는 내부 로깅 시스템을 Amazon OpenSearch Service에서 운영하며, Kafka·Connect·Flink 플릿을 지원하기 위해 하루 수백 테라바이트의 로그를 수집한다. 이 규모에서는 인덱싱 작업이 핫 티어의 부하를 지배하기 때문에, 엔지니어링 팀은 더 저렴한 하드웨어로 옮길 수 있는지가 아니라 노드 한 대가 얼마나 더 많은 수집량을 감당할 수 있는지를 문제로 삼았다. 글은 로컬 NVMe를 덧붙인 형태의 이전 세대 범용 Graviton2 인스턴스인 r6gd에서, OpenSearch를 위해 설계된 최신 인스턴스 패밀리인 oi2로 핫 티어를 "측정 우선" 방식으로 이전한 과정을 정리한다.

핵심 지렛대는 인스턴스 교체 자체다. oi2에서는 로컬 NVMe가 별도의 Amazon EBS 볼륨 없이 주 저장 계층으로 동작한다. 데이터는 로컬에 기록되면서 내구성(11 nines)을 위해 Amazon S3로 동기 복제되고, 저장·네트워크 경로가 인덱싱과 병합 입출력에 맞춰 통합되어 있다. 또한 OpenSearch 전용 인스턴스는 논리적(문서 단위) 복제 대신 물리적(세그먼트 단위) 복제를 사용해, 데이터를 프라이머리 사본에서만 인덱싱하고 이미 S3에 저장된 세그먼트를 복사해 나머지 사본을 만든다. 이렇게 하면 복제본에서의 중복 인덱싱 작업과 프라이머리의 네트워크 부담이 사라진다. 운영상 주의할 점도 있다. 복제본을 구성한 상태에서는 보고되는 인덱싱 속도가 실제보다 낮게 보일 수 있다. 초당 1,000건으로 표시되는 도메인이 실제로는 2,000건을 인덱싱하고 있을 수 있는데, 인덱싱이 프라이머리 샤드에서만 일어나기 때문이다.

각 도메인은 용량을 줄이기 전에 새 인스턴스의 효율을 실제 운영 환경에서 측정할 수 있도록 두 단계로 현대화했다. 1단계는 노드 수를 그대로 둔 채 인플레이스 블루/그린 재프로비저닝으로 인스턴스 타입만 교체하는 단계로, 같은 노드 수에서 oi2는 동일한 수집량에 대해 r6gd의 약 3분의 1 수준의 CPU를 사용해 노드당 여유가 약 2.7배였다. 2단계는 이 여유를 단계적으로 노드를 제거하며 소비하는 적정 규모화로, 각 단계마다 클러스터 상태를 확인하며 진행하다 한계 기준에 부딪혔다. 그 기준은 CPU가 아니라 JVM 힙이었다. 힙 압박은 쿼리 패턴을 따르는데, 노드를 줄이면 같은 샤드가 더 적은 노드에 몰리기 때문이다. 결과적으로 플릿은 노드 수가 절반 가까이로 통합됐고, oi2 노드 한 대는 r6gd 노드의 약 1.9배 부하(168 ÷ 90)를 감당하면서도 인덱싱은 오히려 빨라졌다.

## 핵심 내용

- 플릿 규모가 r6gd 168대에서 oi2 90대로 46% 줄었고, 도메인별 감축 폭은 31~60%였다.
- 인덱싱 지연은 네 개 도메인 모두에서 대략 절반으로 줄어, r6gd의 약 0.18~0.19ms에서 oi2의 약 0.08~0.10ms가 됐다.
- 쓰기 백프레셔가 해소됐다. r6gd 도메인은 모두 8~38개의 대기 연산이라는 두 자릿수 쓰기 큐를 안고 있었지만, oi2의 네 도메인은 모두 약 1 미만으로 떨어졌다.
- 노드 수를 크게 줄였는데도 네 도메인 중 세 곳에서 CPU 사용률이 내려갔다. 예를 들어 도메인 B는 노드가 절반이 된 상태에서 60%에서 40%로 낮아졌다.
- 적정 규모화의 하한은 CPU가 아니라 힙이 정했다. oi2는 노드당 힙이 r6gd와 같아서, 샤드를 더 적은 노드에 몰아넣자 모든 도메인에서 평균 힙 사용량이 상승했다.
- 도메인 D는 솔직한 예외 사례다. 부하 대비 가장 크게 줄인 도메인으로 CPU가 43%에서 56%로 올랐고, 쓰기 큐도 유일하게 0에 가깝지 않다. 피크 트래픽을 지켜봐야 하는 도메인으로 지목된다.
- 안정성은 유지됐다. 최종 상태에서 쓰기 및 프라이머리 쓰기 거부가 0건이었고 모든 클러스터가 정상 상태였다.
- 노드 단가가 더 비싼데도 비용은 줄었다. 약 46%의 통합이 oi2의 단가 프리미엄을 상쇄하고도 남아, 온디맨드 기준 핫 티어 비용이 약 18% 낮아진 것으로 추정된다. 최종 규모를 1년 예약 인스턴스로 약정하면 기존 r6gd 온디맨드 기준선보다 약 47~51% 낮아질 것으로 추정된다.

## 상세

운영 지표는 동일한 작업량을 비교한 것이다. 같은 수집량에서 r6gd의 7일 기준선과 최종 노드 수의 oi2 24시간 구간을 비교했고, R8gd는 벤치마크하지 않았다. 평가는 로그 분석 수집과 스토리지 경제성을 위해 설계된 oi2 패밀리에 의도적으로 집중했으며, 참고 수치는 AWS 내부 벤치마크에서 가져왔다. 여기서 oi2는 OR2 인스턴스보다 최대 9%, I8g보다 최대 33% 높은 인덱싱 처리량을 낸다. oi2 패밀리는 large부터 24xlarge까지 제공되며 최대 22.5TB의 스토리지를 갖추고, 각 인스턴스는 컴퓨트와 함께 캐싱용 3세대 AWS Nitro SSD, Amazon S3 기반 원격 관리 스토리지를 묶어 제공한다.

인덱싱 처리량을 최대화하려는 팀을 위해 저자들은 버퍼 활용도를 높이는 큰 벌크 크기(10MB), 병렬 처리를 위한 다중 클라이언트, 처리량을 위한 프라이머리 샤드 추가(다만 과도한 샤딩은 노드당 샤드 밀도를 높여 역효과), 그리고 10초 이상의 리프레시 간격 유지(전용 인스턴스의 기본값이 10초)를 권한다. 비용 수치는 온디맨드 가격 기준의 대략적인 정가 기반 비율이며, 예약 인스턴스 값은 견적 미확정 상태의 추정치다. 스토리지 계층(UltraWarm과 스냅샷)과 전용 마스터 계층은 변동이 없어 비교에서 제외했다. 저자들이 뽑은 결론은 인스턴스 단가가 아니라 작업 단위당 효율을 최적화하고, 용량을 줄이기 전에 실제 규모 판단 신호(이 경우 힙)를 먼저 따르라는 것이다.
