# Amazon Redshift의 Apache Iceberg 테이블을 위한 다중 문장 트랜잭션

**원문**: [AWS 빅데이터 블로그](https://aws.amazon.com/blogs/big-data/multi-statement-transactions-for-apache-iceberg-tables-in-amazon-redshift) · **게시일**: 2026-11-13

## 개요

데이터 파이프라인은 한 테이블을 여러 단계로 변경하는 경우가 많습니다. 당일 매출을 업서트한 뒤 취소된 주문을 삭제하는 식입니다. 지금까지 Amazon Redshift에서 Iceberg 테이블에 대한 쓰기는 문장 하나하나가 각자 커밋되었습니다. 문장 사이의 중간 상태가 외부에 공개되고, 한 단계가 실패하면 절반만 반영된 테이블이 깔끔하게 되돌릴 수 없는 채로 남았으며, N개 문장짜리 작업은 카탈로그 갱신 비용을 N번 지불했습니다. Redshift는 Iceberg 테이블 생성, INSERT 쓰기, DELETE·UPDATE·MERGE에 의한 행 수정, Iceberg 테이블로 저장되는 머터리얼라이즈드 뷰, 겹치지 않는 동시 쓰기 커밋을 이미 지원하고 있었지만, 항상 문장 단위였습니다.

다중 문장 트랜잭션이 이 상황을 바꿉니다. 하나의 Iceberg 테이블에 대한 여러 데이터 조작 언어(DML) 문장을 단일 BEGIN…COMMIT 안에서 실행하면, Amazon Redshift가 배치 전체를 카탈로그 갱신 한 번으로 하나의 Iceberg 스냅샷으로 발행합니다. 다른 세션과 다른 엔진의 읽기는 배치 이전 또는 이후 상태만 보지, 중간 상태는 절대 보지 못합니다. 실패하거나 롤백된 트랜잭션은 되돌릴 것 자체를 남기지 않습니다. 이 기능은 Patch 206 이상에서 사용할 수 있고 새로운 문법이 필요 없습니다.

글은 야간 작업이 판매점(POS) 매출을 병합하고 취소 매출을 삭제하는 소매업 예제로 시작해, 두 단계와 데이터 품질 감사 쿼리를 하나의 트랜잭션으로 감싸고 검증이 통과할 때만 커밋하는, 일반 SQL로 구현한 세션 범위의 쓰기-감사-발행(write-audit-publish) 패턴을 보여 줍니다. 이어서 트랜잭션이 허용하는 문장의 종류, 동시 읽기·쓰기에 대한 보장, 고아 파일 정리, 그리고 측정된 성능을 다룹니다.

## 핵심 내용

- 하나의 Iceberg 테이블에 대한 여러 DML 문장(INSERT, UPDATE, DELETE, MERGE)을 BEGIN…COMMIT 안에서 실행하면 COMMIT 시점에 하나의 스냅샷으로 발행됩니다. Iceberg DML은 다중 문장 명령 문자열과 프리페어드 스테이트먼트, Amazon Redshift JDBC 드라이버 경로에서도 허용됩니다.
- 트랜잭션 안의 모든 쓰기는 같은 Iceberg 테이블로 향해야 합니다. 두 번째 Iceberg 테이블에 대한 쓰기, RMS나 임시 테이블 DML, COPY, UNLOAD, GRANT, REVOKE, ANALYZE, 기타 DDL은 거부되고, 저장 프로시저 안의 Iceberg 쓰기도 거부됩니다.
- BEGIN…COMMIT 안의 단일 Iceberg DDL 문장은 예전에는 성공했지만 이제 거부됩니다. Iceberg DDL은 독립 문장으로 실행해야 하며 기존 워크로드의 동작이 바뀌는 부분입니다.
- 하나의 물리 테이블을 서로 다른 두 외부 스키마로, 또는 외부 스키마와 awsdatacatalog로 참조하면 두 개 테이블로 간주되어 두 번째 이름을 통한 쓰기는 거부됩니다. Redshift는 테이블을 참조 방식으로 식별합니다.
- 같은 이름을 쓰는 한 자신이 쓰고 있는 테이블에 대한 읽기는 미커밋 변경을 포함해 보여 줍니다. 각 Iceberg 테이블의 첫 읽기가 이후 트랜잭션 내내 그 버전을 고정하며(반복 가능 읽기), 트랜잭션 도중 처음 읽는 테이블은 트랜잭션 시작 이후 다른 세션이 커밋한 내용을 포함할 수 있습니다.
- 충돌 해결은 모든 다중 문장 트랜잭션에 적용됩니다. 다른 쓰기와 변경 집합이 겹치지 않으면 Redshift가 트랜잭션을 최신 테이블 버전 위로 리베이스해 문장을 다시 실행하지 않고 하나의 스냅샷으로 커밋하고, 진짜 충돌(같은 데이터 변경)만 커밋 실패로 이어지며 애플리케이션이 재시도합니다.
- 작은 문장 25개를 커밋 하나로 묶으면 문장별 커밋 대비 INSERT는 14.77%, DELETE는 11.29% 총 실행 시간이 줄었습니다. 절반 이상의 개선(9.20%와 6.21%)은 커밋당 4문장에서 이미 나타납니다.
- 쓰기 플로우 1개일 때 트랜잭션은 오토커밋보다 1.18배 많은 문장을 커밋하고, 동시 쓰기 32개에서는 오토커밋이 단일 쓰기 대비 2.89배, 트랜잭션은 10.37배에 이르러 같은 시간에 3.59배 많은 문장이 커밋됩니다.
- 각 문장이 이미 무거운 데이터 작업을 수행한다면 묶어도 체감할 만한 이득이 없습니다. 커밋 시간 절약이 너무 작습니다.
- 커밋되지 않은 트랜잭션이 남긴 중간 파일은 고아 파일이 됩니다. S3 Tables 버킷은 미참조 파일 제거가 기본 활성화되고, AWS Glue Data Catalog 테이블은 고아 파일 삭제 테이블 옵티마이저를 활성화해야 하며, 활성화 이후 생성된 파일만 제거하므로 도입 전에 켜야 합니다.

## 세부 사항

### 트랜잭션 안에 허용되는 것들

허용 범위는 의도적으로 좁습니다. 데이터베이스 전반의 Iceberg, Redshift 관리형 스토리지(RMS), 외부 테이블 읽기는 허용됩니다. 하나의 Iceberg 테이블에 대한 INSERT, UPDATE, DELETE, MERGE는 허용되고 COMMIT 시 하나의 스냅샷으로 발행됩니다. 하나의 Iceberg 머터리얼라이즈드 뷰에 대한 REFRESH MATERIALIZED VIEW는 허용되며, 이 뷰가 트랜잭션의 쓰기 대상이 됩니다. 나머지는 모두 거부입니다. 두 번째 Iceberg 테이블에 대한 쓰기, RMS나 임시 테이블 DML, COPY, UNLOAD, GRANT, REVOKE, ANALYZE, 기타 DDL, 그리고 CREATE TABLE, CREATE TABLE AS, ALTER TABLE, CREATE MATERIALIZED VIEW, DROP TABLE, DROP MATERIALIZED VIEW 같은 Iceberg 테이블 DDL이 거부됩니다. 거부된 문장은 실패하며 트랜잭션을 중단시키므로 그 전에 실행된 것도 발행되지 않습니다. 예제의 야간 작업은 pos_sales와 pos_voids Iceberg 테이블을 읽고 sales 테이블만 쓰기 때문에 이 규칙에 맞고, 스테이징 테이블 정리는 COMMIT 이후에 해야 합니다.

### 읽는 사람과 쓰는 사람을 위한 세 가지 보장

원자적 발행: 다른 세션과 엔진은 COMMIT까지 어떤 변경도 보지 못하고, 그 뒤에는 모든 변경을 하나의 스냅샷으로 봅니다. 자기 쓰기 읽기: 같은 이름을 쓰는 한 쓰기 중인 테이블의 읽기에 미커밋 변경이 포함됩니다. 테이블별 반복 가능 읽기: 첫 읽기가 해당 테이블의 버전을 트랜잭션 나머지 동안 고정해, 다른 세션이 도중에 커밋해도 이후 읽기는 같은 데이터를 돌려줍니다. 각 테이블의 버전은 트랜잭션 시작이 아니라 첫 읽기 시점에 고정됩니다. 매출 병합 후에 발행한 매장 상세 조회에는 다른 세션이 그 사이에 stores 테이블에 넣은 삽입이 포함될 수 있습니다. RMS 테이블은 트랜잭션의 첫 문장에서 찍힌 자체 스냅샷을 따르며 Iceberg 카탈로그와 조율되지 않습니다.

### 성능 측정

실험 환경은 미국 동부(버지니아 북부) 리전(us-east-1)의 AWS Glue Data Catalog에 등록된 Iceberg 테이블 하나를 단일 Amazon Redshift 프로비저닝 클러스터에서 쓰는 구성이고, 쓰기 플로우당 세션 하나로 실행하며 실패한 커밋은 롤백 후 집계에서 제외했습니다. 지연 측정에서는 한 테이블에 작은 문장 500개를 실행했을 때 커밋당 25문장 묶음이 INSERT는 14.77%, DELETE는 11.29% 총 실행 시간을 줄였고, 커밋당 4문장에서 이미 절반 이상의 개선이 나왔습니다. 이득은 문장마다가 아니라 트랜잭션당 카탈로그 커밋 한 번을 지불하는 데서, 그리고 문장별 트랜잭션 오버헤드 감소에서 옵니다. 처리량 측정에서는 동시 쓰기 플로우 수를 늘려가며 오토커밋 단일 INSERT와 INSERT 4개짜리 트랜잭션을 비교했고, 결과는 단일 오토커밋 쓰기 플로우 기준으로 정규화한 초당 커밋 문장 수입니다. 동시성이 커질수록 이점이 커집니다. 두 구성 모두 초당 카탈로그 커밋 수는 어느 수준에서 평탄해지지만, 트랜잭션 커밋 하나가 문장 하나가 아니라 네 개를 실어 나르기 때문입니다.

### 도입과 정리 작업

커밋되지 않은 트랜잭션이 쓴 중간 파일은 어떤 스냅샷에도 참조되지 않는 고아 파일이 됩니다. S3 Tables는 테이블 버킷에 대해 미참조 파일 제거가 기본으로 활성화되어 있고, Glue Data Catalog 테이블은 고아 파일 삭제 테이블 옵티마이저를 활성화해야 하며, 이 옵티마이저는 활성화 이후 생성된 파일만 제거하므로 다중 문장 트랜잭션 사용을 시작하기 전에 켜야 합니다. 도입은 Patch 206 이상으로 업그레이드하는 것부터 시작하며, 관련 자료로 Iceberg 쓰기 지원 시작하기, 동시 쓰기 충돌 해결, Iceberg 머터리얼라이즈드 뷰 소개, Redshift에서 Iceberg 테이블 참조하기 문서가 소개됩니다.
