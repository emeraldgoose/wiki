# Apache Airflow

> 영문 원본: [/en/concepts/data-engineering/apache-airflow](/en/concepts/data-engineering/apache-airflow)

**Apache Airflow**는 데이터 파이프라인을 만들고 예약하고 감시하는 오픈소스 워크플로 오케스트레이션 플랫폼이다. 파이프라인은 파이썬으로 쓴 방향성 비순환 그래프(DAG)로 정의되고, 중앙 스케줄러가 예약하며, 워커들에 분산된 개별 태스크로 실행된다.

## 핵심 모델: DAG와 태스크

DAG는 의존 관계 간선으로 묶인 태스크들의 모음이며, Airflow는 모든 상위 태스크가 성공한 뒤에만(또는 설정한 트리거 규칙에 따라) 태스크가 실행되도록 보장한다. 핵심 속성은 다음과 같다.

- **비순환성**: 순환을 허용하지 않으므로 실행이 항상 끝나고 스케줄러가 태스크를 위상 순서로 배치할 수 있다.
- **설정으로서의 파이썬**: DAG 파일은 일반 소프트웨어처럼 버전 관리와 테스트와 리뷰를 거치는 파이썬 코드다. TaskFlow API(`@dag`와 `@task` 데코레이터)를 쓰면 상용구 없이 반환값이 XCom을 통해 태스크 사이로 흐른다.
- **설계부터 멱등성**: 각 DAG 실행은 논리 날짜(`data_interval`)를 가지므로, 백필과 재시도는 공유 상태를 바꾸는 대신 결정적인 파티션을 다시 계산한다.

가장 작은 DAG는 이렇게 생겼다. 추출 태스크가 API에서 로우를 가져오고, 변환 태스크가 그것에 의존하고, 적재 태스크가 변환에 의존한다. 추출이 실패하면 하류는 아무것도 실행되지 않고 실패한 태스크에 알림이 울린다.

## 아키텍처

### 스케줄러

스케줄러는 DAG 파일을 주기적으로 해석하고 예약에 따라 DAG 실행을 만들며 실행 가능한 태스크를 큐에 넣는다. 두뇌이지 근육은 아니다. 태스크 코드를 직접 실행하지 않는다. Airflow 2대부터 고가용 스케줄러가 여러 복제본으로 뜨고, 3대 계열은 대규모 해석 속도를 위해 스케줄러와 DAG 프로세서를 분리했다.

### 익스큐터

익스큐터는 태스크 프로세스가 어디에서 도는지 정한다.

| 익스큐터 | 태스크 실행 위치 | 적합한 경우 |
|----------|-----------|----------|
| LocalExecutor | 로컬 프로세스 | 단일 노드와 작은 팀 |
| CeleryExecutor | 분산 Celery 워커 | 전통적인 수평 확장 |
| KubernetesExecutor | 태스크당 하나의 파드 | 탄력적이고 격리된 클라우드 네이티브 |
| Edge와 원격 | 원격 플릿 | 하이브리드와 엣지 배포 |

익스큐터 선택이 가장 큰 확장 수단이다. Local에서 Celery나 Kubernetes로 옮기면 수십 개 수준이던 동시 태스크가 수천 개 수준으로 늘어난다.

### 메타데이터 데이터베이스와 웹서버

모든 상태(DAG 실행과 태스크 인스턴스와 변수와 연결 정보와 XCom)는 메타데이터 데이터베이스, 보통 PostgreSQL에 산다. 웹서버는 이 데이터베이스를 바탕으로 사용자 화면(격자 보기와 간트와 로그)과 REST API를 보여준다. 메타데이터 데이터베이스는 빠른 저장 장치에 두고 주기적으로 정리한다. 비대해진 메타데이터 데이터베이스가 스케줄러 둔화의 가장 흔한 원인이다.

## 구성 요소

### 오퍼레이터

오퍼레이터는 작업 한 단위를 감싼다. 호출 가능 객체용 `PythonOperator`, 셸용 `BashOperator`, 관리형 서비스용 제공자 오퍼레이터(`S3ToRedshiftOperator`와 `BigQueryInsertJobOperator`와 `KubernetesPodOperator`)가 있다. 오래 기다리는 작업(API 폴링이나 클러스터 기동)은 지연 가능 오퍼레이터를 쓴다. 대기 중 워커 슬롯을 내놓아 실질 처리량이 크게 오른다.

### 센서

센서는 외부 조건(파일 도착이나 테이블 파티션 준비나 API 상태 전환)이 참이 될 때까지 찌른다. 멈춘 센서가 워커를 몇 시간씩 붙잡지 않도록 `poke_interval`과 `timeout`과 `mode="reschedule"`을 항상 설정한다.

### 훅과 연결 정보와 변수

- **훅**: 재시도와 연결 처리를 갖춘 외부 시스템 클라이언트 감싸개이며, 오퍼레이터는 훅 위의 얇은 감싸개다.
- **연결 정보**: 자격 증명과 접속 지점을 저장한다. 기본 저장소보다 Vault나 클라우드 비밀 관리 같은 비밀 백엔드를 쓴다.
- **변수**: 작은 JSON 설정을 담는다. 큰 데이터용이 아니며, 큰 데이터는 객체 저장소에 두고 참조로 전달한다.

### XCom

XCom은 태스크 사이에서 작은 값(식별자와 경로와 로우 수)을 주고받는다. 기본 백엔드는 메타데이터 데이터베이스에 저장하므로 데이터프레임이나 파일 내용을 XCom으로 보내면 안 되고 S3나 GCS 주소를 보낸다. 사용자 XCom 백엔드를 쓰면 값을 객체 저장소로 투명하게 보낼 수 있다.

## 예약 의미

- **벽시계가 아니라 데이터 구간**: 자정 시작 일간 DAG는 구간이 닫힌 뒤에 실행되므로, 2026-09-06 표시 실행은 그날 하루 완성 데이터를 처리한다.
- **따라잡기와 백필**: `catchup=True`이면 `start_date` 이후 놓친 구간마다 실행을 만든다. 과거 재처리는 명령줄이나 화면에서 명시적 백필로 일으키고 실패한 태스크 재실행 의미를 함께 쓴다.
- **시간표**: 크론 프리셋에 더해 영업일 달력과 복수 크론과 이벤트 기반 트리거용 사용자 시간표를 쓴다. Airflow 3은 일급 이벤트 기반 예약을 넣어 객체 저장소 이벤트가 직접 실행을 일으킬 수 있다.

## 운영 수칙

- **서비스 수준과 알림**: 지연에 민감한 태스크에 `sla`를 걸고 `on_failure_callback` 웹훅(PagerDuty와 Slack)을 단다. 호출 가능 객체 안에서 예외를 다루어 재시도 가능한 오류(일시적 API 429)와 치명 오류를 구분한다.
- **풀과 우선순위**: 풀은 깨지기 쉬운 원본에 대한 동시 접속을 묶는다(예로 구형 전사 자원 시스템에 최대 3연결). 슬롯이 모자랄 때는 `priority_weight`가 태스크 순서를 정한다.
- **테스트**: 태스크 호출 가능 객체는 일반 pytest로 단위 테스트하고, DAG 무결성 테스트는 모든 DAG 파일의 가져오기 오류 없음과 순환 없음과 담당자와 sla 규칙을 지속적 통합에서 검사한다.
- **업그레이드**: 제공자 꾸러미는 코어와 따로 고정하고, 부 버전마다 깨지는 변경점을 읽는다. 오퍼레이터 서명이 계속 바뀌기 때문이다.

## Airflow와 이웃 도구

- [[stream-processing|스트림 처리]] 도구인 [[apache-flink|Flink]]과 비교하면, Airflow는 배치 단계를 예약 따라 엮고 Flink는 이벤트를 연속 처리한다. 경쟁이 아니라 조합이다(Airflow가 Flink 작업을 일으킨다).
- Dagster 같은 자산 중심 오케스트레이터는 모델이 반대다(데이터 자산을 정의하고 DAG를 끌어낸다). Airflow는 태스크 중심이라 갈래가 많은 추출 변환 적재 순서에 맞는다.
- dbt는 웨어하우스 안 SQL 변환을 맡고, Airflow는 dbt 주변(앞의 수집, 뒤의 품질 검사와 역방향 추출 변환 적재)을 엮는다.
