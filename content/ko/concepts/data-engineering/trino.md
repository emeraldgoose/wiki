# Trino

**Trino**(구 PrestoSQL, 2020년 페이스북 Presto에서 포크)는 서로 다른 저장소를 아우르는 대화형 분석용 분산 SQL 쿼리 엔진이다. 데이터 레이크, 웨어하우스, NoSQL, 이벤트 스트림 위에 연합 ANSI SQL을 메모리 속도로 실행하며, 자체 스토리지는 보유하지 않는다.

## 위치

Trino는 컴퓨트와 스토리지를 분리한다. 자체 API를 갖춘 완전한 처리 프레임워크인 [[apache-spark|Spark]]와 달리, Trino는 한 가지에 집중한다. 데이터가 있는 자리에서 SQL을 빠르게 답하는 것이다. 단일 쿼리로 S3 위 [[apache-iceberg|Iceberg]] 테이블, Postgres 차원 테이블, Elasticsearch 인덱스를 조인할 수 있으며, 타입 변환, 분산 조인, 각 소스로의 부분 푸시다운을 Trino가 처리한다.

## 아키텍처

### 코디네이터와 워커

- **코디네이터**: SQL을 파싱하고 쿼리를 계획 및 최적화한 뒤 스테이지를 워커에 스케줄링한다. UI와 REST API도 제공한다. 액티브-스탠바이 구성 또는 장애 조치용 코디네이터를 두어야 하며, 코디네이터가 죽으면 실행 중인 쿼리가 모두 중단된다.
- **워커**: 파이프라인 스테이지를 실행하고 중간 페이지를 네트워크로 교환한 뒤 결과를 스트리밍으로 반환한다. 워커는 상태가 없어 수평 확장이 가능하다. 노드를 추가하면 스캔 중심 쿼리에서 오브젝트 스토어나 셔플 대역폭이 포화하기 전까지 대체로 선형에 가까운 속도 향상을 얻는다.
- **디스커버리**: 워커가 서비스 디스커버리를 통해 코디네이터에 등록되므로, 쿠버네티스에서 설정 파일을 고치지 않고 오토스케일이 가능하다.

### 실행 모델

Trino는 쿼리 스테이지마다 파이프라인 방식의 벡터화 연산자로 컴파일하여 워커 스레드에서 벌케이노 스타일 풀 루프로 실행한다. 데이터는 CPU 캐시 크기에 맞춘 압축 컬럼형 페이지 단위로 이동하며, 메모리 한계에 도달했을 때만 디스크로 스필한다. 장애 허용은 Spark식 스테이지 재계산이 아니라 쿼리 재시도 단위이므로, Trino는 수 시간짜리 ETL이 아니라 수 분 이내 대화형 쿼리를 겨냥한다.

## 커넥터

커넥터가 Trino의 핵심 무기이다. 외부 시스템을 메타데이터 매핑과 조건 및 프로젝션 푸시다운을 갖춘 SQL 테이블처럼 노출한다.

| 커넥터 | 소스 | 비고 |
|-----------|--------|-------|
| Hive / Iceberg / Delta / Hudi | 데이터 레이크(S3, GCS, ADLS) | 컬럼형 스캔, 파티션 프루닝, 동적 필터링 |
| Postgres / MySQL | 관계형 데이터베이스 | 안전한 경우 조인 푸시다운, 원본 부하 주의 |
| Kafka | 이벤트 스트림 | 토픽당 테이블, 오프셋을 가상 컬럼으로 제공 |
| Elasticsearch / OpenSearch | 검색 인덱스 | 전문 검색 조건 푸시다운 |
| BigQuery / Snowflake / Redshift | 웨어하우스 | 기존 마트에 대한 연합 쿼리 |

푸시다운 품질이 성능을 결정한다. `WHERE date = ...`를 파티션 프루닝으로 밀어내는 커넥터는 메가바이트만 스캔하지만, 그렇지 못한 커넥터는 테라바이트를 스캔한다. `EXPLAIN`으로 필터가 원본까지 도달하는지 항상 확인하라.

## 비용 기반 옵티마이저

Trino의 비용 기반 옵티마이저(CBO)는 테이블과 컬럼 통계를 이용해 조인 순서를 정하고, 브로드캐스트와 파티션 교환을 선택하며, 집계 위치를 결정한다. 구체적으로는 다음과 같다.

- **통계**: 대형 레이크 테이블에 `ANALYZE`를 실행하여 플래너가 행 수와 NDV를 알도록 한다. 오래된 통계가 갑작스러운 플랜 성능 저하의 주원인이다.
- **조인 전략**: 작은 차원 테이블은 모든 워커에 브로드캐스트하고(셔플 없음), 큰 테이블끼리의 조인은 키 기준으로 리파티셔닝한다. 자동이지만, 쏠린 키는 솔티드 사전 집계나 필터링된 세미 조인으로 따로 다뤄야 한다.
- **동적 필터링**: 실행 시점에 조인의 빌드 측이 블룸 필터를 프로브 측 스캔으로 보내, 읽기 전에 통째로 스플릿을 건너뛴다. 이 기능 하나로 레이크 쿼리 입출력량이 한 자릿수 배율로 줄어드는 경우가 많다.

## 메모리와 동시성 관리

운영 클러스터의 성패는 리소스 그룹에 달려 있다. 쿼리 부류(대화형 BI, 배치 리포트, ETL 서비스 계정)마다 메모리 상한, 동시 실행 제한, 우선순위를 부여하는 JSON 기반 큐이다. 쿼리당 메모리 제한과 클러스터 전체 스필 정책을 함께 설정하라. 폭주하는 카테시안 조인 하나가 클러스터를 멈추게 해서는 안 되며, 대기열에 머물거나 실패해야 한다. 작은 쿼리를 많이 공유하는 고동시성 모드와 대형 스캔 몇 개를 도는 배치 모드는 구분하여 운영한다.

## 보안과 거버넌스

코디네이터에서 Kerberos 또는 OIDC 인증, 전 구간 TLS, Apache Ranger나 Open Policy Agent 플러그인을 통한 세밀한 접근 제어로 컬럼과 행 필터 단위까지 통제한다. BI 도구가 하나의 커넥션 풀을 공유할 때는 Trino 서비스 사용자에 최종 사용자 정체성을 매핑하는 가장 체인으로 감사 추적을 정확히 유지한다.

## Trino와 이웃 기술 비교

- **Spark SQL과 비교**: 대화형 지연 시간과 연합 쿼리는 Trino가 이기고, 수 시간짜리 배치, ML 파이프라인, 세밀한 복구는 Spark가 이긴다. 많은 레이크하우스가 같은 Iceberg 테이블 위에 둘을 함께 둔다.
- **Flink과 비교**: Trino는 유한 스냅샷을 쿼리하고, [[apache-flink|Flink]]는 무한 스트림을 처리한다. Trino와 Iceberg 조합은 분 단위 최신성의 준실시간 분석을, Flink는 초 이하 단위를 담당한다.
- **웨어하우스 컴퓨트와 비교**(Snowflake, BigQuery): 웨어하우스는 스토리지와 컴퓨트를 묶어 탄력적으로 확장하고, Trino는 데이터가 이미 있는 자리에서 복사나 이그레스 없이 쿼리한다.

## 운영 실무

- 코디네이터 힙을 넉넉히 주고 GC 로그를 남긴다. 코디네이터 메모리 부족은 클러스터 전체 장애이다.
- 커넥터와 카탈로그 버전을 고정한다. 레이크 커넥터 업그레이드가 푸시다운 동작을 조용히 바꿀 수 있다.
- 오브젝트 스토어 지연이 병목이면 Alluxio나 RubiX식 로컬 SSD 캐싱으로 자주 읽는 Parquet과 ORC 스플릿을 캐시한다.
- 리소스 그룹별 대기 대 실행 쿼리를 모니터링한다. 대기가 지속되면 워커를 늘리거나 워크로드를 분리한다.
