# 가상 메모리

**가상 메모리(virtual memory)** 는 각 프로세스에게 크고 독자적이며 연속적인 주소 공간이라는 환상을 제공한다. OS와 MMU가 가상 페이지를 물리 RAM(또는 디스크)에 투명하게 매핑한다. 프로세스 격리, 효율적 메모리 사용, 메모리-매핑 파일의 기반 메커니즘이다.

## 정의

- **가상 주소 공간**: 프로세스가 사용할 수 있는 주소 집합 (x86-64 Linux에서 유저 공간 약 128 TB). **페이지**(보통 4 KB, huge page는 2 MB / 1 GB) 단위로 나뉜다.
- **물리 메모리**: 실제 RAM 프레임. **MMU**가 **페이지 테이블**을 통해 가상 주소를 변환하고, **TLB**(변환 색인 버퍼)가 최근 변환 결과를 하드웨어에 캐시한다.
- **페이징**: OS가 프로세스마다 다단계 페이지 테이블을 유지하며 가상 페이지 번호 → 물리 프레임 번호 + 권한 비트(읽기/쓰기/실행, 유저/슈퍼바이저, present)를 매핑한다.
- **요구 페이징/스와핑**: RAM에 없는 페이지는 **페이지 폴트**를 일으키고, 커널이 디스크에서 읽거나(또는 제로 페이지를 할당) 프로세스를 재개한다. 차가운 페이지는 스왑 영역으로 쫓겨날 수 있다.

## 왜 중요한가

- **격리**: 프로세스는 서로의 메모리를 지칭할 수 없다 — 프로세스 A의 포인터는 B에서 무의미하다. OS 보안·안정성의 하드웨어적 토대다.
- **오버커밋과 효율**: 프로세스는 일상적으로 물리 RAM보다 큰 가상 메모리를 매핑한다(성긴 힙, 지연 할당 스택, 한 번만 매핑되는 공유 라이브러리). 실제 손댄 페이지만 프레임을 차지한다.
- **단순한 프로그래밍**: 링커·로더는 고정 레이아웃(코드, 위로 자라는 힙, 아래로 자라는 스택, mmap 영역)을 보고, 프로그래머는 물리적 배치를 신경 쓰지 않는다.
- **성능 레버**: 페이지 크기, TLB 적중률, NUMA 배치, 스왑 동작이 메모리-바운드 워크로드 성능을 직접 좌우한다.

## 동작 원리

### 주소 변환 탐색 (x86-64, 4단계)

```
가상 주소 = [9비트 PML4][9비트 PDPT][9비트 PD][9비트 PT][12비트 오프셋]
CR3 → PML4 → PDPT → PD → PT → 프레임 + 오프셋 = 물리 주소
```

- 각 단계는 512개 8바이트 엔트리의 4 KB 테이블이다. 전체 변환은 최대 4번의 메모리 읽기가 필요해서 **TLB**(보통 ~64–1500 엔트리, L1/L2 분리)가 존재한다: 적중하면 탐색이 필요 없다.
- **Huge page**(2 MB/1 GB)는 단계를 합치고 TLB 도달 범위를 곱절로 늘린다(한 엔트리가 4 KB 대신 2 MB 커버). DB와 JVM이 TLB 미스 절감용으로 사용한다(`hugetlbfs`, Transparent Huge Pages).

### 페이지 폴트: 마이너 vs 메이저

- **마이너 폴트**: 페이지는 RAM에 있지만 아직 매핑 안 됨(익명 메모리의 첫 접근, COW 분리). 디스크 I/O 없이 테이블만 고치면 된다.
- **메이저 폴트**: 디스크에서 읽어야 함(파일 기반 mmap, 스왑-인). 폴트 스레드는 슬립한다. 메이저 폴트율은 1급 지연 지표다(`time`, `ps -o min_flt,maj_flt`).
- **스래싱(thrashing)**: 워킹 셋이 RAM을 초과 → 메이저 폴트 연속 → 디스크 대기 중 CPU 유휴. 처방: RAM 증설, 워킹 셋 축소, 콜드 데이터 분리 — 페이저 "튜닝"이 먼저가 아니다.

### mmap: 파일을 메모리처럼

```c
void *p = mmap(NULL, len, PROT_READ, MAP_PRIVATE, fd, 0);
```

- 파일(또는 익명 메모리)을 주소 공간에 매핑한다. **공유** 매핑은 쓰기를 파일과 다른 매퍼에 전파(공유 라이브러리, IPC의 기반), **사설** 매핑은 COW다.
- `madvise()` 힌트(`SEQUENTIAL`, `RANDOM`, `WILLNEED`, `DONTNEED`, `HUGEPAGE`)로 성능 민감 코드가 선행 읽기와 축출을 조종할 수 있다.
- 대부분 언어 런타임은 힙을 `brk`/`sbrk`가 아닌 익명 `mmap`으로 할당한다.

### Copy-on-Write와 fork

- `fork()` 후 부모와 자식은 모든 물리 페이지를 읽기 전용으로 공유한다. 첫 쓰기에서 폴트가 나고 커널이 페이지를 복사해 작성자에게 사본을 준다. 결과: 빠른 프로세스 생성, 지연된 비용 지불.
- 같은 메커니즘이 공유 라이브러리(코드 페이지를 모든 프로세스가 공유)와 `MAP_PRIVATE` 파일 매핑의 기반이다.

## 흔한 함정

1. **지연 예산에서 페이지 폴트 비용 무시**: 메이저 폴트 1회는 ~ms(디스크) vs ~ns(TLB 적중). 대용량 파일을 mmap하고 랜덤 접근하면 "CPU가 느린 것"처럼 보이는 테일 지연이 생긴다.
2. **THP + 지연 민감 할당자**: THP의 백그라운드 컴팩션(`khugepaged`)이 프로세스를 멈출 수 있다. THP 환경의 Redis 지연 스파이크가 대표 사례 — `echo never > /sys/kernel/mm/transparent_hugepage/enabled`가 표준 Redis 가이드다.
3. **오버커밋의 역습**: Linux 기본 휴리스틱 오버커밋은 `malloc`을 성공시키고 실제 접근 시 **OOM killer**로 죽인다. 그에 맞게 설계하라(`vm.overcommit_memory`, cgroup 제한) — OOM-kill을 설계 입력으로 다뤄라.
4. **SSD 스왑을 공짜로 취급**: 빠른 SSD의 스왑도 폴트당 ~100 µs — 콜드 페이지엔 괜찮지만 핫 루프엔 치명적이다. 여유 RAM이 아니라 `maj_flt`와 스왑-인율을 모니터링하라.
5. **NUMA 맹목**: 멀티 소켓 머신에서 페이지는 한 노드에 산다. 원격 접근은 1.3–2배 비싸다. 메모리-바운드 서비스는 스레드를 고정하고 로컬에 할당하라(`numactl`, `mbind`).
6. **madvise 없는 mmap**: 기본 선행 읽기는 순차 접근을 가정한다. 거대 매핑 위 랜덤 접근은 I/O 낭비와 페이지 캐시 오염을 부른다. 접근 패턴을 커널에 알려줘라.
