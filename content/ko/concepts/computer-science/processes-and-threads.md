# 프로세스와 스레드

> [English version](/en/concepts/computer-science/processes-and-threads)

**프로세스(process)** 는 독자적인 주소 공간을 가진 실행 중인 프로그램이고, **스레드(thread)** 는 프로세스 내부에서 스케줄링되는 가장 작은 실행 단위로, 같은 프로세스의 메모리를 공유한다. 동시성에 관한 성능·정확성·OS 설계의 모든 논의는 이 구분에서 출발한다.

## 정의

- **프로세스**: 실행 중인 프로그램의 인스턴스. 독자적인 가상 주소 공간, 파일 디스크립터, 보안 자격증명, 하나 이상의 스레드를 소유한다. 커널은 **PCB(Process Control Block)** 로 관리한다: PID, 상태(new/ready/running/waiting/terminated), 프로그램 카운터, 레지스터, 메모리 맵, 열린 파일, 스케줄링 우선순위.
- **스레드**: 프로세스 내부의 제어 흐름. 자신만의 스택·레지스터·프로그램 카운터를 갖지만, 힙·코드·파일 디스크립터는 같은 프로세스의 스레드끼리 **공유**한다.
- **멀티프로세싱 vs 멀티스레딩**: 프로세스 간 통신은 IPC(파이프, 소켓, 공유 메모리)로 하고, 스레드는 공유 메모리에 직접 접근하므로 빠르지만 명시적 동기화가 필요하다.

## 왜 중요한가

- **격리 vs 속도**: 프로세스 하나가 죽어도 다른 프로세스는 살지만, 스레드 하나가 죽으면 프로세스 전체가 죽는다. 서버 설계(Chrome의 멀티프로세스 탭 vs Nginx의 스레드/이벤트 워커)의 근본적인 신뢰성/성능 트레이드오프다.
- **멀티코어 활용**: 단일 스레드 프로세스는 코어 하나만 쓴다. 추가 코어를 처리량으로 바꾸는 수단이 스레드(또는 프로세스)다.
- **블로킹 I/O**: 한 스레드가 디스크·네트워크를 기다리는 동안 다른 스레드가 계속 일한다 — 반응형 서버와 UI의 기반이다.
- **비용 모델**: 프로세스 생성(`fork` + `exec`)은 스레드 생성보다 수 order 무겁다. 프로세스 간 컨텍스트 스위치는 TLB를 비우지만, 프로세스 내부 스레드 전환은 더 싸다.

## 동작 원리

### 프로세스 생명주기와 상태

```
new → ready ⇄ running → waiting → terminated
              (스케줄러 디스패치)  (I/O 대기)
```

- **스케줄러**가 CPU를 ready 상태의 프로세스/스레드에 분배한다. 선점형 스케줄러(Linux CFS — Completely Fair Scheduler)는 가상 런타임 회계로 타임슬라이스를 나눠 모든 실행 가능 태스크에 공평한 몫을 준다.
- **컨텍스트 스위치**: 커널이 나가는 태스크의 레지스터/PC/스택 포인터를 PCB/TCB에 저장하고 들어오는 태스크의 것을 복원한다. 레지스터 작업 자체보다 캐시/TLB 오염이 더 큰 간접 비용이다.

### fork, exec, Copy-on-Write

```c
pid_t pid = fork();   // 부모는 자식 PID, 자식은 0을 받음
if (pid == 0) { execl("/bin/ls", "ls", NULL); }
```

- `fork()`는 호출 프로세스를 복제한다. 현대 커널은 **COW(copy-on-write)** 를 사용한다: 부모와 자식이 읽기 전용 표시된 물리 페이지를 공유하다가 쓰기가 발생하면 복사하므로, 메모리가 갈라지기 전까지 `fork`는 싸다.
- `exec()`는 프로세스 이미지를 새 프로그램으로 교체한다. 셸, 프리포킹 서버, 컨테이너 런타임이 모두 fork+exec(또는 `posix_spawn`) 위에 구축된다.

### 스레드: 모델과 구현

- **유저 스레드 (M:N / 그린 스레드)**: 런타임이 스케줄링 (Go 고루틴, Erlang 프로세스, Java 가상 스레드/Project Loom). 생성 비용은 수 KB라 수백만 개도 가능하다. 런타임이 소수의 커널 스레드 위에 다중화한다.
- **커널 스레드 (1:1)**: 유저 스레드마다 커널 스케줄링 엔티티가 대응 (pthread, `std::thread`). 생성 비용은 스택 ~1–8 MB + 커널 객체라서 실용 한계는 수천 개 수준이다.
- **스레드 풀 패턴**: N개 워커를 미리 띄우고 큐로 일을 먹인다. 메모리를 제한하고 생성 비용을 상각하며 백프레셔를 제공한다. 실전 서버는 거의 모두 이 방식을 쓴다.

### 동기화 프리미티브

| 프리미티브 | 용도 | 비용/비고 |
|---|---|---|
| 뮤텍스 | 임계 구역 상호 배제 | Linux futex 기반: 경합 없으면 유저공간에서만 처리 |
| 세마포어 | 자원 슬롯 개수 세기 | 뮤텍스의 일반화 |
| 조건 변수 | 조건이 참이 될 때까지 대기 | 항상 루프에서 조건 재확인 (spurious wakeup) |
| RWLock | 다수 읽기 / 단일 쓰기 | 읽기-쓰기 기아(starvation) 정책이 중요 |
| Atomic / CAS | 락-프리 카운터, 큐 | 락-프리 알고리즘의 기반, 메모리 순서가 미묘함 |

- **경쟁 조건(race condition)**: 제어되지 않은 스레드 엇갈림에 결과가 달라짐. 단일 락으로 보호되는 불변식을 세우거나, 메시지 패싱·불변 데이터로 공유 자체를 없애서 해결한다.
- **교착상태(deadlock)** (Coffman 조건): 상호 배제 + 점유 대기 + 비선점 + 순환 대기. 처방: 전역 락 순서, 타임아웃+백오프, 또는 락-프리 설계.

## 흔한 함정

1. **"그냥 플래그"에 대한 데이터 레이스**: 스레드 간 공유되는 동기화 없는 불리언은 C++/Rust에서 미정의 동작, Java에서 `volatile`/atomic 없이는 가시성 미보장이다. 베어 변수 대신 atomic이나 락을 쓴다.
2. **블로킹 호출을 락 안에서**: 뮤텍스를 쥔 채 sleep이나 I/O를 하면 서브시스템 전체가 직렬화되고 교착상태를 부른다. 임계 구역은 최소로 유지한다.
3. **대규모 연결에 thread-per-connection**: 1만 연결 × 8 MB 스택 = 80 GB 가상 메모리 + 스케줄러 스래싱. 풀, 넌블로킹 I/O, 그린 스레드를 쓴다.
4. **fork 안전성**: 멀티스레드 프로그램에서 `fork`와 `exec` 사이에는 async-signal-safe 함수만 호출할 수 있다(자식은 스레드 하나만 살아남지만 뮤텍스 상태는 전부 상속). 즉시 `exec` 한다.
5. **폴스 셰어링(false sharing)**: 두 스레드가 같은 캐시 라인의 인접 필드에 쓰면 라인 소유권이 코어 간에 튀면서 확장성이 무너진다. 핫 필드는 스레드별로 분리·패딩한다.
6. **메모리 모델 무시**: "x86에서 돌아간다"는 가정으로 짠 락-프리 코드는 순서 보장이 약한 ARM에서 깨진다. 언어 수준 atomic과 명시적 순서(ordering)를 쓴다.
