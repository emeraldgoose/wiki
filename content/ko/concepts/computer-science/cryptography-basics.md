# 암호학 기초

**암호학**은 전송 중·저장 중 데이터에 기밀성, 무결성, 진정성을 준다. 소수의 기본 요소(암호, 해시, MAC, 서명)를 TLS 같은 프로토콜로 조합해 만든다. 수학은 강하다. 실제 실패는 거의 전부 기본 요소를 *깨서*가 아니라 *잘못 써서* 일어난다.

## 정의

- **기밀성**: 키 보유자만 데이터를 읽는다(암호화). **무결성**: 변조가 발각된다(해시, MAC). **진정성**: 상대가 주장하는 그 사람이다(서명, 인증서). 대부분 프로토콜은 셋을 한꺼번에 요구한다.
- **대칭키 암호**: 하나의 공유 비밀키로 암호화·복호화한다(AES-256-GCM, ChaCha20-Poly1305). 빠르다(~GB/s). 다만 양쪽이 미리 키를 공유해야 한다.
- **공개키 암호**: 공개키로 암호화·검증하고 개인키로 복호화·서명한다(RSA, Curve25519/P-256 위 ECDH/ECDSA). 키 분배를 풀지만 ~1000배 느리다. 대량 데이터가 아니라 대칭 세션 키 합의에 쓴다.
- **암호학적 해시**: 원상·제2원상·충돌 내성을 가진 단방향 지문(SHA-256, SHA-3, BLAKE3). 입력이 하나라도 바뀌면 다이제스트가 눈사태처럼 바뀌고, 같은 다이제스트의 두 입력을 찾는 것은 불가능해야 한다.
- **MAC / 디지털 서명**: MAC(HMAC-SHA256)은 공유 비밀 보유자에게 무결성을 증명하고, 서명(Ed25519, ECDSA, RSA-PSS)은 공개키 보유자 누구에게나 작성자를 증명해 부인 방지를 준다.

## 왜 중요한가

- **민감한 모든 것이 의존한다**: HTTPS 세션, 비밀번호 저장, API 토큰, 소프트웨어 업데이트, 디스크 암호화. 기본 요소 오용 하나(ECB 모드, 고정 IV)가 보장 전체를 조용히 무효화한다.
- **위협 모델이 기본 요소를 정한다**: 디스크 암호화(대칭, 키 보유자 하나) 대 릴리스 출처 증명(서명, 검증자는 전 세계) 대 비밀번호 저장(느리고 솔트 친 KDF, 되돌릴 수 있는 암호화 금지). 기본 요소를 잘못 고르면 구조적으로 실패한다.
- **성능이 프로토콜 설계를 빚는다**: TLS 핸드셰이크는 ECDH를 한 번 써서 대칭 세션 키를 뽑고, 대량은 AES-GCM/ChaCha20으로 암호화한다. 하이브리드 구조 덕분에 웹 전체 암호화가 감당된다.
- **양자 지평선**: Shor 알고리즘은 충분히 큰 양자 컴퓨터에서 RSA/ECDSA를 깬다. NIST 양자내성 표준(키 교환 ML-KEM, 서명 ML-DSA, 2024)이 지금부터 준비할 이전 경로다.

## 동작 원리

### 대칭 암호를 제대로 쓰기

- **AEAD만 쓴다**: AES-256-GCM이나 ChaCha20-Poly1305는 기밀성과 무결성을 한 구조에 묶는다. 변조된 암호문은 위조 평문을 내놓는 대신 복호화에 실패한다. 날 CBC/CTR에 검사를 나사로 붙이지 않는다.
- **Nonce는 한 키 아래에서 절대 재사용 금지**(GCM은 nonce 재사용에 치명적으로 무너져 키가 복원된다). 랜덤 96비트 nonce도 카운터도 된다. XChaCha20의 192비트 nonce는 대규모 랜덤 생성을 감당한다.
- **키 유도**: 마스터 비밀에서 용도별 키를 HKDF로 뽑는다. 비밀번호는 Argon2id, scrypt, bcrypt(느리고, 솔트 있고, 메모리 하드)로 저장한다. SHA-256 단독 같은 빠른 해시는 공격자가 초당 수십억 추측을 하게 해준다.

### 공개키 장치

```
키 교환 (ECDH):   A와 B가 각자 개인키와 상대 공개키를 결합 → 같은 공유 비밀
서명 (Ed25519):   Sign(개인키, 메시지) → sigma, Verify(공개키, 메시지, sigma) → 참/거짓
인증서 (X.509):   CA 서명이 "이 공개키는 example.com 것이다"를 묶음 → 브라우저는 루트 저장소로 신뢰
```

- **전방향 비밀성**: ECDHE는 세션마다 일회성 키를 만들어 서버 장기 키가 털려도 과거 트래픽이 안 풀린다. 최신 TLS 1.3은 기본 제공한다. 1.3에서 사라진 정적 RSA 키 전송은 그렇지 못했다.
- **서명 대 MAC**: 빌드 서버는 릴리스에 서명(누구나 검증, 서명은 그것만 가능), 비밀을 공유하는 마이크로서비스 사이는 웹훅에 HMAC(어느 쪽이 만들었어도 상관없다. 둘 다 신뢰하므로 괜찮다).

### TLS 1.3 핸드셰이크 요약

1. ClientHello(지원 버전, 암호 모음, 일회성 ECDH 공유) → ServerHello(선택 모음, 자기 ECDH 공유, 인증서).
2. 양쪽이 세션 키 유도, 서버는 CertificateVerify로 개인키 보유 증명, Finished MAC으로 변조 없음 확인.
3. 애플리케이션 데이터는 레코드별 nonce의 AEAD 아래 흐른다. 재접속은 PSK 티켓 재개로 전체 핸드셰이크 생략.
4. 신뢰 닻은 루트 CA 저장소, Certificate Transparency 로그는 부정 발급을 공개 감사 가능하게 한다.

## 흔한 함정

1. **직접 만든 암호/프로토콜**: 자작 XOR "암호화"나 자택 핸드셰이크는 Kerckhoffs 원칙과 동료 검토에서 진다. 검증된 기본 요소(libsodium, age, TLS)를 조합한다.
2. **ECB 모드와 고정 IV**: ECB는 평문 패턴을 흘린다(유명한 펭귄 그림). 예측 가능 IV의 CBC는 BEAST 계열 공격을 불렀다. 항상 고유 nonce의 AEAD를 쓴다.
3. **솔트 없는 SHA-256/MD5 비밀번호 해싱**: 레인보우 테이블과 GPU가 수 분에 깬다. 사용자별 솔트의 Argon2id/scrypt/bcrypt에 작업량을 얹고 시간이 지나 올린다.
4. **인증서 검증 건너뛰기**: "임시로" 검증을 끄거나 아무 인증서나 받으면 MITM 초대다. 시스템 신뢰 저장소로 기대를 고정한다. DANE·키 피닝은 정당할 때만 쓴다.
5. **타이밍 부채널**: MAC을 `==`로 비교하면 타이밍으로 접두 길이가 샌다. 상수 시간 비교를 쓴다. RSA/ECDSA도 상수 시간·결정적 nonce(RFC 6979) 구현이 필요하고, Ed25519가 낫다.
6. **코드·로그·이미지의 키**: 하드코딩 비밀은 저장소와 컨테이너 레이어로 샌다. 키는 KMS/HSM·비밀 관리자에 두고 주기 교체하며 모든 사용을 기록한다. 소스에는 절대 안 둔다.
