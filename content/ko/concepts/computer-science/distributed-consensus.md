# 분산 합의

**요약:** 분산 합의는 일부 머신이 고장나거나 메시지가 지연되어도 여러 머신이 하나의 값(또는 순서화된 로그)에 동의하게 한다. 복제 상태 머신(etcd, ZooKeeper, Consul)의 토대이며, 리더 선출·설정 저장소·강한 일관성의 메타데이터를 떠받친다. 핵심 결과는 **FLP 불가능성**(완전 비동기 네트워크에서 1개 고장만 있어도 결정적 합의 불가)과, 타임아웃·과반수·리더 선출로 이를 우회하는 실용 프로토콜 **Paxos**·**Raft**이다.

## 정의

- **합의 문제:** N개 프로세스가 각자 값을 제안하고, 모든 정상 프로세스가 결국 *같은* 값을 *결정*해야 하며, 결정값은 누군가 제안한 값이어야 하고(타당성) 종료가 보장되어야 한다.
- **상태 머신 복제:** 합의를 반복 실행해 명령의 순서 로그에 합의한다. 모든 복제본이 같은 로그를 실행하므로 동일 상태를 유지한다. Raft/etcd가 실제로 제공하는 것이다.
- **결함 모델:** *crash-stop*(조용히 정지) vs *비잔틴*(임의·악의적 동작). 크래시 f개 허용에 2f+1대, 비잔틴 f개 허용에 3f+1대가 필요하다.
- **쿼럼:** 과반수(⌊N/2⌋+1). 두 과반수는 항상 겹치므로, 과반수가 수락한 값은 몰래 덮어쓸 수 없다. 아래 모든 프로토콜이 의존하는 교집합 성질이다.

## 왜 중요한가

- **모든 컨트롤 플레인이 의존한다.** 쿠버네티스는 클러스터 상태를 etcd(Raft)에 저장하고, Consul/ZooKeeper의 디스커버리·락·설정이 일관된 로그를 가정한다.
- **일관성의 경계를 긋는다.** 장애 속 선형화 가능한 메타데이터가 필요하면 합의가 필수이다. 더 가벼운 원시 수단은 없다. 파티션 시 브레인 스플릿 나는 "간단한" 리더 선출 직접 구현을 막아준다([[cap-theorem]] 참조).
- **블록체인은 비잔틴 결함 하의 합의이다.** PBFT, Tendermint, 나카모토 합의는 결함 모델만 적대적인 같은 문제이다.

## 동작 방식

### FLP 불가능성 (Fischer–Lynch–Paterson, 1985)

*완전 비동기* 네트워크(메시지 지연에 상한 없음)에서 1개 이상 고장 가능 시, 종료를 보장하는 **결정적 합의 프로토콜은 존재하지 않는다**. 직관: 죽은 노드와 느린 노드를 구분할 수 없어, 적대적 스케줄이 시스템을 영원히 미결정(bivalent) 상태에 둔다. 실용 탈출구: 부분 동기(partial synchrony) 가정 — 타임아웃과 장애 감지기를 둔다(실제 시스템이 하는 일).

### Paxos (Lamport, 1998)

- **역할:** 제안자·수락자·학습자. 투표 번호 n마다 2단계:
  1. **Prepare(n)/Promise:** 제안자가 과반수에 n 미만 투표 무시 약속을 요청. 수락자는 이미 수락한 가장 큰 번호의 값을 반환.
  2. **Accept(n, v)/Accepted:** 제안자는 자신의 값, 또는 반환된 값 중 가장 큰 번호의 값을 보낸다(이 규칙이 합의를 보존). 수락자는 더 큰 번호에 약속하지 않았으면 수락.
- 과반수가 수락한 값은 *선택*된 것이며, "가장 큰 번호" 규칙 덕분에 이후 투표도 같은 값을 제안한다.
- 원 논문만으로 정확히 구현하기 악명 높다. Multi-Paxos(고정 리더가 1단계를 생략)가 시스템들이 근사하는 형태이다.

### Raft (Ongaro & Ousterhout, 2014)

이해 가능성을 목표로 설계되었으며 합의를 세 조각으로 분해한다:

1. **리더 선출:** 팔로워가 타임아웃(무작위 150–300ms) 시 후보가 되고, 과반수 득표 시 *텀*의 리더가 된다. 무작위화가 표 분산을 막는다.
2. **로그 복제:** 리더가 클라이언트 명령을 받아 추가하고 AppendEntries RPC로 복제한다. 과반수에 올라가면 *커밋*되고 상태 머신에 적용된다.
3. **안전성:** 선출 제한 — 후보의 로그가 과반수만큼 최신일 때만 당선 — 덕분에 리더는 모든 커밋 항목을 보유하고, 커밋된 항목은 절대 손실·덮어쓰기되지 않는다.

### 비잔틴 허용 (PBFT, Castro–Liskov 1999)

- 3f+1 복제본이 비잔틴 f개를 허용한다. 3단계(pre-prepare → prepare → commit), 단계마다 2f+1개 일치 메시지, MAC/서명으로 위조 방지.
- 비용: 결정당 O(n²) 메시지. BFT가 작은 클러스터에 머물렀던 이유이며, 현대 체인이 선형 변형(HotStuff)에 투자하는 이유이다.

## 흔한 함정

- **쿼럼 없는 리더 선출 직접 구현.** "가장 큰 IP 승리"나 DB 플래그 방식은 파티션 시 이중 선출된다. 리더십에는 검증된 합의 저장소를 써라.
- **FLP 가정 무시.** 테스트에서 "정확한" 프로토콜이 운영에서 DNS/GC 멈춤(비동기처럼 보임) 시 행에 걸린다. 타임아웃·지터 재시도·pre-vote(Raft의 disruptive 재선출 방지)를 함께 둬라.
- **리더에서 무검증 읽기.** 파티션된 리더는 오래된 읽기를 낸다. read-index/lease 읽기나 쿼럼 경유 선형화 읽기를 써라.
- **짝수 노드 수.** 4대는 3대와 같은 1개 고장만 허용하면서 쿼럼은 3개 필요 — 느리고 회복력 이득이 없다. 홀수(3, 5)를 써라.
- **합의와 가십 혼동.** 가십은 전파는 하지만 장애 시 순서에 합의하지 않는다. 멤버십(SWIM)용이지 메타데이터 로그용이 아니다.
