# 동시성 대 병렬성 (Concurrency vs Parallelism)

[English version](/en/concepts/computer-science/concurrency-vs-parallelism.md)

> 동시성(concurrency)은 많은 일을 한꺼번에 *다루는* 것(수명 겹침, 엇갈린 실행)이고, 병렬성(parallelism)은 많은 일을 *동시에 하는* 것(여러 코어의 동시 실행)이다. 올바른 동시 프로그램은 공유 상태의 문제 — 레이스, 교착상태, 가시성 — 를 길들여야 한다.

## 정의

- **동시성**: 하나의 프로그램이 수명이 겹치는 여러 작업을 관리한다. 단일 코어에서 실행이 엇갈릴 수 있으며(타임슬라이싱, 이벤트 루프) 작업들은 *함께 도는 것처럼* 보인다.
- **병렬성**: 여러 작업이 문자 그대로 동시에 실행되며, 여러 코어(별도 CPU의 스레드, SIMD 레인, GPU 코어, 분산 노드)가 필요하다.

고전적 표현 (Rob Pike): *"Concurrency is about dealing with lots of things at once. Parallelism is about doing lots of things at once."* 동시성은 프로그램 구조의 속성이고, 병렬성은 하드웨어 실행의 속성이다. 동시 프로그램(Go 고루틴, async 태스크)은 단일 코어에서 병렬성 없이 돌 수 있으며, 병렬 실행은 동시 설계 *안에* 도입되는 경우가 많다.

## 왜 중요한가

- **성능**: I/O 바운드 서버는 동시성(async/이벤트 루프)으로 1만 연결을 처리하고, CPU 바운드 작업(렌더링, 학습, 시뮬레이션)은 32코어를 쓰려면 진짜 병렬성이 필요하다.
- **정확성은 어렵다**: 데이터 레이스, 교착상태, 기아는 비결정적이어서 테스트는 통과하고 새벽 3시 운영에서 터진다.
- **시스템 설계**: 모든 백엔드 결정 — 요청당 스레드 대 이벤트 루프, 락 대 락-프리, 공유 메모리 대 메시지 패싱 — 은 동시성 모델 결정이다.
- **하드웨어 추세**: 단일 코어 스케일링은 ~2005년에 끝났고, 이후 모든 속도 향상은 병렬성(멀티코어, GPU, 클러스터)에서 온다.

## 동작 원리

### 동시성 모델

| 모델 | 단위 | 실행 방식 | 예시 | 적합한 경우 |
|------|------|-----------|------|--------------|
| 스레드 + 공유 메모리 | OS/커널 스레드 | 선점 스케줄링, 공유 힙 | Java 스레드, pthreads | CPU 바운드 병렬 작업, 레거시 코드 |
| 이벤트 루프 / async | 태스크/코루틴 | 단일 스레드, 논블로킹 I/O | Node.js, Python asyncio, nginx | 대기 중인 다수 I/O 연결 |
| 액터 / 메시지 패싱 | 액터 | 공유 상태 없음, 비동기 메시지 | Erlang, Akka, Go 채널 (CSP) | 분산, 장애 내성 시스템 |
| SIMD / 데이터 병렬 | 레인 | 한 명령, 다수 데이터 | NumPy, GPU, AVX | 수치 루프, ML 추론 |
| 분산 | 프로세스/노드 | 네트워크 메시지 | MapReduce, Spark, 마이크로서비스 | 인터넷 규모 데이터 |

### 스레드 대 Async (대비)

요청당 스레드 (블로킹 I/O, 스레드당 ~MB 스택):

```python
# 스레드: 코드는 단순, 그러나 1만 스레드 = GB 단위 스택 + 컨텍스트 스위칭 비용
with ThreadPoolExecutor(max_workers=100) as pool:
    pool.map(fetch_url, urls)
```

Async 이벤트 루프 (한 스레드, I/O에서 양보하는 태스크):

```python
# asyncio: 한 스레드로 1만 연결, 코드는 절대 블로킹 금지
async with aiohttp.ClientSession() as s:
    await asyncio.gather(*[fetch(s, u) for u in urls])
```

경험칙: **I/O 바운드 → async/동시성**(스레드 낭비 없이 대기), **CPU 바운드 → 스레드/프로세스/병렬성**(CPython 같은 GIL 언어는 CPU 병렬에 멀티프로세싱 필요).

### 세 가지 위험

**1. 데이터 레이스.** 두 스레드가 동기화 없이 공유 상태에 접근하고 최소 하나가 쓰기인 경우:

```python
counter = 0
def inc():
    global counter
    for _ in range(100_000):
        counter += 1   # 읽기-수정-쓰기: 두 스레드가 엇갈리면 업데이트 손실
```

해결: 락/뮤텍스, 아토믹, 또는 격리(단일 소유자 + 메시지 패싱).

**2. 교착상태.** 네 조건 (Coffman): 상호 배제, 점유 대기, 비선점, 순환 대기. 정석: 스레드 A는 락 1을 쥐고 락 2를 원하고, 스레드 B는 2를 쥐고 1을 원함. 해결: 전역 락 순서, 락 타임아웃/`try_lock`, 락-프리·메시지 패싱 설계.

**3. 가시성 / 메모리 모델.** 종이 위 레이스가 없어도 CPU 캐시와 컴파일러 재정렬 때문에 한 코어의 쓰기가 메모리 배리어 없이 다른 코어에 *보이지* 않을 수 있다(`volatile`, 순서 지정 아토믹, 채널 연산). "x86에서 됐으니 된다"는 추론 금지 — 언어 메모리 모델(Java JMM, C++11 아토믹, Go 메모리 모델)이 계약이다.

### 동기화 도구함

| 도구 | 비용 | 용도 |
|------|------|------|
| 뮤텍스/락 | 블로킹, 경합은 직렬화 | 공유 상태의 짧은 임계 구역 |
| 읽기-쓰기 락 | 읽기 동시 허용 | 읽기 위주 워크로드 |
| 세마포어 | 카운터 기반 허가 | 유한 자원 (커넥션 풀) |
| 조건 변수/채널 | 대기/신호 | 생산자–소비자 핸드오프 |
| 아토믹/CAS | 락-프리 고속 경로 | 카운터, 락-프리 구조 |
| 불변 데이터 + 메시지 패싱 | 복사 오버헤드 | 공유 상태 자체를 제거 |

**Amdahl 법칙**이 승리의 상한을 정한다. 작업의 `p` 비율이 `n` 코어로 병렬화되면 속도 향상 ≤ 1 / ((1−p) + p/n). 90% 병렬화 프로그램을 32코어로 돌려도 상한은 ~7.6× — 직렬 10%가 지배한다. 직렬 부분을 최적화하거나 더 병렬화하라.

## 흔한 함정

- **설계 리뷰에서의 용어 혼동.** "동시하게 만들었다"(async I/O)는 CPU 바운드 코드를 빠르게 하지 못하고, "병렬로 만들었다"(32 스레드)는 대기 중인 1만 연결에 도움이 안 된다. I/O 바운드 대 CPU 바운드에 맞는 도구를 써라.
- **과도한 락 (전부 직렬화).** 거대한 전역 락 하나면 32 스레드가 순차 실행된다 — 정확하지만 무의미하다. 임계 구역은 최소로, 샤드별 락이나 락-프리 읽기를 선호하라.
- **부족한 락 ("내 머신에선 되는데" 레이스).** 레이스는 타이밍 의존이라 단위 테스트를 통과한다. 스트레스 테스트와 새니타이저(ThreadSanitizer, `-race` 계열)가 단위 테스트가 놓치는 것을 잡는다.
- **일관성 없는 락 순서의 교착.** 두 락을 서로 다른 곳에서 다른 순서로 잡으면 교착할 수 있다. 전역 순서를 강제하거나 서브시스템당 단일 락을 써라.
- **이벤트 루프 블로킹.** async 코드의 200ms 동기 호출 하나가 1만 연결 *전부*를 멈춘다. 블로킹 작업은 스레드 풀로 넘겨라.
- **GIL 무시 (CPython).** 스레드는 CPU 바운드 파이썬을 병렬화하지 못한다. 멀티프로세싱, GIL을 놓는 네이티브 확장(NumPy), 또는 다른 런타임을 써라.
- **성급한 분산화.** 분산 병렬은 네트워크 분할과 정확히 한 번(exactly-once) 문제를 더한다 — 단일 머신 병렬(코어, SIMD, GPU)을 먼저 소진하라.
